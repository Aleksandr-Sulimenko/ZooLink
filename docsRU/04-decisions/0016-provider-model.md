# ADR-0016: Модель провайдера — организация | физлицо | агент-провайдер

**Status**: Proposed — ожидает матрицу верификации провайдеров от security+legal (владелец рассмотрел Q1–Q6 2026-07-01)
**Date**: 2026-07-01
**Relates to**: [ADR-0014](0014-offering-supertype-polymorphic-seam.md), [ADR-0006](0006-ai-agents-operate-platform.md) & [ADR-0011](0011-agent-principal-actor-model.md) (agent-as-principal), домен организаций, Legal launch-compliance checklist (`docs/legal/launch-compliance-checklist.md`).
**Source vision**: `docsRU/01-discovery/future-features.md` §B (Provider-абстракция), §C (Доверие — верификация пропорциональна риску).

> **ЧТО** — Определяем единую абстракцию **Provider** — *кто стоит за не-животным Offering* — с тремя видами: **ORG** (клиника/гостиница/магазин, опирается на существующий домен организаций), **INDIVIDUAL** (соло-грумер/выгульщик, человек-пользователь, действующий в роли провайдера), **AGENT** (ИИ-консультант, `principal_type=AGENT`, ADR-0006/0011). К Provider'у привязывается **запись верификации, пропорциональная риску категории**, которая гейтит badge высокого доверия и — для регулируемых категорий — иммунитет платформы как информационного посредника.
>
> **ПОЧЕМУ** — ServiceOffering / ProductOffering / ConsultationOffering (ADR-0014) все нуждаются в ответе на «кто это предлагает, и можем ли мы им доверять?». Три вида реальны и различны: уже смоделированная организация, одинокий человек без организации, и ИИ-принципал, которым управляет сама платформа. Модель one-size (напр. «провайдер = всегда организация») вынуждает фейковые орги для соло-провайдеров и не имеет места для ИИ-провайдера. Legal явно: **верификация лицензии/личности, пропорциональная риску, — это *условие* сохранения иммунитета посредника** (ст.1253.1 ГК; обязанности агрегатора ЗоЗПП ст.9/12) для регулируемых категорий (вет, аптека, кинолог; ВетИС/«Меркурий», 498-ФЗ).
>
> **ПОЧЕМУ ТАК ЛУЧШЕ для всего проекта** — Переиспользует домен организаций вместо его дублирования; позволяет прогрессивному role-онбордингу (один аккаунт → провайдер) работать без перерегистрации (BR про комфорт); делает путь ИИ-провайдера *типизированным* случаем модели актора, уже решённой в ADR-0006/0011, а не спец-приделкой; и превращает «доверие» в явный, risk-tiered, юридически нагруженный шов верификации (form-now, поведение gated), а не в довесок. Object-level authz на каждом provider-owned объекте (IDOR риск №1) — обязательно.

## Context and Problem Statement

Шов Offering (ADR-0014) ссылается на *провайдера*. Vision называет три формы провайдера и привязывает доверие к **верификации, пропорциональной риску**:
- **ORG-backed** — вет-клиника, гостиница для животных, магазин. Домен `organization` уже моделирует идентичность юрлица, org-admin'ов, ИНН/КПП.
- **INDIVIDUAL** — соло-грумер/выгульщик/дрессировщик без организации; человек-`user`, который через прогрессивные just-in-time роли начинает предлагать услугу без второй регистрации.
- **AGENT** — ИИ-провайдер юр/консультаций, `principal_type=AGENT`, управляемый платформой по ADR-0006/0011 (least-privilege, полный аудит, обязательный human-override при выпуске документов).

Два сквозных требования:
- **Верификация, пропорциональная риску** (security + legal): регулируемые категории (вет/аптека/кинолог) требуют лицензию/диплом → badge высокого доверия; нерегулируемые (грумер/выгульщик/передержка) требуют верифицированную личность + телефон. Верификация лицензии для регулируемых категорий — **условие иммунитета посредника** — без неё платформа рискует «соскользнуть» из нейтральной площадки в исполнителя/гаранта и потерять щит ст.1253.1.
- **Object-level authorization** на каждом provider-owned объекте (offering, booking, order, документ экспертизы) — IDOR/broken-access-control это риск №1 в кодовой базе; применяется 404-no-leak.

## Decision Drivers

1. **Переиспользовать, не дублировать** — домен орг уже есть; INDIVIDUAL и AGENT — принципалы, уже смоделированные (`users`, `principal_type`).
2. **Прогрессивные роли / BR про комфорт** — один аккаунт становится провайдером без перерегистрации.
3. **Верификация = условие иммунитета** (legal) — должна быть first-class, risk-tiered записью, а не опциональными метаданными.
4. **Agent-as-principal** (ADR-0006/0011) — AGENT-провайдер это типизированное переиспользование решённой модели актора, с least-privilege + human-override.
5. **Object-level authz везде** (security) — владение провайдера должно быть проверяемым на объект; 404-no-leak.
6. **Анти-rewrite (§5)** — форма ссылки на провайдера + `provider_kind` + verification-tier — form-now; поведение (реальный workflow верификации, badge'и) gated.

## Considered Options

### Option 1: Provider = всегда организация
Каждый провайдер обязан зарегистрировать организацию; соло-провайдеры создают org из одного человека; ИИ-провайдеры моделируются как синтетическая org.

Pros:
- Единая backing-сущность; единообразно переиспользует org-admin authz.

Cons:
- Вынуждает **фейковые org из одного человека** для соло-грумеров → трение, противоречит BR про комфорт прогрессивных ролей.
- Нет честного дома для **ИИ**-провайдера (org — юрлицо; агент — нет).
- Поля ИНН/КПП и юрлица бессмысленны для физлиц → nullable-каша.

### Option 2: Отдельная таблица Provider на вид (org_providers, individual_providers, agent_providers)
Три параллельные provider-таблицы, каждая со своим владением и верификацией.

Pros:
- Каждый вид полностью заточен.

Cons:
- Утраивает шов верификации + discovery + object-authz; read-model из ADR-0014 нужны три join-пути.
- Кросс-видовые запросы («все провайдеры рядом») фрагментируются.

### Option 3: Одна абстракция Provider с `provider_kind` над существующими принципалами + risk-tiered запись верификации (Выбрано)
Единая концепция Provider, идентифицируемая **ровно одним из** `organization_id` (kind=ORG) **xor** `user_id` (kind=INDIVIDUAL или AGENT), с `principal_type`, различающим AGENT, и **записью верификации**, несущей risk tier. Шов Offering ссылается на Provider; object-level authz резолвится через backing-принципала (org-admin для ORG, владелец для INDIVIDUAL, operating-account для AGENT).

Pros:
- Переиспользует домен org (ORG) и модель user/principal (INDIVIDUAL/AGENT) — без дублирования.
- Один шов верификации, один join discovery, один резолв object-authz.
- AGENT — типизированный случай ADR-0006/0011, а не спец-путь.
- Прогрессивная роль: `user` получает Provider без нового аккаунта.

Cons:
- Матрица «ровно один из org/user» + `provider_kind` + `principal_type` должна быть CHECK-constrained и задокументирована (зеркалит паттерн ownership XOR, уже используемый в animals/ownership_transfers).
- Тиры верификации должны быть определены на категорию (security + legal владеют матрицей).

## Decision

Принимаем **Option 3**. Нормативные правила:

1. **`provider_kind ∈ {ORG, INDIVIDUAL, AGENT}`**, опирается на **ровно один из** `organization_id` (ORG) **xor** `user_id` (INDIVIDUAL/AGENT); `AGENT` — случай `user_id`, где backing-принципал имеет `principal_type=AGENT` (ADR-0006/0011). CHECK-constrained, зеркалит существующий паттерн ownership-XOR.
2. **Object-level authorization резолвится через backing-принципала** — ORG → org-admin (существующий `isOrgAdmin`), INDIVIDUAL → владелец (`user_id==actor`), AGENT → operating-account под least-privilege scope. Каждый provider-owned объект (offering, booking, order, документ) authz-проверяется на объект; **404-no-leak**.
3. **Верификация — first-class, risk-tiered запись на Provider'е** (form-now; workflow gated):
   - **Регулируемое / высокий риск** (вет, аптека, кинолог) → верификация лицензии/диплома → **badge высокого доверия** И **предусловие иммунитета посредника** для этой категории (legal). Провайдер, не верифицированный для регулируемой категории, НЕ ДОЛЖЕН публиковать регулируемое предложение в ней.
   - **Нерегулируемое** (грумер, выгульщик, передержка, дрессировка) → верифицированная личность + подтверждённый телефон → стандартное доверие.
4. **AGENT-провайдеры несут гарантии ADR-0006/0011** — least-privilege credentials (`service_credentials`, форма миграции 0017), полный аудит, и **обязательный human-override при выпуске любого документа/решения** (дисклеймер консультации: информационно, не юр/вет-консультация).
5. **`monetization_type` (ADR-0014) живёт на предложении, не на провайдере** — один провайдер может вести lead-gen и take-rate предложения одновременно.
6. **Тир верификации привязан к `market_scope` ADR-0015** — провайдер, верифицированный только для `pet`, не может публиковать регулируемое предложение, scope'нутое `livestock`/`both`.
7. **В MVP не выпускается никакого поведения** — таблицы провайдеров/workflow верификации gated (форма по ADR-0014, когда строится сторона услуг); *форма* (provider_kind, XOR backing, verification-tier, AGENT-типизация) зафиксирована здесь, так что активация не требует rewrite'а.

## Consequences

### Positive
- Соло, организационные и ИИ-провайдеры все вписываются в одну чистую абстракцию; домен org переиспользован.
- Верификация становится явным, юридически нагруженным, risk-tiered швом (условие иммунитета закодировано, а не подразумевается).
- AGENT-провайдер — уже решённая модель актора — когерентен с vision'ом ИИ-управляемой платформы.
- Один путь discovery/authz/верификации → меньше drift'а, меньше поверхности для IDOR.

### Negative
- Матрице provider_kind × backing × principal_type нужны CHECK-ограничения + чёткая документация.
- Пер-категорийную матрицу verification-tier нужно написать (security + legal) до открытия регулируемой стороны.

### Neutral
- MVP без изменений (провайдеров ещё нет).
- Reviews/Reputation над provider+offering — зарезервированный шов (ADR-E, позже).

## Implementation Notes (когда строится сторона услуг — не сейчас)
- Таблица Provider + `provider_kind` + XOR-backing CHECK + запись verification-tier (backend; form-now по ADR-0014).
- **security** владеет risk-матрицей верификации (каким категориям нужна лицензия vs личность); **legal** подтверждает, чьих категорий иммунитет зависит от верификации (ВетИС/«Меркурий», 498-ФЗ, 61-ФЗ для Rx — Rx остаётся OFF, отдельный gated-трек).
- alpha-analyst пишет контракт provider + верификации (object-level authz, 404-no-leak, гейт регулируемого предложения).
