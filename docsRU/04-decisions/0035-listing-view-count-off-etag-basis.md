# ADR-0035: Базис ETag / оптимистичной блокировки листинга отвязан от `updated_at` (счётчик просмотров — вне пути конкурентности)

**Статус**: Accepted
**Дата**: 2026-07-08

## Контекст и постановка проблемы

`listings.view_count` (миграция 0031, линия ADR-0018 / Wave-D) — счётчик вершины воронки,
инкрементируемый по возможности на **публичном** чтении карточки `GET /v1/listings/{id}`:

```
// listing.service.ts captureView (:294)
await this.prisma.listings.update({ where: { id: row.id }, data: { view_count: { increment: 1 } } });
```

Схема навешивает **общий** триггер `updated_at` на *каждую* таблицу с колонкой `updated_at`
(миграция 0013, `database_schema.sql:675-707`):

```
CREATE OR REPLACE FUNCTION update_updated_at_column() ... NEW.updated_at = NOW(); ...
-- авто-навешивание BEFORE UPDATE на listings (и все такие таблицы)
```

То есть триггер выставляет `updated_at = NOW()` на **любой** UPDATE строки — включая инкремент
счётчика просмотров. А **ETag листинга выводится из `updated_at`**:

```
// listing.service.ts etag() (:1246)
private etag(row: ListingRow): string { return weakEtag(`listing:${row.id}`, row.updated_at); }
// etag.util.ts weakEtag(id, updatedAt) → W/"sha1(id:updatedAt.toISOString())"
```

ETag — это **валидатор оптимистичной блокировки** для мутирующих PATCH: `assertIfMatch`
(`etag.util.ts:23`) отклоняет устаревший `If-Match` ошибкой **412 STALE_RESOURCE**. Отсюда два
структурных следствия, оба подтверждены инспекцией кода (AUDIT4 architect находка №1,
backend-engineer, data-analyst; trash-линза их вооружает):

1. **Ошибка корректности / доступности — ложный 412, блокировка редактирования.** Каждый учтённый
   анонимный просмотр двигает `updated_at` → ETag публичного чтения меняется на каждом обращении.
   Продавец (или оператор, или ИИ-оператор по ADR-0006), удерживающий ETag листинга, получает **412**
   на своём следующем PATCH с `If-Match`, потому что трафик чтения сдвинул валидатор между его GET и
   PATCH. На популярном листинге владельца можно **навсегда заблокировать от редактирования** без
   ошибки, на которую он мог бы среагировать. Это тривиальный рычаг **гриферства / DoS**: атакующий,
   ротируя IP (ключ анонимной дедупликации) или обновляя страницу через 30-минутное окно Redis-дедупа,
   заваливает листинг конкурента просмотрами → его `updated_at` «мельтешит» → правки жертвы вечно 412.

2. **Запись в строку сущности на пути чтения.** Публичное чтение выполняет `UPDATE` уровня строки на
   первичной таблице `listings`: конкуренция за «горячую строку» и MVCC-раздувание на самой горячей
   поверхности запросов, плюс условный GET (`ETag`/`Cache-Control`) на этом эндпоинте ломается на
   каждом обращении (кэширование побеждено).

Дефект **не специфичен для `view_count`.** Тот же триггер уже двигает `updated_at` (а значит и ETag),
когда приложение пишет другие **системные/производные** колонки той же строки `listings`, с которыми
правка клиента не конфликтует: `escalated_at` (маркер SLA, миграция 0024), пересчёт кэша `market` D3
(миграция 0033), `moderation_enqueued_at`. Корневая причина в том, что ETag — который обязан быть
**валидатором контента** — привязан к `updated_at`, **физическому mtime строки**, который двигает
любая запись. Починка только `view_count` оставит тот же класс бага для каждой другой не-контентной
записи.

Этот ADR решает структурный вопрос (из чего выводится ETag / токен оптимистичной блокировки и где
живёт счётчик просмотров), чтобы бэкенд-слайс мог реализовать. Он **не пишет код**.

## Драйверы решения

- **Починить поломку 412 / ETag (обязательно).** Публичное чтение не должно менять ETag листинга и не
  должно вызывать 412 на последующем PATCH с `If-Match`. Это требование корректности + доступности +
  анти-гриферства, ранг первый.
- **Убрать запись на пути чтения в базис конкурентности.** Значение, из которого выводится ETag, не
  должно никогда записываться чтением.
- **Общее, а не специфичное для view_count.** `escalated_at`, пересчёт `market` D3 и другие системные
  записи дают ту же поломку ETag; фикс должен нейтрализовать класс, а не один экземпляр.
- **Семантическая правда.** Валидатор оптимистичной блокировки должен отслеживать **видимые клиенту
  изменения контента/состояния** («изменилось ли то, что я редактирую, с момента моего чтения?»), а не
  «трогали ли строку физически». `updated_at` смешивает эти два смысла.
- **Стоимость изменения, анти-переписывание (фаза по стоимости, не по ярлыку).** Предпочесть фикс,
  который дёшев сейчас, который **не** выбрасывается более поздней масштабной эволюцией и не вынуждает
  переписывать контракт, когда счётчик позже уедет со строки.
- **Без регресса аналитики (ADR-0006, бизнес под управлением агентов).** `view_count` намеренно —
  скалярный, совещательный, best-effort счётчик (data-analyst, миграция 0031 — единственный
  безвозвратно теряемый сигнал). Фикс обязан сохранить его работающим и не деградировать. Бизнес под
  управлением агентов оптимизируется по метрикам.
- **Совместимость записи при rolling-деплое N-1.** Любая новая NOT NULL колонка на пишемой приложением
  таблице требует DEFAULT или триггера, чтобы поды N-1, не знающие колонку, могли INSERT (урок миг-0033).

## Рассмотренные варианты

### Вариант A: Отвязать базис ETag — выделенная колонка версии контента

Добавить `listings.content_updated_at TIMESTAMPTZ` (валидатор *контента*). Двигать её в `now()` только
на записях, меняющих **видимое клиенту состояние листинга** — те же записи, что сегодня легитимно
ставят `updated_at = new Date()` в сервисе (create, материальная/черновая правка, submit, одобрение/
отклонение/запрос-изменений модерацией, снятие/деактивация, отметка-продано) и две функции
каскадной деактивации в БД (линия миграции 0025). Выводить ETag из **`content_updated_at`**, а не из
`updated_at`. Системные/производные записи (инкремент `view_count`, `escalated_at`, пересчёт `market`
D3) её **не** трогают. Счётчик остаётся на строке (`view_count`), но его инкремент больше не влияет на
ETag. `updated_at` сохраняет смысл (физический mtime), его общий триггер не трогается.

Плюсы:
- **Полностью чинит №1** — просмотр (или любая системная запись) оставляет `content_updated_at`, а
  значит ETag, неизменным; PATCH продавца с `If-Match` больше не 412. Рычаг блокировки правок закрыт.
- **Чинит весь класс, а не только view_count** — `escalated_at`, пересчёт market и т.д. тоже перестают
  ломать ETag, ведь валидатор двигают лишь настоящие изменения контента/состояния.
- **Семантически верно и постоянно.** ETag становится истинным валидатором контента. Это правильный
  базис *вне зависимости от масштаба* — его **не** заменяет более поздний внестрочный счётчик
  (Вариант C); он с ним компонуется. Не выбрасывается.
- **Дёшево сейчас:** одна колонка (nullable→NOT NULL) + бэкфилл; метод `etag()` меняет одно поле; пути
  мутаций уже проносят `updated_at: new Date()`, так что добавить `content_updated_at: <тотЖеDate>`
  механически и в доменном слое, где «что есть изменение контента» и должно жить.
- **Без регресса аналитики** — `view_count` не тронут; путь инкремента не меняется.
- **Общий триггер `updated_at` остаётся общим** (в разделяемую инфраструктуру не течёт знание колонок).

Минусы:
- Сам по себе **не** убирает `UPDATE`-на-чтении горячей строки (просмотр всё ещё пишет строку) — MVCC/
  конкуренция и рычаг усиления записи остаются (смягчены 30-минутным Redis-дедупом; структурно решаются
  Вариантом C, зарезервированным ниже).
- Сервис обязан ставить `content_updated_at` на каждой записи контента/состояния, и две каскадные
  функции БД тоже — конечное, перечислимое множество писателей, но его надо выдержать (закрыто тестами),
  иначе изменение состояния может оставить валидатор устаревшим.

### Вариант B: Сделать триггер `updated_at` no-op, когда изменился только `view_count`

Изменить `update_updated_at_column()` (или триггер listings), чтобы пропускать `NEW.updated_at = NOW()`,
когда единственная изменённая колонка — `view_count` (`NEW IS DISTINCT FROM OLD` исключая `view_count`).
Оставляет ETag на `updated_at` и счётчик на строке.

Плюсы:
- Наименьшая миграция; оба симптома (поломка ETag + мельтешение `updated_at`) исчезают для пути просмотра.
- Счётчик остаётся на строке; тип на пути чтения не меняется.

Минусы:
- **Течёт знание колонок в разделяемую инфраструктуру.** Триггер авто-навешен на *каждую* таблицу с
  `updated_at` изящным выводом (миграция 0013); спец-обработка `view_count` связывает общую функцию с
  колонкой одной таблицы, а у Postgres нет чистого «distinct исключая колонку» — список исключений
  прописывается вручную и должен расти при каждой новой горячей/производной колонке.
- **Решает только `view_count`.** `escalated_at`, пересчёт `market` D3 и любая будущая производная
  колонка всё ещё ломают ETag — класс не закрыт.
- Оставляет ETag смешанным с физическим mtime (семантически мутно); лишь прячет одного писателя.
- **Не убирает `UPDATE`-на-чтении горячей строки** — конкуренция и рычаг DoS усиления записи остаются,
  как и в A.

### Вариант C: Вынести счётчик из строки сущности полностью

Перенести `view_count` в соседнюю таблицу `listing_stats` (или Redis-авторитетный счётчик, периодически
сбрасываемый воркер-тиком по образцу advisory-lock `MODERATION_ESCALATION_TICK` из миграции 0024). Строка
`listings` никогда не пишется на чтении.

Плюсы:
- **Идеально по масштабу:** полностью убирает запись на пути чтения → нет поломки ETag, нет 412, нет
  конкуренции за горячую строку, нет MVCC-раздувания и нет рычага усиления записи (находка trash-линзы
  закрыта полностью).
- Правильное долгосрочное конечное состояние для высокочастотного счётчика.

Минусы:
- **Наибольшее изменение сейчас:** соседняя таблица (или Redis-авторитетное хранилище) + воркер сброса +
  join на пути чтения + перенаправление `getAnalytics`/`toView` на новый источник + семантика
  долговечности/потерь между сбросами. Целый слайс — ради масштабной заботы, ещё не нагружающей на объёме
  MVP.
- Сам по себе **не** чинит базис ETag: даже с внестрочным счётчиком `escalated_at` / пересчёт D3 всё ещё
  двигают `updated_at`. C без A оставляет класс-бага открытым — так что правильный базис ETag (A) нужен в
  любом случае.
- Тянуть полную масштабную работу вперёд сейчас не оправдано стоимостью изменения: после A вынос счётчика
  со строки позже — **внутренний рефакторинг**, а не изменение контракта (базис ETag уже
  `content_updated_at`, а `view_count` уже читается через единый сервисный аксессор). Отсрочка **не**
  вынуждает переписывание.

## Решение

Принять **Вариант A сейчас** и **зарезервировать Вариант C** как задокументированную эволюцию Фазы-2 /
масштаба за швом, который устанавливает A. Отклонить Вариант B (течёт, частичный).

1. **Новая колонка версии контента.** Добавить `listings.content_updated_at TIMESTAMPTZ NOT NULL
   DEFAULT now()`. Это **валидатор контента/состояния** листинга. Бэкфилл однократно из `updated_at`
   (лучшее доступное приближение «последнего реального изменения»); `DEFAULT now()` сохраняется навсегда
   ради N-1 совместимости записи (под N-1, вставляющий без колонки, получает осмысленное «создано сейчас»).

2. **Смена базиса ETag.** `listing.service.ts etag()` выводит ETag из `content_updated_at`, а не из
   `updated_at`: `weakEtag(\`listing:${row.id}\`, row.content_updated_at)`. `assertIfMatch` / `If-Match`
   не меняются; теперь они сравнивают с валидатором, который чтение не двигает. Сигнатура помощника
   `weakEtag(id, Date)` не меняется (минимальный радиус поражения).

3. **Что двигает валидатор (множество записей контента/состояния).** `content_updated_at = <now>`
   ставится **каждым писателем, меняющим видимое клиенту состояние листинга, и никаким другим**:
   - **Двигают:** `create` (через DEFAULT на INSERT), `update` (черновая + материальная правка), `submit`
     (→ PENDING_MODERATION), одобрение/отклонение/запрос-изменений модерацией (status/moderation_status),
     снятие/деактивация, отметка-продано — т.е. рядом с каждым существующим `updated_at: new Date()` в
     сервисе ставить `content_updated_at` на **тот же** `Date` — **и** две функции каскадной деактивации
     в БД (`cascade_animal_deactivation` / `cascade_user_deactivation`, линия миграции 0025) добавляют
     `content_updated_at = now()` рядом со своими записями `status/is_active/updated_at`, чтобы изменение
     состояния из БД оставалось правдивым.
   - **НЕ двигают:** инкремент `view_count` в `captureView` (`:294`), запись `market` в
     `recomputeMarketForSpecies` D3 (`:789`), запись маркера SLA `escalated_at` (миграция 0024) и любая
     будущая системная/производная запись. Они намеренно опускают `content_updated_at` в своём `data:`,
     так что валидатор — и ETag — не сдвигаются.

4. **Счётчик остаётся на строке в MVP; внестрочный зарезервирован.** `view_count` остаётся колонкой
   `listings`, его best-effort дедуп-инкремент (миграция 0031) не меняется — **без регресса аналитики**.
   Оставшаяся запись строки на пути чтения (конкуренция за горячую строку + рычаг усиления записи)
   **принимается на объёме MVP** за существующим 30-минутным Redis-дедупом и является триггером для
   **Варианта C** (внестрочный счётчик через соседнюю `listing_stats` или Redis-авторитетный + тик-сброс),
   когда придут кэширование выдачи / реальный объём чтения. Поскольку A уже чинит базис ETag, а
   `view_count` читается через единый аксессор, этот перенос — внутренний рефакторинг, а не слом
   контракта — заменяющим ADR, когда он приземлится.

5. **ETag под-ресурса аналитики не меняется (намеренная граница).** ETag `getAnalytics`
   (`listing.service.ts:772`, `weakEtag(\`analytics:${id}\`, lastActivityAt ?? updated_at)`) **не**
   меняется: это отдельный read-only ресурс без мутирующего PATCH (нет `If-Match`), и его ETag *должен*
   отражать изменения просмотров/активности. Только первичный ETag листинга переходит на
   `content_updated_at`.

## Последствия

### Положительные
- Публичное чтение больше не меняет ETag листинга; PATCH продавца/оператора с `If-Match` больше ложно не
  412 — баг корректности «блокировка редактирования» и рычаг гриферства через флуд просмотров закрыты.
- Фикс **общий**: `escalated_at`, пересчёт `market` D3, `moderation_enqueued_at` и любая будущая
  производная запись тоже перестают ломать ETag, ведь валидатор двигают лишь настоящие изменения
  контента/состояния. Закрыт класс бага, а не один экземпляр.
- ETag становится семантически верным **валидатором контента**; оптимистичная блокировка по-прежнему
  работает для настоящих правок (реальное изменение контента двигает валидатор → устаревший `If-Match`
  корректно 412).
- Восстановлено условное GET-кэширование на горячем публичном чтении (ETag перестаёт мельтешить на
  трафике просмотров).
- `view_count` и его использование в аналитике не тронуты — без регресса единственного безвозвратного
  сигнала.
- Изменение небольшое и живёт в доменном слое; общий триггер `updated_at` остаётся общим.
- Чисто компонуется с зарезервированным внестрочным счётчиком (Вариант C) — A им не выбрасывается.

### Отрицательные
- Запись строки на пути чтения для `view_count` остаётся в MVP (конкуренция за горячую строку + рычаг
  усиления записи), принята за Redis-дедупом до масштабного слайса Варианта C; находка trash-линзы про
  конкуренцию сейчас снята лишь частично (половина «блокировки редактирования» починена полностью).
- Корректность теперь зависит от того, что сервис (и две каскадные функции БД) ставят `content_updated_at`
  на каждой записи контента/состояния; пропущенный писатель оставит валидатор устаревшим на реальном
  изменении. Это закреплено приёмочными тестами ниже.
- Небольшая миграция listings (одна колонка + защищённый бэкфилл); распространение EN↔RU + схема/ERD/
  data-model.

### Нейтральные
- `updated_at` сохраняет смысл (физический mtime строки) и продолжает двигаться на каждом UPDATE; ничто,
  что читает `updated_at` ради «когда строку трогали в последний раз», не меняется.
- Вопрос доверительной границы анонимного зрителя / `trust proxy` (AUDIT4 MINOR — вывод ключа дедупа
  просмотров) **вне области** здесь; он влияет на *точность подсчёта*, а не на базис ETag. Отложен на
  devops+security.

## Заметки по реализации (build-spec для backend-engineer)

- **Миграция** `migrations/20260708_0035_listings_content_version.sql` (следующий свободный номер; таблиц
  +0 → 37). Идемпотентный + N-1-безопасный бэкфилл одним защищённым блоком (бэкфилл срабатывает **только**
  при первом создании, так что повтор никогда не затрёт записанные приложением значения испорченным
  просмотрами `updated_at`):
  ```sql
  DO $$
  BEGIN
    IF NOT EXISTS (SELECT 1 FROM information_schema.columns
                   WHERE table_name = 'listings' AND column_name = 'content_updated_at') THEN
      ALTER TABLE listings ADD COLUMN content_updated_at TIMESTAMPTZ NOT NULL DEFAULT now();
      UPDATE listings SET content_updated_at = updated_at;   -- однократное историческое приближение
    END IF;
  END $$;
  ```
  Сохранить `DEFAULT now()` навсегда (N-1 совместимость записи). Прогнать на живом PG **дважды** (доказать
  идемпотентность).
- **Каскадные функции БД.** В `cascade_animal_deactivation` / `cascade_user_deactivation` (тела
  `CREATE OR REPLACE FUNCTION`, последний раз тронутые миграцией 0025) добавить `content_updated_at = now()`
  к операторам `UPDATE listings SET status='DEACTIVATED', is_active=false, updated_at=now()`
  (`database_schema.sql:1093,1106`). Поставить той же миграцией (CREATE OR REPLACE, идемпотентно).
- **Базис ETag.** `listing.service.ts`: добавить `content_updated_at: Date` в тип `ListingRow` и в select
  `findRow`; изменить `etag()` (`:1246`) на `weakEtag(\`listing:${row.id}\`, row.content_updated_at)`.
  ETag `getAnalytics` (`:772`) оставить как есть.
- **Писатели контента/состояния.** Рядом с каждым существующим `updated_at: new Date()` в мутации
  контента/состояния (`update` :343, `submit` :457, `withdraw/deactivate` :496, `markSold` :684 и записи
  одобрения/отклонения/запроса-изменений модерации в строку листинга) также ставить `content_updated_at`
  на **тот же** экземпляр `Date`. **Не** добавлять его в `captureView` (`:294`) и `recomputeMarketForSpecies`
  (`:789`), ни в путь записи `escalated_at`.
- **Распространение:** `database_schema.sql` + `ZooLink_ERD.mmd` + `docs/03-architecture/data-model.md` +
  заметка о числе таблиц/ledger в `ZooLink/CLAUDE.md` + `API_CONVENTIONS.md` §10 (отметить, что ETag
  листинга выводится из выделенной версии контента, а не `updated_at`) + зеркало EN↔RU (механическое RU-
  зеркало делегировать doc-keeper).

- **Приёмочные / негативные тесты (бэкенд обязан добавить):**
  1. **ОБЯЗАТЕЛЬНО — публичное чтение не ломает ETag / не 412 последующий PATCH.** GET ACTIVE-листинга →
     захватить ETag `E1`. Сделать несколько публичных GET от **разных зрителей/IP**, чтобы `captureView`
     инкрементировал `view_count` (проверить рост `view_count`). GET снова → проверить **ETag == E1**
     (не изменился). Затем PATCH контентного поля с `If-Match: E1` → **200** (НЕ 412). Это регресс-гейт
     всей находки.
  2. **Гриферство флудом просмотров нейтрализовано (trash-линза).** Смоделировать флуд анонимных
     просмотров на листинге, чей ETag удерживает продавец → последующий PATCH продавца с `If-Match`
     доФлудовым ETag **успешен** (нет 412 блокировки редактирования).
  3. **Настоящая правка контента всё ещё двигает + конкурентность работает.** GET → `E1`; PATCH title/
     price с `If-Match: E1` → 200, вернул `E2 ≠ E1`; второй PATCH с устаревшим `E1` → **412
     STALE_RESOURCE**.
  4. **Переходы состояния двигают валидатор.** submit / withdraw / mark-sold каждый меняют ETag (клиент,
     удерживающий доПереходный ETag, получает 412 на конфликтующем `If-Match`).
  5. **Системные записи НЕ двигают.** После инкремента `view_count` — и, где достижимо в тесте, установки
     `escalated_at` и `recomputeMarketForSpecies` — проверить, что `content_updated_at` (и ETag) не
     изменился.
  6. **Каскадная деактивация двигает.** Деактивация владельца/животного (каскадный путь) обновляет
     `content_updated_at` листинга (изменение состояния из БД остаётся правдивым).
  7. **Идемпотентность миграции + N-1 совместимость записи.** Прогнать 0035 дважды → без ошибки, без
     двойного дрейфа бэкфилла; INSERT листинга **без** `content_updated_at` (симуляция пода N-1) →
     успешно через DEFAULT.
  8. **Без регресса аналитики.** `getAnalytics.views` всё ещё отражает инкременты `view_count`.
