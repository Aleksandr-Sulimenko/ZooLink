# ADR-0036: Выдача учётных данных агенту — расстубливание `service_credentials` (учётные данные, выданные человеком → короткоживущий JWT AGENT)

**Статус**: Accepted — принят (владелец, 2026-07-09)
**Дата**: 2026-07-08
**Уточняет / развивает**: [ADR-0011](0011-agent-principal-actor-model.md) §5 (фиксирует конкретную форму предъявления, выдачи, bootstrap и верификации учётных данных, которую ADR-0011 §5.3 оставил *forward-compatible-заглушкой* — **не** переписывает и не supersede-ит его).
**Связано**: [ADR-0006](0006-ai-agents-operate-platform.md) (ИИ-агенты как принципалы; непреложное #4 = scoped, least-privilege учётные данные агента), [ADR-0009](0009-mvp-vs-target-architecture.md) (внутри монолита, без отдельного auth-сервиса), [ADR-0037](0037-agent-scoped-ability.md) (scope, который несёт выданный credential/JWT), RBAC-матрица `docs/specs/security/rbac-matrix.md`.
**Триггер аудита**: AUDIT4 §4a scorecard agent-runnability — *«agent-auth bootstrap — BLOCKED — выдача `service_credentials` = заглушка; единственный структурный блокер ЛЮБОЙ автономии»*; `AUDIT4/architect.md` anti-North-Star debt #1; `AUDIT4/security.md` §STRATEGIC (у bootstrap агента нет живого пути).

## Контекст и постановка проблемы

ADR-0011 §5 заложил **форму** agent-service-auth: source-agnostic принципал, разрешаемый упорядоченной цепочкой `RequestAuthenticator`, зарезервированный env-секрет подписи (`AGENT_SERVICE_SIGNING_SECRET`, ≥32) и ротируемое/отзываемое хранилище хешированных секретов — таблица `service_credentials` (миграция 0017, `database_schema.sql:1194`). Эта форма реальна и корректно спроектирована (`id`, `agent_user_id FK users ON DELETE RESTRICT`, `secret_hash`, `is_active`, `revoked_at`, `rotated_from`).

Но форма **инертна**. AUDIT4 (раунд-3) проверил разрыв по коду и назвал его единственным структурным блокером Северной звезды (ADR-0006 — операторские роли, выполняемые ИИ-агентами):

- `AgentServiceTokenAuthenticator.tryAuthenticate()` возвращает `null` на каждый запрос (умышленная заглушка — `backend/src/lib/auth/agent-service-token.authenticator.ts:23`).
- **Ни один эндпоинт не выдаёт учётные данные.** `service_credentials` никогда не заполняется; «подключено в никуда», как `s3.adapter`. Нет пути, чтобы машина получила, предъявила, ротировала или отозвала credential.
- Формы *записи актора* agent-as-principal (ADR-0011 §1–§4: снапшоты `principal_type`, human-override, деактивация-не-удаление) все на месте и простаивают впустую — **AGENT можно представить в журнале решений, но он не может аутентифицироваться**, поэтому ни один домен (moderation в остальном READY) реально не может управляться агентом.

Этот ADR фиксирует **конкретную форму выдачи**: *как* принципал-AGENT получает, предъявляет, ротирует и теряет учётные данные; **путь bootstrap** (кто выдаёт первый credential — разрешение «курица-и-яйцо»); подход к **хешированию/верификации** (повторно используя существующие crypto/auth-примитивы платформы); **аудит-след** (ADR-0006/0011); и **границу фазы** (что за форма отгружается сейчас vs поведение под гейтом позже). Строится **на** таблице 0017; единственная schema-дельта — небольшое аддитивное PROPOSED-расширение для подотчётности/операбельности (§7) — без переписывания.

Этот ADR решает *выдачу и аутентификацию*. **Что аутентифицированному агенту затем позволено делать** — least-privilege scope, deny-by-default, без `manage:all` — это парное решение [ADR-0037](0037-agent-scoped-ability.md) (AUDIT4 P1-6). Вместе они разблокируют Северную звезду; поодиночке ни одного недостаточно (агент иначе либо бессилен — нет creds — либо сверх-полномочен — наследует роль человека).

## Драйверы решения

1. **Разблокировка Северной звезды (ADR-0006)** — машина должна уметь аутентифицироваться прежде, чем любой операторский домен станет agent-run; это буквально первый шаг. Высший драйвер.
2. **Непреложное подотчётности (ADR-0006 #5)** — «ответственное физ/юрлицо всегда подотчётно». Корень доверия credential должен замыкаться на **ЧЕЛОВЕКЕ**, а выдача — быть аудируемым человеческим актом. Агент не является юрлицом (правовая заметка AUDIT4 §4a) — зарегистрированный человек-оператор несёт ответственность.
3. **Least-privilege / scoped credentials (ADR-0006 #4, ADR-0011 §5/§C)** — учётные данные должны быть ротируемыми, отзываемыми и никогда не в открытом виде на хранении; утёкший или сбойный credential должен мгновенно убиваться с ограниченным радиусом поражения.
4. **Переиспользовать-не-изобретать (фундамент платформы ADR-0001)** — путь верификации access-token (JWT с пином HS256, несущий `principal_type`), constant-time-сравнение, keyed-hash HMAC (`CryptoService`, миграция 0028), дисциплина ротации refresh и rate-limiting на Redis уже существуют. Форма выдачи должна ехать на них, а не добавлять параллельный примитив.
5. **Внутри монолита (ADR-0009, зафиксированный канон ADR-0011 §5)** — без отдельного auth-сервиса; выдача/верификация — забота principal/guard внутри монолита.
6. **Фазирование / cost-of-change (`IMPLEMENTATION_PLAYBOOK.md §5`)** — проектировать сейчас (дешевле всего до того, как Admin Slice 2 захардкодит human-only-допущения); отгрузить механику под гейтом (master-toggle off), в MVP не выдавать ничего.
7. **Комплаенс (ФЗ-152, ст.16 «решения исключительно автоматизированной обработкой»)** — регулятор должен реконструировать, какой человек авторизовал полномочия данного агента и когда; машина override (ADR-0011 §3) уже существует — этот ADR поставляет *выдачную* половину аудит-цепочки.

## §1 — Предъявление credential: секрет, выданный человеком, обменивается на короткоживущий JWT AGENT

**Рассмотренные варианты**

### Вариант 1: Долгоживущий opaque-секрет на каждом запросе (per-request проверка в БД)
Агент предъявляет свой сырой секрет `service_credentials` как bearer на каждом вызове; `AgentServiceTokenAuthenticator` ищет строку и constant-time-сравнивает `secret_hash` на каждый запрос.

Плюсы:
- Проще всего; форма цепочки аутентификаторов ADR-0011 §5 ложится 1:1 (аутентификатор возвращает принципала напрямую).

Минусы:
- **Долгоживущий высокоценный секрет идёт по проводу на каждом запросе** (горячий путь) — большая поверхность раскрытия (логи, прокси, replay при утечке), чем у короткоживущего токена.
- Поиск в БД + сравнение хеша **на каждом аутентифицированном запросе агента** (hot-row-чтение `service_credentials`); задержка отзыва per-request-хороша, но стоимость верификации повторяется бесконечно.
- Нет естественного истечения: утёкший секрет валиден, пока кто-то не заметит и не отзовёт.

### Вариант 2: Обмен credential → короткоживущий JWT AGENT (Выбран)
Агент предъявляет свой секрет **один раз** эндпоинту обмена (`POST /v1/auth/agent/token`); эндпоинт верифицирует его против `service_credentials`, затем выдаёт **короткоживущий access JWT** существующей формы (`AccessTokenClaims { sub, role, principal_type:'AGENT' }`, плюс scope-claim из ADR-0037). Далее агент использует этот JWT ровно как человеческий access-токен — верифицируемый уже построенным `BearerJwtAuthenticator` (пин HS256). Долгоживущий секрет появляется только на rate-limited-эндпоинте обмена.

Плюсы:
- **Переиспользует весь существующий путь access-token** — один downstream authz-путь, пин HS256, `principal_type` уже claim; добавление агентов = «заполнить claim», а не новая подсистема верификации.
- **Ограниченный радиус поражения**: артефакт на проводе на 99% запросов — короткоживущий JWT; отзыв credential мгновенно останавливает *новые* токены, а короткий TTL ограничивает окно выживания живого токена после отзыва (defense-in-depth) — та же причина, по которой у человека refresh↔access разделены.
- Долгоживущий секрет касается только одного rate-limited-эндпоинта (зеркалит изоляцию phone-OTP / refresh).
- Нет per-request hot-row-чтения `service_credentials`.

Минусы:
- Уже выданный JWT отозванного credential остаётся валидным до истечения (ограничено TTL) — смягчается коротким TTL + опциональным deny-list для экстренного убийства (ниже).
- Чуть больше движущихся частей, чем Вариант 1 (сервис обмена) — но это существующие части (token service, HMAC, rate-limit).

### Вариант 3: Подпись каждого запроса (в стиле HMAC-SigV4, без bearer-секрета на проводе)
Агент HMAC-подписывает каждый запрос своим секретом; сервер пересчитывает.

Плюсы:
- Самый сильный: нет переиспользуемого bearer-артефакта на проводе.

Минусы:
- **Кастомная схема**, не переиспользует JWT-путь — целая новая подсистема верификации и нагрузка на клиента; противоречит драйверу 4. Over-engineered для объёма агентов эпохи MVP. Отклонён.

**Решение:** **Вариант 2** — секрет, выданный человеком, обменивается на короткоживущий JWT AGENT. `AgentServiceTokenAuthenticator` **перепозиционируется** из «per-request звена цепочки» в «верификатор за эндпоинтом обмена» (развитие ADR-0011 §5, полностью совместимое: получившийся JWT AGENT течёт через source-agnostic `BearerJwtAuthenticator`, поэтому downstream authz остаётся single-path и agent-agnostic ровно так, как задумывал ADR-0011 §5). Прямой per-request-секрет-путь (Вариант 1) — зарезервированный fallback, не строится.

**ЧТО:** AGENT аутентифицируется, обменивая долгоживущий выданный человеком секрет `service_credentials` на короткоживущий access JWT AGENT в `POST /v1/auth/agent/token`; per-request-аутентификация — существующий bearer-JWT-путь.
**ПОЧЕМУ:** Машине нужен живой путь аутентификации; короткоживущий токен из одноразового обмена ограничивает раскрытие и переиспользует весь существующий верифицированный конвейер access-token вместо добавления параллельной per-request-проверки секрета.
**ПОЧЕМУ ТАК ЛУЧШЕ для проекта:** Максимально дешёвая forward-compat (реализация «один аутентификатор, а не переписывание подсистемы» ADR-0011 §5 как «один эндпоинт обмена, питающий существующий конвейер»); один downstream authz-путь (defense-in-depth без изменений, пин HS256 унаследован); least-privilege-радиус (короткий TTL + отзываемый credential) удовлетворяет ADR-0006 #4; держит долгоживущий секрет вне горячего пути (security). Отклонены: per-request-секрет (большее раскрытие на проводе + повторяющаяся hot-row-верификация); кастомная HMAC-подпись (новая подсистема, противоречит драйверу переиспользования).

## §2 — Bootstrap: первый credential выдаёт ЧЕЛОВЕК-ADMIN (без курицы-и-яйца)

Курица-и-яйцо («агенту нужен credential, чтобы действовать, но кто создаёт первый credential?») разрешается **закреплением корня доверия за человеком**, что также удовлетворяет непреложному подотчётности.

**Рассмотренные варианты**

### Вариант 1: Выдача человеком-админом (Выбран)
AGENT — это аккаунт (строка `users`, `principal_type='AGENT'`, ADR-0011 §4), **создаваемый человеком-ADMIN**, и его учётные данные выдаются **только** человеком-оператором через админ-эндпоинт `POST /v1/admin/agents/{agentUserId}/credentials`. Эндпоинт возвращает открытый секрет **один раз** (более не извлекается; хранится только `secret_hash`). Ни один агент не может создать агент-аккаунт или выдать какой-либо credential — выдача = human-only-возможность (обеспечено [ADR-0037](0037-agent-scoped-ability.md): выдача credential никогда не входит ни в один scope AGENT, даже admin-scoped).

Плюсы:
- **Без курицы-и-яйца**: корень доверия — существующий человек-админ, провижионится out-of-band ровно как первый человек-админ платформы (предсуществующая забота bootstrap, без изменений).
- Прямо удовлетворяет ADR-0006 #5 (человек/юрлицо — issuer-of-record и подотчётная сторона) и реконструируемости ст.16 ФЗ-152.
- Полномочия каждого credential прослеживаются до именованного человеческого акта в `audit_log`.

Минусы:
- Человек в контуре при онбординге/ротации агента (приемлемо — и правильно — для ближайших фаз автономии P-A…P-C).

### Вариант 2: Seed/env break-glass bootstrap-credential
Провижионить первый credential через миграцию/env при деплое.

Минусы:
- Риск открытого текста в конфиге/сиде; трудно чисто ротировать; **нет человека-actor-of-record** для существования credential. Отклонён (нарушает драйвер 2 + ADR-0011 §5.3 «никогда не в открытом виде»).

### Вариант 3: Само-регистрация агента / агент-выдаёт-агента
Агент чеканит свой или чужой первый credential.

Минусы:
- Именно тот анти-паттерн: неподотчётное, не-юрлицо чеканит собственные полномочия. Отклонён напрочь (противоречит ADR-0006 #5). Может ли *будущий* доверенный агент когда-либо выдавать peer-credentials (P-D) — вопрос владельца (§Открытые вопросы), по умолчанию **НЕТ**.

**Решение:** **Вариант 1.** Цепочка bootstrap: человек-ADMIN создаёт агент-аккаунт → человек-ADMIN выдаёт credential (аудируется) → агент обменивает его на JWT (§1) → агент может действовать **только** в рамках своего scope ADR-0037 **и** только там, где включён per-domain autonomy-toggle `agent_<domain>`. Выдача = human-only-возможность, навсегда в MVP/ближайшем сроке.

**ЧТО:** Первый (и каждый) credential агента выдаётся человеком-ADMIN через `POST /v1/admin/agents/{agentUserId}/credentials`, возвращая открытый секрет однократно; агенты никогда не могут выдавать credentials.
**ПОЧЕМУ:** Полномочия credential должны замыкаться на подотчётном человеке; само-bootstrap или seed-в-конфиге credential ломает подотчётность и реконструируемость.
**ПОЧЕМУ ТАК ЛУЧШЕ:** Разрешает курицу-и-яйцо переиспользованием предсуществующего корня доверия человек-админ (без новой поверхности bootstrap); делает полномочия каждого агента прослеживаемыми до именованного человеческого акта (ADR-0006 #5, ст.16 ФЗ-152); держит вопрос «полностью автономной выдачи» P-D явно под owner-гейтом, а не тихо включённым. Отклонены: env/seed-credential (открытый текст + нет человека-of-record); само-выдача агента (неподотчётная чеканка полномочий).

## §3 — Формат credential и хеширование/верификация (переиспользовать crypto платформы)

**Решение (нормативное):**
1. **Форма секрета.** Секрет credential — машинно-сгенерированное **256-битное** случайное значение, рендерится как префиксный, само-идентифицирующийся токен: `zlk_agent_<credId>_<secret>` (аналогично GitHub PAT `ghp_…`). Сегмент `credId` = `service_credentials.id`, поэтому верификация — **O(1) поиск по id** (не скан таблицы), а фиксированный префикс `zlk_agent_` позволяет secret-сканеру / leak-детектору распознать тип токена в логах и репозиториях.
2. **На хранении.** Хранить **только** `secret_hash = HMAC-SHA256(secret, AGENT_SERVICE_SIGNING_SECRET)` — переиспользуя env-секрет, уже зарезервированный ADR-0011 §5.2 (≥32, проверяется на boot), и keyed-hash-примитив HMAC, уже имеющийся в `CryptoService` (конструкция blind-index, миграция 0028). Никогда открытый текст (ADR-0011 §5.3).
3. **Верификация.** При обмене (§1): распарсить `credId` → загрузить строку (`is_active AND revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now())`) → **constant-time-сравнить** пересчитанный HMAC с хранимым `secret_hash`. Любой режим промаха (неизвестный id / неактивен / отозван / истёк / несовпадение) возвращает **один единообразный 401** (без existence/timing-оракула — та же дисциплина, что и единообразный-422 claim-code в transfer).
4. **Rate-limit.** Эндпоинт обмена rate-limited на Redis per-`credId` и per-IP (429 + Retry-After), зеркалит claim-mint transfer — душит brute-force и credential-stuffing.

Почему HMAC-с-зарезервированным-env-секретом, а не медленный password-hash (argon2/bcrypt): секрет сервиса — **полные 256 бит энтропии** (машинно-сгенерирован, не человеческий пароль), поэтому memory-hard KDF ничего не даёт против brute-force и лишь добавляет задержку обмену. Keyed-HMAC дополнительно означает, что украденная одна БД (без env-секрета) не может верифицировать ни один credential — свойство defense-in-depth, которого нет у обычного salted-хеша. (Отклонённая альтернатива: argon2id — уместна лишь для низкоэнтропийных человеческих секретов; здесь избыточная стоимость.)

**ЧТО:** Префиксный само-идентифицирующийся 256-битный секрет (`zlk_agent_<id>_<secret>`); на хранении только `HMAC-SHA256(secret, AGENT_SERVICE_SIGNING_SECRET)`; constant-time-верификация с одним единообразным 401 на любой сбой; rate-limited обмен.
**ПОЧЕМУ:** Машинному credential нужно O(1)-верифицируемое, без-оракула, leak-детектируемое предъявление без открытого текста на хранении, на примитивах, которым платформа уже доверяет.
**ПОЧЕМУ ТАК ЛУЧШЕ:** Переиспользует зарезервированный env-секрет + существующие HMAC/constant-time/rate-limit-примитивы (драйвер 4) — нет новой crypto для ревью; keyed-hash бьёт обычный хеш при краже только БД; id-префикс даёт O(1)-верификацию + leak-сканирование; единообразный-401 зеркалит устоявшийся no-oracle-паттерн кодовой базы. Отклонён: argon2id (неверный инструмент для полноэнтропийных машинных секретов).

## §4 — Ротация и отзыв (таблица 0017 уже поддерживает оба)

**Решение (нормативное):**
- **Ротация** = issue-new-then-revoke-old с коротким **окном перекрытия**: вставить новую строку с `rotated_from = <old id>`, отдать новый секрет агенту, затем отозвать старый (`is_active=false, revoked_at=now()`). Перекрытие даёт агенту сменить учётные данные без даунтайма. Ротация — человеческий админ-акт (§2).
- **Отзыв** = немедленный `is_active=false, revoked_at=now()`. Верификация (§3) отклоняет credential при самом следующем обмене. Уже выданные JWT (§1) выживают до TTL; для экстренного убийства (скомпрометированный агент) можно наслоить короткоживущий JWT-deny-list по `credId`/`jti` (переиспользовать паттерн отзыва refresh-family) — помечено как hardening на момент активации, не обязательное для формы MVP.
- **Деактивация агент-аккаунта** (ADR-0011 §4, `status='DEACTIVATED'`) ДОЛЖНА каскадно отзывать его живые учётные данные в той же транзакции (деактивированный агент не должен сохранять аутентифицирующий credential). FK `agent_user_id` = `ON DELETE RESTRICT` — учётные данные никогда не осиротеют.

**ЧТО:** Ротация = issue-new (`rotated_from`-связь) + revoke-old с перекрытием; отзыв = немедленный `is_active=false`; деактивация агента каскадно отзывает; экстренный JWT-deny-list зарезервирован.
**ПОЧЕМУ:** Least-privilege требует, чтобы credential был сменяемым без даунтайма и мгновенно убиваемым; деактивированный агент должен лишиться всех полномочий.
**ПОЧЕМУ ТАК ЛУЧШЕ:** Использует встроенные `rotated_from`/`is_active`/`revoked_at` таблицы (ноль изменений схемы для базового жизненного цикла); перекрытие устраняет режим «даунтайм-вынуждает-рискованный-шорткат»; каскад-деактивации закрывает дыру «отставной агент всё ещё аутентифицируется»; удовлетворяет ADR-0006 #4 + ADR-0011 §5.3 (ротируемый/отзываемый) ровно как обещала форма.

## §5 — Аудит-след (выдача — первоклассный, привязанный к человеку акт)

**Решение (нормативное):** Каждая выдача, ротация и отзыв пишут строку `audit_log` с `actor_id = <человек-админ>`, `actor_principal_type = 'HUMAN'` (ADR-0011 §1), снапшотом `actor_role`, entity = строка `service_credentials` (`entity_type='service_credential'`, `entity_id`). Открытый секрет **никогда** не логируется (только `credId`). Когда агент затем *действует*, эти действия снапшотят `actor_principal_type='AGENT'` по ADR-0011 §1–§3 — поэтому вся цепочка «человек X выдал credential C в T → агент A (аутентифицирован через C) решил D в T′ → человек Y переопределил D» реконструируема сквозь весь путь, удовлетворяя ст.16 ФЗ-152 и ADR-0006 #5.

**ЧТО:** Выдача/ротация/отзыв аудируются как HUMAN-акты над entity `service_credential`; секрет не логируется; действия агента остаются AGENT-снапшотнутыми (ADR-0011).
**ПОЧЕМУ:** Акт предоставления полномочий сам должен быть атрибутируем подотчётному человеку, замыкая аудит-цепочку от human-grant → agent-action → human-override.
**ПОЧЕМУ ТАК ЛУЧШЕ:** Достраивает аудит-хребет ADR-0011 (записывавший *действия*, но не *предоставления полномочий*); даёт регулятору «кто-что-когда-авторизовал» для решений исключительно автоматизированной обработки (ст.16); переиспользует существующий `audit_log` + actor-снапшот без нового механизма.

## §6 — Граница фазы: форма/механика строится сейчас, поведение под гейтом (в MVP не выдавать ничего)

По правилу cost-of-change (AUDIT4 §4c #4: дешевле всего до Admin Slice 2) **механика выдачи проектируется сейчас и реализуется как gated-slice**; **ни один AGENT не активен в MVP**.

- **Master-гейт.** Новый `feature_toggles.agent_service_auth` (по умолчанию **off**, засеян как `payments`/`ownership_transfer_verification`) гейтит эндпоинт обмена: при off `POST /v1/auth/agent/token` не выдаёт **никакого** JWT AGENT (403). Админ-эндпоинт выдачи МОЖЕТ создавать строки credential для пред-провижионинга, но они ничего не аутентифицируют, пока master-гейт off.
- **Per-domain autonomy-гейт (без изменений).** Что аутентифицированный агент может *делать*, остаётся дополнительно под существующими per-capability-toggle `agent_<domain>` (`agent_moderation` у moderation — эталон, `moderation.service.ts:289`) **и** под его scope ADR-0037. Три независимых предела: master-auth-гейт → scope (ADR-0037) → per-domain autonomy-toggle.
- **Истина MVP.** Master-гейт off, агент-аккаунт не провижионен, секрет не выдан, `service_credentials` пуста — побайтово-идентичное HUMAN-поведение. Slice отгружает тестируемую механику, а не живых агентов.

**ЧТО:** Строить выдачу/обмен/ротацию/отзыв сейчас за `feature_toggles.agent_service_auth` (по умолчанию off); per-domain `agent_<domain>`-toggle + scope ADR-0037 остаются downstream-пределами; MVP не выдаёт ничего.
**ПОЧЕМУ:** Механику дешевле всего заложить до затвердевания human-only-админ-допущений, но она не должна менять поведение MVP или обнажать непротестированную agent-auth-поверхность.
**ПОЧЕМУ ТАК ЛУЧШЕ:** Зеркалит проверенный на платформе паттерн form-now/behaviour-gated (payments-toggle, agent-toggle moderation, спящий junction миграции 0034) — тестируемо, обратимо, ноль изменений поведения MVP; три независимых гейта дают градуированную, убиваемую раскатку (auth → scope → per-domain autonomy), соответствующую поэтапному P-A…P-D ADR-0006.

## §7 — Предлагаемое расширение схемы (только PROPOSED-набросок — этот ADR миграцию не пишет)

Таблица 0017 уже несёт базовый жизненный цикл (`secret_hash`, `is_active`, `revoked_at`, `rotated_from`, FK RESTRICT). Следующие **аддитивные, nullable, идемпотентные** колонки нужны для подотчётности-of-record и операбельности. Backend-engineer реализует их в agent-auth-slice по `IMPLEMENTATION_PLAYBOOK.md §3` (правка `database_schema.sql` + новая идемпотентная миграция `migrations/YYYYMMDD_NNNN_*.sql` + `ZooLink_ERD.mmd` + `data-model.md` + счётчик таблиц в обоих `CLAUDE.md`; прогон дважды на живом PG; негативные тесты; `npm run db:sync`).

```sql
-- Подотчётный человек-issuer-of-record прямо на строке credential (ADR-0006 #5), не только через join к audit_log.
ALTER TABLE service_credentials
  ADD COLUMN IF NOT EXISTS issued_by UUID REFERENCES users(id) ON DELETE RESTRICT;
-- Операбельность: выявлять устаревшие/неиспользуемые credentials (defense-in-depth; best-effort, никогда на горячем пути).
ALTER TABLE service_credentials
  ADD COLUMN IF NOT EXISTS last_used_at TIMESTAMP WITH TIME ZONE;
-- Опциональное ограничение по времени: NULL = без истечения; задано = credential авто-истекает (верификация проверяет, §3).
ALTER TABLE service_credentials
  ADD COLUMN IF NOT EXISTS expires_at TIMESTAMP WITH TIME ZONE;
```

- `scope` (least-privilege-грант abilities, который обмен встраивает в JWT AGENT) **умышленно НЕ добавляется здесь** — им владеет [ADR-0037](0037-agent-scoped-ability.md), решающий, живёт ли scope на строке credential или в таблице именованных capability-профилей. Обмен §1 читает то, что определяет ADR-0037, и встраивает как JWT-claim.
- Все три колонки аддитивны/nullable → **N-1 rolling-deploy safe** (старые pod'ы, игнорирующие их, всё равно `INSERT`-ят нормально — учитывает AUDIT4 P1-5).
- Счётчик таблиц без изменений (только колонки, +0 таблиц). `expires_at`/`last_used_at` — рекомендуемая-но-опциональная defense-in-depth; `issued_by` обязателен для непреложного подотчётности.

## Последствия

### Положительные
- Единственный структурный auth-блокер Северной звезды снят: машина может получить, предъявить, ротировать и потерять учётные данные; каждый иначе-READY-домен (moderation) становится по-настоящему agent-operable, как только его per-domain-гейт + scope включены.
- Полномочия credential всегда прослеживаются до подотчётного человеческого акта (ADR-0006 #5, ст.16 ФЗ-152) — выдачная половина аудит-цепочки, начатой ADR-0011.
- Переиспользует всю существующую верифицированную механику access-token / HMAC / rate-limit / audit — минимум новой поверхности атаки, один authz-путь.
- Ограниченный радиус поражения (короткоживущий JWT + мгновенно-отзываемый credential + каскад-деактивации); градуированная раскатка на трёх гейтах.

### Отрицательные
- Уже выданный JWT отозванного credential выживает до TTL (ограничено; экстренный deny-list зарезервирован).
- Человек остаётся в контуре онбординга credential (верно для P-A…P-C; вопрос P-D «агент выдаёт агента» отложен, не решён).
- Одна небольшая аддитивная миграция (§7) сверх формы 0017.

### Нейтральные
- Поведение MVP без изменений: master-гейт off, `service_credentials` пуста, JWT AGENT не выдаётся — HUMAN-only, побайтово-идентично.
- Точный scope-claim JWT определяется ADR-0037; этот ADR фиксирует только выдачу и аутентификацию.
