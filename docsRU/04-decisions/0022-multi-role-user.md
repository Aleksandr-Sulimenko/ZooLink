# ADR-0022: Мультиролевой пользователь — junction `user_roles` + шов JIT self-claim (form-now)

**Status**: Accepted — 2026-07-05 (владелец ратифицировал «по рекомендациям»; OD-A и OD-B разрешены — см. §Owner decisions). Низкорисковый аддитивный шов; сохраняет `users.role` авторитетным в MVP. Supersedes прежний «Proposed — 2026-07-04 (ожидает кивок владельца)».
**Date**: 2026-07-04
**Relates to**: [ADR-0016](0016-provider-model.md) (тир верификации T0–T3 самопровозглашённой роли провайдера гейтит, что она может публиковать), [ADR-0006](0006-ai-agents-operate-platform.md)/[ADR-0011](0011-agent-principal-actor-model.md) (роль ортогональна `principal_type`), [ADR-0014](0014-offering-supertype-polymorphic-seam.md) (роле-гейтед offering-фичи множатся на этом шве), матрица RBAC `docs/specs/security/rbac-matrix.md`.
**Source vision**: `docsRU/01-discovery/future-features.md` §B (comfort-BR — один аккаунт = владелец + грумер + продавец + покупатель).

> **ЧТО** — Зарезервировать **junction** `user_roles(user_id, role)` как form-now шов для пользователя, держащего **несколько ролей одновременно**, сохраняя одиночную колонку `users.role CHECK IN (…7…)` как **primary/default-active** роль для authz в MVP. Зарезервировать шов **JIT self-claim**: пользователь может активировать дополнительную роль (напр. GROOMER, FARMER, продавец) без повторной регистрации.
>
> **ПОЧЕМУ** — Comfort-BR экосистемы требует, чтобы один аккаунт был владельцем питомца **и** грумером **и** продавцом товаров **и** покупателем. `users.role` сегодня одно-значный (`database_schema.sql:115`); как только роле-гейтед offering-фичи (ADR-0014/0016) размножатся, ретрофит мультироли означает бэкфилл junction'а из одной колонки и переписывание каждого authz-чтения разом — дешевле зарезервировать junction сейчас, пока он спит.
>
> **ПОЧЕМУ ТАК ЛУЧШЕ для всего проекта** — Аддитивно и обратимо: authz в MVP продолжает читать `users.role` без изменений (нулевое изменение поведения); junction спит, пока не появятся роле-гейтед фичи. Роль остаётся **ортогональной `principal_type`** (AGENT может держать операторские роли — ADR-0011). Self-claim чисто сцепляется с тирами верификации ADR-0016 (заявленная регулируемая роль publish-gated, пока её тир не достигнут), поэтому мультироль никогда не становится обходом доверия.

## Decision Drivers
1. Comfort-BR — один аккаунт, много ролей, без повторной регистрации.
2. Анти-rewrite (§5) — зарезервировать junction до того, как роле-гейтед фичи размножатся.
3. Ортогональность — роль ⟂ `principal_type` (ADR-0011); ⟂ `role_in_org` (членство в организации).
4. Сцепка с верификацией — самопровозглашённая регулируемая роль гейтится тиром ADR-0016, а не заявлением клиента.
5. Простота MVP — никакого переписывания authz сейчас; правит по-прежнему одна primary-роль.

## Considered Options
- **(1) Мигрировать `users.role` → массив `roles TEXT[]`.** Плюсы: одна колонка. Минусы: переписывает каждое authz-чтение разом; теряет чистую концепцию «primary/default-active»; array-CHECK'и неуклюжи; больший blast radius сейчас.
- **(2) Junction `user_roles(user_id, role)`, `users.role` остаётся primary (Выбрано).** Плюсы: аддитивно, спит, authz MVP не тронут; primary-роль чётко определена; self-claim и верификация цепляются к строкам junction'а. Минусы: два места записывают роль, пока authz не читает junction (задокументировано; junction спит до тех пор).
- **(3) Ничего не делать сейчас.** Минусы: тихий сброс comfort-BR; вынужденный одновременный ретрофит позже.

## Decision
Принимаем **Option 2**. Нормативные правила:
1. Зарезервировать `user_roles(user_id, role)` (словарь ролей = канон из 7 ролей), `UNIQUE(user_id, role)`; **спит** в MVP.
2. `users.role` остаётся **primary/default-active** ролью и единственным источником authz **до тех пор, пока** роле-гейтед фичи не начнут читать junction. Никакого изменения поведения MVP.
3. Пользователь может **self-claim** дополнительную роль (JIT); заявленная **регулируемая** роль **publish-gated** её тиром верификации ADR-0016 — сама заявка не даёт ничего регулируемого.
4. Роль **ортогональна** `principal_type` (ADR-0011) и `role_in_org`. Принципал AGENT может держать роли.
5. Это **резервирование**: junction + поведение self-claim строятся в слайсе, который первым выпускает роле-гейтед offering-фичу — не в MVP.

## Consequences
- **Positive:** comfort-BR зарезервирован; никакого переписывания authz сейчас; self-claim + верификация объединены с ADR-0016.
- **Negative:** два хранилища ролей сосуществуют, пока authz не читает junction (задокументировано; спит тем временем).
- **Neutral:** MVP без изменений; junction пуст/спит.

## Owner decisions (resolved 2026-07-05)
- **OD-A — разрешено 2026-07-05 (подтверждено):** junction-with-primary (Option 2), **не** массив `roles TEXT[]` (Option 1).
- **OD-B — разрешено 2026-07-05 (подтверждено):** пользователь может self-активировать **нерегулируемую** роль (покупатель/продавец/владелец) свободно; **регулируемые** роли publish-gated их тиром верификации ADR-0016 (сама заявка не даёт ничего регулируемого).
