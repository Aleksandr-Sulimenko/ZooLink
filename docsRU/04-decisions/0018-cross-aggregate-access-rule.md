# ADR-0018: Правило межагрегатного доступа — чтение животного через AnimalService (подтверждает ADR-0004)

**Status**: Accepted — 2026-07-04 (форма разрешена: брешь это 3 сайта, а не 1, и чинится в **двух упорядоченных частях** — см. §Decision / §Implementation Notes; низкий риск, подтверждает ADR-0004). Кивок владельца свёрнут в kickoff Wave-D (вынесен как пункт-подтверждение, не принят молча); **владелец явно подтвердил флип 2026-07-05**. Supersedes прежний «Proposed — ожидает кивок владельца (2026-07-01)».
**Date**: 2026-07-01 (accepted 2026-07-04)
**Amends**: [ADR-0004](0004-animal-as-aggregate.md) — **подтверждает и операционализирует его границу агрегата; НЕ supersedes.** Решение ADR-0004 стоит; этот ADR чинит код, отошедший от него, и делает границу обеспечиваемым, ревьюабельным правилом.
**Relates to**: [ADR-0014](0014-offering-supertype-polymorphic-seam.md) (это **предпосылка** — полиморфный шов должен стоять на чистых границах агрегатов), [ADR-0009](0009-mvp-vs-target-architecture.md).

> **ЧТО** — Делаем **нормативным архитектурным правилом**, что модуль НЕ ДОЛЖЕН читать или писать таблицы другого агрегата напрямую; он обращается к ним только через сервис, владеющий этим агрегатом. Конкретно: `ListingService` (и `ModerationService`) ДОЛЖНЫ получать данные животного и проверки владения через **публичный метод `AnimalService`**, а не через `prisma.animals.findUnique(...)` + дублированную проверку владения.
>
> **ПОЧЕМУ** — Аудит нашёл, что `listing.service.ts` читает таблицу `animals` напрямую (`loadAnimal`) и переписывает проверку владения (`assertOwnsAnimal`), обходя `AnimalService` — прямое нарушение собственной Implementation Note #2 ADR-0004 («ListingService валидирует владение животным **через** AnimalService»). Это двунаправленная кросс-агрегатная связанность (listing ↔ moderation ↔ animal через сырые чтения таблиц), названная «центральным структурным долгом». Адъюдикация conflict-of-opinion записала обе позиции как верные: backend («формы ещё нет») и architect («нарушение ADR-0004») — разрешение это решение architect'а.
>
> **ПОЧЕМУ ТАК ЛУЧШЕ для всего проекта** — ADR-0004 *верен*; код отошёл. По протоколу doc↔code конфликт code↔contract чинится **в сторону контракта**, а не переписыванием здравого решения под отошедший код. Маршрутизация через `AnimalService` (a) восстанавливает единственную реализацию проверки владения (аудит также нашёл `isOrgAdmin` дублированным в 4 сервисах — тот же класс долга), (b) держит animal-authz логику в одном месте, где agent-as-principal ADR-0006/0011 и будущие инварианты применяются единообразно, и (c) это **жёсткая предпосылка для ADR-0014**: полиморфный шов Offering нельзя строить поверх прямых межтабличных чтений, иначе каждый новый тип предложения наследует связанность. Это разблокирует Part B, погашая долг Part A.

## Context and Problem Statement

ADR-0004 сделал **Animal агрегатным корнем**; Listing ссылается на него и «валидирует владение животным **через** AnimalService» (ADR-0004 Implementation Note #2). Реализация разошлась:
- `backend/src/modules/listing/listing.service.ts` имеет приватный `loadAnimal(animalId)`, делающий `prisma.animals.findUnique(...)` напрямую, и приватный `assertOwnsAnimal(actor, animal)`, переписывающий проверку владелец/org-admin.
- `AnimalService` владеет авторитетной логикой владения (CASL-keyed на `owner_id`, org-admin через `isOrgAdmin`), но **не** экспонирует чистый кросс-модульный метод «загрузить summary животного + проверить владение» для вызова из `ListingService`/`ModerationService`.

Результат: логика владения дублирована, граница агрегата пориста, и треугольник listing↔moderation↔animal читает таблицы друг друга напрямую. Аудит ранжировал это как MAJOR структурный долг и **предпосылку для полиморфного шва ADR-0014** (вердикт Part B: «полиморфный шов не может стоять на текущей связке listing↔animal»).

Два способа разрешить (conflict #2 аудита оставил выбор architect'у):
- **(a)** Supersede ADR-0004 и *благословить* прямые межтабличные чтения как сознательное отклонение.
- **(b)** Подтвердить ADR-0004 и *маршрутизировать* весь доступ к животному через `AnimalService`.

## Decision Drivers

1. **ADR-0004 здрав** — Animal-as-aggregate соответствует доменной реальности и не под вопросом; отошёл только код.
2. **Протокол doc↔code** — чинить код в сторону контракта, не переписывать контракт под drift.
3. **Единый источник истины владения** — дублированный authz (здесь, и `isOrgAdmin` ×4) это класс дефекта, а не паттерн для благословения.
4. **Предпосылка ADR-0014** — полиморфному шву нужны чистые границы агрегатов; связанность распространилась бы на каждый тип предложения.
5. **Единообразие agent-as-principal** (ADR-0006/0011) — animal-authz должен применять agent/human-правила в одном месте.
6. **Модульный монолит (ADR-0009)** — in-process сервис-вызовы дёшевы; нет performance-причины обходить сервис.

## Considered Options

### Option (a): Supersede ADR-0004 — благословить прямые межтабличные чтения как сознательное отклонение
Заменить ADR-0004 решением, разрешающим модулям читать таблицы соседних агрегатов напрямую для read-mostly путей.

Pros:
- Соответствует коду как-написан-сегодня (нет рефакторинга).
- Маргинально меньше сервис-хопов на горячем read-пути.

Cons:
- Переписывает **верное** решение под отошедший код — инвертирует протокол doc↔code.
- Благословляет дублированную логику владения → риск authz-drift (ровно дублирование `isOrgAdmin`-×4 / `assertOwnsAnimal`, отмеченное аудитом); будущее изменение инварианта надо делать в N местах.
- Распространяет связанность в ADR-0014: каждый тип предложения читал бы таблицы animal/provider напрямую → полиморфный шов наследует долг.
- Подрывает границу агрегата, на централизованности которой держится agent-authz ADR-0006/0011.

### Option (b): Подтвердить ADR-0004 — маршрутизировать доступ к животному через публичный метод AnimalService (Выбрано)
Сохранить ADR-0004. Добавить публичный метод `AnimalService` (напр. `getOwnedAnimalForActor(actor, animalId)`, возвращающий минимальный summary + выполняющий проверку владелец/org-admin/agent, с 404-no-leak), который `ListingService` и `ModerationService` вызывают вместо прямого чтения `animals`. Удалить приватные `loadAnimal`/`assertOwnsAnimal` из `listing.service.ts`. Консолидировать дублированный `isOrgAdmin` в общий сервис org-membership.

Pros:
- Восстанавливает задуманную границу ADR-0004; одна реализация проверки владения.
- Agent/human authz, 404-no-leak и будущие инварианты животного применяются единообразно в одном месте.
- Удовлетворяет предпосылку ADR-0014 — шов стоит на чистых границах.
- Гасит долг класса дублированного authz.

Cons:
- Ограниченный рефакторинг сейчас (backend) — извлечь метод, перенаправить call-sites, держать тесты зелёными.
- Один лишний in-process сервис-хоп на пути listing-create/ownership (пренебрежимо в монолите).

## Decision

Принимаем **Option (b)**. ADR-0004 стоит. Нормативные правила:

1. **Ни один модуль не читает и не пишет таблицы другого агрегата напрямую.** Кросс-агрегатный доступ идёт через **публичный сервис-метод** владеющего агрегата.
2. **`AnimalService` экспонирует публичный ownership-aware accessor** — возвращает минимальный summary животного, нужный вызывающему, И выполняет проверку владелец / org-admin / agent-principal с **404-no-leak** (без existence-оракула). `ListingService` и `ModerationService` используют его; их приватные `loadAnimal` / `assertOwnsAnimal` удаляются.
3. **Логика владения/authz не дублируется.** `isOrgAdmin` (сейчас дублирован в ~4 сервисах) консолидируется в общий сервис org-membership; владение животным живёт только в `AnimalService`.
4. **Это предпосылка для ADR-0014.** Полиморфный шов Offering ДОЛЖЕН строиться на этих чистых границах; reviewer-qa обеспечивает «нет сырых межтабличных кросс-агрегатных чтений» как review-гейт.
5. **Поведение MVP без изменений** — те же проверки, те же результаты; меняется только *местоположение* логики. Никаких изменений контракта/схемы на single-row пути.

### Amendment 2026-07-04 — брешь это 3 сайта, а фикс — две упорядоченные части (разрешает циркулярность AUDIT3)

**ЧТО** — AUDIT3 подтвердил, что сырой кросс-агрегатный джойн `animals ⋈ species` живёт в **трёх** сайтах, а не одном: `listing.service.ts:627-628` (`marketOf`), `moderation.service.ts:577-578` (`marketOf`, **дословный дубликат**), и **базовый CTE очереди модерации** `moderation.service.ts:189-191` (`FROM listings l JOIN animals a JOIN species s`). CTE очереди — **пагинируемый list-запрос** и **не** декомпозируется в пер-строчные вызовы `AnimalService` без N+1. Поэтому этот ADR чинится в **двух упорядоченных частях**:

- **Part 1 — single-row (истинная предпосылка ADR-0014).** Две копии `marketOf` и каждое single-row чтение владения маршрутизируются через публичный accessor `AnimalService` (rule 2). Чистый code-рефакторинг, **без изменения схемы**, **без зависимости от ADR-0014**. Именно эта часть действительно *предшествует* 0014 (чистые границы до шва).
- **Part 2 — list-path (чинится через data-шов, НЕ пер-строчными вызовами).** List-джойны очереди/discovery убираются чтением **денормализованной производной колонки-кэша `market` на `listings`** (кэш `species.market`, вычисляемый in-tx на записи объявления, бэкфилл один раз, пересчёт на редком admin-исправлении вида). CTE очереди и обе копии `marketOf` затем читают `listings.market` с **нулём** кросс-агрегатных джойнов.

**ПОЧЕМУ ТАК ЛУЧШЕ / циркулярность разрешена** — AUDIT3 отметил, что «0018 — предпосылка для 0014» *частично циркулярно*, потому что чистый фикс list-джойнов — это discovery read-model из 0014. Это **не** циркулярно, когда разбито: Part 1 не нуждается ни в чём из 0014; Part 2 нуждается лишь в **минимальной производной колонке-кэше `market`**, которая является дешёвым автономным слайсом — и forward-совместима с — будущим read-model из 0014. Мы **не** строим полную материализованную discovery-проекцию сейчас (это Phase-2-heavy: projector, eventual consistency, ops-бремя); колонка-кэш поглотится в read-model позже. Кэш несёт **производный** `market` (`pet|livestock`), **не** назначенный тег `market_scope` — поэтому rule 7 ADR-0015 («ни одно объявление о животном не несёт `market_scope`») соблюдается: это *кэш деривации*, а не назначенное измерение.

6. **Денормализованная производная колонка-кэш `market` на `listings` — санкционированная форма** для устранения list-джойнов. Она по-прежнему «производна от species» по ADR-0004/0015 — просто кэширована, держится консистентной in-tx. Это НЕ назначенный тег `market_scope` (который живёт только на предложениях без вида, ADR-0015).
7. **Порядок нормативен:** Part 1 (accessor AnimalService) и колонка-кэш `market` обе приземляются **до** рефакторинга `marketOf`/очереди; рефакторинг GREEN только когда `grep -rnE "FROM +animals|JOIN +species|JOIN +animals"` по модулям `listing` **и** `moderation` возвращает ноль совпадений вне `AnimalService`.

## Consequences

### Positive
- Граница агрегата ADR-0004 реальна и обеспечена, а не аспирационна.
- Единая реализация проверки владения → agent/human authz и будущие инварианты меняются в одном месте.
- ADR-0014 разблокирован на чистых границах; связанность не распространена на новые типы предложений.
- Класс дефекта (дублированный authz) погашен.

### Negative
- Ограниченный backend-рефакторинг (извлечь + перенаправить + держать ~600 тестов зелёными); reviewer-qa проверяет паритет поведения.
- Один лишний in-process хоп (пренебрежимо в монолите).

### Neutral
- Никаких изменений API/схемы; чисто внутренняя структура + review-гейт.
- Текст ADR-0004 без изменений; этот ADR операционализирует его Implementation Note #2.

## Implementation Notes (backend — Wave D, секвенировано)
**Part 1 — single-row (Wave-D слайс D4, CODE-ONLY, без миграции):**
- Добавить `AnimalService.getOwnedAnimalForActor(actor, animalId)` (или эквивалент) — минимальный summary + проверка владелец/org-admin/agent + 404-no-leak.
- Удалить `listing.service.ts` `loadAnimal` / `assertOwnsAnimal`; перенаправить single-row `marketOf` в **обоих** `listing.service.ts:627` **и** `moderation.service.ts:577` (дословный дубликат).
- Консолидировать `isOrgAdmin`/`orgAdminIds` в общий сервис org-membership (единое определение).

**Part 2 — list-path (нужна сначала колонка-кэш `market`, Wave-D слайс D3 миграция, затем D8 CODE-ONLY):**
- Миграция (D3): `listings.market VARCHAR(9) CHECK (market IN ('pet','livestock'))`, вычисляется in-tx из `species.market` животного на create/update объявления, идемпотентный бэкфилл из существующего джойна, hook пересчёта на пути admin-исправления вида.
- Рефакторинг (D8): базовый CTE очереди модерации (`moderation.service.ts:189-191`) и обе копии `marketOf` читают `listings.market` — **убрать** джойны `animals ⋈ species`.
- **НЕ** маршрутизировать list-запросный джойн через пер-строчные вызовы `AnimalService` (N+1). List-путь чинится data-швом, single-row путь — сервис-accessor'ом.

**Обе части:** сохранить существующее поведение идентичным (паритет-тесты); reviewer-qa добавляет grep-гейт «нет сырого кросс-агрегатного чтения таблиц» по модулям `listing` **и** `moderation` (все 3 сайта). Полный материализованный discovery read-model из ADR-0014 здесь **не** строится; колонка-кэш `market` поглотится в него, когда выйдет первый подтип без вида.

> **Код реализует Part-2 — DONE (Wave D8, 2026-07-06, code-only, без миграции).** Все читатели рынка (listing / moderation / scheduler) теперь читают производный кэш `listings.market` (D3), ноль market-джойнов: (1) discovery-CTE объявлений — `l.market` (джойн `animals` добавляется только при наличии фильтра species_id/breed_id); (2) `listing.marketOf` — удалён, вызывающие читают `listing.market` из загруженной строки; (3) `moderation.marketOf` — удалён, читает `listing.market`; (4) базовый CTE очереди модерации — `l.market`; (5) скан SLA-эскалации (`lib/scheduler/moderation-escalation.service.ts`) — `l.market` (см. D8b ниже). **Grep-гейт активен**: `scripts/check-no-raw-market-join.sh` + блокирующий CI-job `market-decoupling` падают на любом сыром `FROM animals`/`JOIN species`. Единственное задокументированное исключение (inline-маркер `grep-allow-market-join`): CTE очереди сохраняет `JOIN species` ТОЛЬКО ради проекции `species.code` для отображения — сам рынок это `l.market`. Паритет доказан неизменными e2e discovery/market/queue (L2-1 market-no-leak жив) + негативный тест на устаревший кэш.
>
> **D8b (2026-07-07, code-only, без миграции) — 5-й читатель + расширенный гейт.** *WHAT:* скан SLA-эскалации (worker-only) всё ещё читал `s.market` через сырой джойн `animals ⋈ species`, чтобы выбрать порог pet-4h/livestock-6h и разметить событие `Moderation.Escalated`, и находился ВНЕ гейта D8 (который сканировал только `listing`/`moderation`). Теперь он читает `l.market`, а гейт сканирует **весь `backend/src`, кроме агрегата animal** (`modules/animal` = AnimalService + intra-агрегатный transfer-flow, санкционированный владелец animal↔species) плюс marker-строки. *WHY:* ревьюер нашёл читателя; читатель рынка вне гейта может тихо переввести кросс-агрегатную связку / market-leak-дрейф, которую ломает ADR-0018. *WHY-BETTER:* инвариант «каждый внешний читатель рынка читает кэш» теперь обеспечивается по всему репозиторию, а не только в двух модулях — будущие читатели (любой новый модуль/scheduler) ловятся CI. Паритет: идентичные пороги/теги (кэш == species.market по D3), доказано неизменным SLA-boundary e2e (pet 8h, livestock 12h) плюс новый drift-тест, показывающий, что порог + тег следуют за `l.market`, а не за species.
