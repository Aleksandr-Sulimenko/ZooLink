# ADR-0014: Супертип Offering — полиморфный шов discovery + moderation (анти-god-table)

**Status**: Accepted
**Date**: 2026-07-01
**Ratified by owner**: 2026-07-01 (Q1 — принято совместно с [ADR-0015](0015-market-scope-refines-0002.md))
**Relates to**: [ADR-0015](0015-market-scope-refines-0002.md) (принято совместно — см. Q1), [ADR-0002](0002-hard-split-markets.md), [ADR-0004](0004-animal-as-aggregate.md), [ADR-0018](0018-cross-aggregate-access-rule.md) (предпосылка), [ADR-0006](0006-ai-agents-operate-platform.md)/[ADR-0011](0011-agent-principal-actor-model.md) (snapshot актора при полиморфной модерации), [ADR-0016](0016-provider-model.md).
**Source vision**: `docsRU/01-discovery/future-features.md` §B (Ecosystem Expansion). Вход в MVP — только через формальный Change Request.

> **ЧТО** — Вводим *логический* супертип **Offering**, идентифицируемый полиморфной ссылкой `(offering_type, offering_id)`, который сквозные возможности **discovery / moderation / favorites / saved-search** потребляют **один раз, полиморфно**, для каждого вида предложения. Конкретные агрегаты-подтипы — `AnimalListing` (существует сегодня как `listings`), `ServiceOffering`, `ProductOffering`, `ConsultationOffering` — материализуются **только когда строится их сторона**. Никакого god-table, никакого EAV.
>
> **ПОЧЕМУ** — Апекс-BR владельца про «комфорт» («всё, что нужно питомцу, рядом, на всю его жизнь, в одном поиске / одном профиле / одном мессенджере») требует, чтобы *find-nearby*, *moderation*, *favorites* и *saved-search* охватывали животных **и** услуги **и** товары **и** консультации. Переписывать эти четыре сквозные возможности под каждый новый тип предложения значило бы (a) разъехаться в четыре стороны, (b) сломать единое обещание «найти рядом», (c) взорвать cost-of-change. Полиморфный шов — это **структурный носитель** этого BR.
>
> **ПОЧЕМУ ТАК ЛУЧШЕ для всего проекта** — Закладывает дешёвый-сейчас / дорогой-для-ретрофита шов (аудит Part-B нашёл его *объявленным, но отсутствующим* — backend + architect + frontend + janitor сошлись), не затягивая никакого поведения Фазы-2 в MVP. Он соблюдает ADR-0002 (разделение рынков *обеспечивается* швом через `market_scope`, ADR-0015), ADR-0004 (Animal остаётся собственным агрегатом; шов ссылается на него, а не поглощает), ADR-0006/0011 (полиморфные строки модерации по-прежнему несут snapshot актора), ФЗ-152 (object-level authz + 404-no-leak обязательны на каждом новом подтипе) и решение про модульный монолит (ADR-0009 — шов это in-process read-model + ссылка, а не новый сервис).

## Context and Problem Statement

Сегодня в системе есть ровно один пользовательский агрегат, который можно находить и модерировать: **объявление о животном `listing`** (ADR-0004). Vision про Ecosystem Expansion добавляет ещё три *вида* того, что пользователь находит и (часть — что) модерирует:

- **ServiceOffering** — провайдер без животного-субъекта и без жизненного цикла продажи (груминг, выгул, ветеринария, передержка, дрессировка). Явно **не** ещё один `listing_type` (vision настаивает на этом — у услуги нет животного и нет терминального SOLD).
- **ProductOffering** — продавец (не-Rx) товаров; расходники дают re-order / подписку.
- **ConsultationOffering** — подтип услуги, чей провайдер может быть `principal_type=AGENT` (ADR-0006).

Каждое из этих должно быть **находимым рядом**, **добавляемым в favorites**, **сохраняемым в saved-search** и (там, где несёт trust/safety-риск) **модерируемым** — ровно те возможности, что существуют сегодня, жёстко прибитые к единственной таблице `listings`. Аудит Part-B зафиксировал жёсткий структурный блокер: *«полиморфный шов не может стоять на текущей связке listing↔animal; швы form-now объявлены, но отсутствуют в схеме/контрактах».*

Нам нужно решить, **как сквозные возможности ссылаются на произвольное предложение** без того, чтобы (a) схлопнуть четыре bounded context'а в одну таблицу, (b) создать EAV attribute-bag, или (c) переписывать discovery/moderation/favorites N раз.

## Decision Drivers

1. **Апекс-BR про комфорт** — один поиск / один профиль по всем видам предложений (высший вес).
2. **Анти-god-table / анти-EAV** — пер-подтиповые инварианты и пер-контекстный ubiquitous language должны выжить; единая широкая nullable-таблица или key-value bag уничтожают оба (DDD).
3. **Cost-of-change / анти-rewrite (§5)** — *форма ссылки* в сквозных таблицах необратима-при-отсрочке (строки favorites/saved-search, записанные против не-полиморфного FK, нельзя честно отретрофитить); *таблицы подтипов* дёшево добавить позже.
4. **Разделение рынков по ADR-0002 должно обеспечиваться, а не размываться** (см. `market_scope` в ADR-0015).
5. **Целостность агрегата ADR-0004** — шов ссылается на агрегат Animal; он не должен снова поглощать его и (по ADR-0018) не должен стоять на прямых межтабличных чтениях.
6. **Object-level authz + 404-no-leak на каждом подтипе** — IDOR это риск №1 в кодовой базе; шов не должен стать enumeration-оракулом.
7. **Agent-as-principal** — модерация любого предложения всё равно снапшотит действующего принципала (ADR-0011).
8. **Модульный монолит (ADR-0009)** — никакого нового сервиса; шов это in-process ссылка + денормализованный read-model.

## Considered Options

### Option 1: Единая полиморфная god-table `offerings` (все типы в одной таблице, type-specific nullable-колонки / JSONB attribute-bag)
Одна строка `offerings` на сущность, с `type` плюс широким набором nullable-колонок (или JSONB `attributes`), покрывающим поля animal/service/product/consultation.

Pros:
- Тривиальный single-table discovery-запрос; одна FK-цель для favorites/saved-search/moderation.
- Нет полиморфной reference-бухгалтерии.

Cons:
- **Анти-паттерн EAV / god-table.** Пер-подтиповые инварианты (напр. «интактное животное для вязки», «у услуги есть часы работы», «у товара есть остаток») становятся непроверяемыми на уровне БД; валидация вырождается в app-side условия — ровно тот провал, который ADR-0002 отверг для опции единого маркетплейса.
- Схлопывает четыре bounded context'а в одну таблицу → ubiquitous language и фокус модерации размываются; разделение ADR-0002 подрывается.
- Широко-разреженная таблица: плохая плотность индексов, каждый потребитель читает ненужные колонки.
- Schema churn на каждом новом виде предложения задевает общую горячую таблицу.

### Option 2: Пер-подтиповые таблицы-агрегаты + тонкий полиморфный *шов* discovery/moderation (Выбрано)
Каждый вид предложения — **собственная** таблица-агрегат с **собственными** инвариантами (`listings` есть; `service_offerings`, `product_offerings`, `consultation_offerings` добавляются только когда строятся). Сквозные возможности ссылаются на предложение через **полиморфный ключ `(offering_type, offering_id)`**, несомый в:
- `favorites` и `saved_searches` (заменяют/расширяют сегодняшнюю listing-only ссылку),
- строках **moderation queue / decision** (полиморфный субъект + snapshot актора ADR-0011),
- **денормализованном discovery read-model** (проекционная таблица, питаемая outbox-событиями каждого подтипа), несущем поля, которые find-nearby реально нужны: `offering_type`, `offering_id`, `market_scope` (ADR-0015), `geo_anchor`, `title`, `price`/`monetization_type`, `status`, `provider_ref` (ADR-0016), `updated_at`.

Ссылочная целостность по полиморфному ключу — это **не** DB FK (Postgres не может FK на полиморфную колонку); она обеспечивается (a) in-app на записи и (b) тем, что read-model event-sourced из каждого подтипа (удалённый/soft-deleted подтип эмитит tombstone, чистящий проекцию). Object-level authz + 404-no-leak переутверждаются на **каждом** endpoint'е подтипа.

Pros:
- Каждый bounded context сохраняет свою таблицу, инварианты и ubiquitous language (DDD; усиливает ADR-0002).
- Discovery / moderation / favorites / saved-search строятся **один раз**, полиморфно — носитель BR про комфорт.
- Новый вид предложения = добавить одну таблицу-подтип + один projector; общий шов не трогается.
- Read-model заточен под find-nearby и плотен по индексам; write-side остаётся нормализованным.
- `market_scope` — first-class колонка на read-model → discovery может **обеспечивать** разделение в одном месте (ADR-0015).

Cons:
- У полиморфной ссылки нет DB FK → целостность это ответственность app + event-sourcing (смягчение: outbox уже есть; tombstone-on-delete это определённый инвариант).
- Read-model по природе eventual-consistency (смягчение: приемлемо для discovery; авторитетные чтения всё равно идут в подтип).
- Больше движущихся частей, чем у одной таблицы (намеренная цена за то, чтобы не схлопывать контексты).

### Option 3: Нет супертипа — каждый новый вид предложения переписывает discovery/moderation/favorites независимо
Выпустить ServiceOffering со своим find-nearby, своими favorites, своей модерацией и т.д.

Pros:
- Каждая вертикаль полностью автономна; нет общей абстракции, которую нужно проектировать заранее.

Cons:
- Переписывает носитель апекс-BR **4×** → гарантированный drift, 4× поддержки, нет единого «найти рядом / один поиск».
- Favorites/saved-search фрагментируются по типу → пользователь не может иметь один сохранённый поиск, охватывающий «грумер + корм рядом».
- Прямо противоречит §B vision'а «строить поиск и модерацию **один раз**, полиморфно».

## Decision

Принимаем **Option 2**. ZooLink моделирует **логический супертип Offering**, реализованный как **полиморфная ссылка `(offering_type, offering_id)`**, потребляемая четырьмя сквозными возможностями, над **пер-подтиповыми таблицами-агрегатами**. Нормативные правила:

1. **Нет god-table, нет EAV.** Нет физической таблицы `offerings`, держащей кросс-типовые атрибуты. Каждый подтип (`listings` сегодня; `service_offerings`, `product_offerings`, `consultation_offerings` позже) — собственный нормализованный агрегат со своими инвариантами. Таблицы подтипов создаются **только когда эта сторона реализуется** (form-now применяется к *шву*, а не к непостроенным подтипам).
2. **Форма полиморфной ссылки выпускается сейчас (form-now шов).** `favorites` и `saved_searches` несут `(offering_type, offering_id)` вместо listing-only FK; субъект модерации становится полиморфным; определяется таблица discovery **read-model**, несущая `offering_type, offering_id, market_scope, geo_anchor, monetization_type, status` + display-поля. *(Backend владеет конкретной миграцией; этот ADR фиксирует форму. Пока подтипов нет, `offering_type` ограничен значением `ANIMAL_LISTING`.)*
3. **`offering_type` — закрытый, аддитивный enum.** `ANIMAL_LISTING` (сейчас) → `SERVICE_OFFERING`, `PRODUCT_OFFERING`, `CONSULTATION_OFFERING` (каждый добавляется со своей стороной). Только аддитивно — никогда не переназначается.
4. **`market_scope` обеспечивается discovery** (ADR-0015) — read-model несёт его; discovery-запрос ОБЯЗАН фильтровать по нему; рынки никогда не смешиваются.
5. **`geo_anchor` — first-class** — точка сейчас, с зарезервированным местом под service-area позже. Find-nearby ключуется по нему. (PostGIS — поздний swap DB-образа, gated.)
6. **Object-level authorization + 404-no-leak на каждом подтипе** — не обсуждается (security; IDOR риск №1). Read-model никогда не отдаёт строку, чей подтип актору видеть нельзя.
7. **Полиморфная модерация несёт snapshot актора ADR-0011** — решение модерации по любому предложению записывает `actor_principal_type` / форму override ровно как сегодня.
8. **Шов НЕ должен стоять на текущей связке прямого чтения listing↔animal.** ADR-0018 (направлять кросс-агрегатные чтения через владеющий сервис) — **предпосылка**: полиморфный шов строится на чистых границах агрегатов, а не на долге связки Part-A.
9. **`monetization_type`** (`lead-gen | subscription | take-rate | none`) — form-now поле на стороне предложения, чтобы бизнес-модель могла переключаться без рефакторинга (vision finance §monetization).
10. **Read-model — проекция, никогда не система записи.** Авторитетные чтения/записи идут в агрегат-подтип; read-model перестраиваем из состояния подтипа + outbox.

## Consequences

### Positive
- Discovery, moderation, favorites, saved-search спроектированы один раз и обслуживают каждый текущий и будущий вид предложения — у BR про комфорт есть реальный структурный дом.
- Bounded context'ы и разделение ADR-0002 сохранены (каждый подтип — своя таблица; `market_scope` обеспечивается централизованно).
- Добавление вертикали — это «одна таблица-подтип + один projector», а не re-platforming.
- Дешёвый-сейчас шов закрывает блокер Part-B, не затягивая поведение Фазы-2 в MVP.

### Negative
- Полиморфная ссылка отказывается от DB-level FK → целостность это обязанность app + event-sourcing (инвариант tombstone + outbox уже есть).
- Discovery read-model добавляет eventual consistency и projector в эксплуатацию (devops/observability).

### Neutral
- Поведение MVP без изменений: существует только `ANIMAL_LISTING`; шов спит, пока не построен подтип.
- PostGIS остаётся поздним, gated swap'ом DB-образа; `geo_anchor` — обычная точка до тех пор.

## Amendment 2026-07-04 — тайминг form-now (разрешает противоречие rule-2 ↔ Implementation-Notes)

*Только уточнение — не меняет решение; дизамбигуирует два противоречивых предложения, отмеченных AUDIT3 (rule 2 «выпускается сейчас» vs Impl Notes «не сейчас»), из-за которых grep=0 был неадъюдицируем.*

**ЧТО / нормативное rule 11** — Разбить шов по необратимости и приземлить каждую часть в слайсе, где впервые пишется управляемая ею строка:

- **Form-now — приземляется в Wave D сейчас (необратимо-при-отсрочке):** **форма полиморфной ссылки** на строках, которые иначе нельзя отретрофитить — `favorites` и `saved_searches` несут `(offering_type, offering_id)` (Wave-D слайс **D2**, миграция), и **публичный контракт** выпускает `offeringType`/`offeringId` с первого дня (default/`CHECK` = `ANIMAL_LISTING`). Это **обязано** предшествовать контроллеру favorites (слайс **D11**): строка favorites или контракт, закоммиченные против listing-only `listingId` (`favorites-api.yaml:58`), нельзя честно отретрофитить, и это станет ломающим v1-изменением. Субъект value-события тоже становится `(offering_type, offering_id)` (слайс **D5**).
- **Отложить — рождается с подтипом (НЕ необратимо):** **таблицы подтипов** (`service_offerings`, …), **материализованная проекционная таблица discovery read-model**, переформованная полиморфная **очередь модерации**, и атрибуты стороны предложения **`monetization_type`** и **назначенный тег `market_scope`** — ни у одного из них нет физического дома, пока не появится предложение без вида, поэтому сейчас не пишется ничего, что позднее аддитивная миграция не сможет поставить. Реконсиляция `geo_anchor` двух near-me endpoint'ов — задача контракта/кода (слайс **D7**), PostGIS отложен.

**ПОЧЕМУ ТАК ЛУЧШЕ** — Разрешает неоднозначность, не затягивая никакого поведения Фазы-2 в MVP: только строки, накапливающиеся сейчас (favorites/saved_searches/events), получают полиморфную форму сейчас; всё, рождающееся с будущим подтипом, ждёт этот подтип. rule 2 стоит (*форма ссылки* выпускается сейчас); «не сейчас» из Implementation-Notes применяется к *таблицам подтипов и read-model*, а не к форме ссылки. Леджер **решений** модерации уже `(entity_type, entity_id)`-формы; реконсилируется только словарь enum (`LISTING` vs `ANIMAL_LISTING`), когда очередь делается полиморфной (с подтипом).

**Owner ratification 2026-07-05** — split form-now (rule 11) подтверждён «по рекомендациям». **`monetization_type` зарезервирован SPEC-ONLY**: резервируется только форма поля (`lead-gen | subscription | take-rate | none`) на контракте предложения; **модель** монетизации отложена до явного обсуждения с владельцем (win-win, soft-start) и **не** строится сейчас. Это уточняет rule 9 и bullet «Отложить» выше.

## Implementation Notes (для backend / alpha-analyst, когда сторона строится — не сейчас)
- Form-now миграция (отдельная задача, backend): полиморфные `(offering_type, offering_id)` на `favorites` + `saved_searches`; полиморфный субъект модерации; таблица discovery read-model + enum `offering_type` (только `ANIMAL_LISTING`); колонки `monetization_type` + `geo_anchor` на стороне предложения. Каждое за правилом «форма сейчас, поведение gated».
- alpha-analyst пишет **контракт** полиморфных discovery + moderation (object-level authz, 404-no-leak, фильтр `market_scope`, envelope read-model) до любого кода подтипа.
- Пер-подтиповые инварианты живут в спеке подтипа, никогда в шве.
