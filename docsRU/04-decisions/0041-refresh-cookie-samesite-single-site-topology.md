# ADR-0041: `SameSite=Strict` у refresh-куки привязывает ZooLink к одно-сайтовой краевой топологии (кросс-сайтовый SPA потребует пересмотра)

**Статус**: Accepted (через владельческий гейт деплой-пака F1; сейчас держим Strict — не ослаблять преждевременно)
**Дата**: 2026-08-06
**Опирается на**: [ADR-0009](0009-mvp-vs-target-architecture.md) (единый публичный край — Caddy отдаёт SPA и API с одного origin, поэтому сессия same-site по построению), [ADR-0019](0019-pii-at-rest-form-enforcement.md) (refresh-кука — это HttpOnly-транспорт, удерживающий долгоживущий креденшл вне JS страницы).
**Связано**: AUDIT5 `frontend-engineer.md` §3 Б-2/Б-3 и §7.2 (находка, вскрывшая эту связку); пак базового пути F1a (`config/api-base.ts` — единый источник; `Path` куки выводится из публичной базы `/api/v1`, поэтому теперь совпадает с путём браузера; `refresh-cookie.ts`).

---

## Контекст и постановка проблемы

Транспорт refresh-токена — кука `HttpOnly; Secure; SameSite=Strict` с областью `Path=/api/v1/auth`
(`backend/src/modules/auth/refresh-cookie.ts`). Атрибут `SameSite=Strict` означает, что браузер прикрепляет
куку **только к same-site запросам** — запросам, чей верхнеуровневый сайт (регистрируемый домен / eTLD+1)
совпадает с сайтом куки. Это сильнейшая CSRF-позиция, доступная куке: кросс-сайтовая страница не может
заставить refresh-куку «поехать» с запросом.

При [ADR-0009](0009-mvp-vs-target-architecture.md) это ровно правильно и бесплатно: **один** Caddy отдаёт и
сборку SPA (`/srv/www`), и API (`/api/*`) с **одного origin**, поэтому любой запрос SPA к
`/api/v1/auth/refresh` — same-origin → same-site → кука едет, с максимальной CSRF-стойкостью и без CORS.

Проблема в том, что эта корректность **держится на топологии и нигде не записана**. `Strict` **молча
закрепляет** ZooLink за одно-сайтовым развёртыванием фронта. Выбор живёт в одной константе; будущее решение
разместить SPA в другом месте столкнётся с ним так, что это невидимо до отказа браузера в продакшене (тот же
класс дыры, что породил разъезд базового пути C1 — правда, жившая только в коде). Этот ADR делает связку явной
и фиксирует позицию, чтобы размен был решением, а не случайностью.

Где именно связка кусается (SameSite — про *сайт*, а не про *origin*; различие важно):

- **Same-origin (ADR-0009 сегодня):** SPA и API на идентичном origin. `Strict` шлёт куку. ✅ Без CORS.
- **Same-site, кросс-origin разбиение по поддоменам** (напр. `app.zoolink.ru` зовёт `api.zoolink.ru` — тот же
  регистрируемый домен `zoolink.ru`): всё ещё **same-site**, поэтому `Strict` **по-прежнему шлёт** куку на
  кросс-origin `fetch`. Что этому разбиению *нужно* — это allowlist **CORS** (точный origin +
  `credentials: true`), и он уже засеян (`CORS_ORIGINS` env + `enableCors` в `main.ts`). Менять SameSite не
  требуется. ⚠ Только CORS.
- **Кросс-сайтовый SPA** (другой регистрируемый домен, либо кросс-сайтовый статик-хост / CDN — напр. SPA на
  `zoolink.app` или домене стороннего CDN, зовущий `zoolink.ru`): теперь **кросс-сайт**, и `SameSite=Strict`
  **блокирует** refresh-куку на этом запросе. Сессию нельзя обновить → тихий разлогин. Именно эту топологию
  `Strict` запрещает. 🚫

## Драйверы решения

1. **CSRF-стойкость — это пол безопасности, а не удобство (security_specification.md).** `Strict` — сильнейшая
   same-site позиция; ослабление (`Lax`/`None`) разменивает CSRF-защиту и должно быть *заработано* конкретной
   топологической нуждой, а не сделано загодя «чтобы оставить опции».
2. **ADR-0009 — принятая топология, и она same-origin.** Сегодня цена `Strict` — ноль: сессия same-site по
   построению. Оптимизируем под решённую реальность, а не под гипотезу.
3. **Делать скрытые связки явными (урок C1).** Корректность, зависящая от топологии и живущая только в атрибуте
   куки, — вторая правда, ждущая разъезда. Записать её.
4. **Дешевле всего осмыслить до открытия фронт-фазы.** SPA ещё не существует; назвать ограничение сейчас — абзац,
   обнаружить позже — потерянный продакшен-день (frontend-engineer Б-2).

## Рассмотренные опции

### Опция 1: Держать `SameSite=Strict`; зафиксировать одно-сайтовую связку; пересматривать только при кросс-сайтовом SPA
Оставить текущий атрибут. Задокументировать, что `Strict` предполагает одно-сайтовый (тот же регистрируемый
домен) фронт, что гарантирует ADR-0009. Любой переезд на кросс-сайтовый хост SPA переоткрывает этот ADR.

Плюсы:
- Максимальная CSRF-стойкость, соответствующая принятому same-origin краю (ADR-0009).
- Ноль изменений поведения; нечего строить; никакой новой поверхности атаки.
- Связка теперь записана — будущий переезд не сломает сессии молча.

Минусы:
- Будущий кросс-сайтовый фронт — **заблокированный** путь до пересмотра этого ADR (по замыслу — в этом и суть).

### Опция 2: Загодя ослабить до `SameSite=Lax` (или `None; Secure`) сейчас, чтобы держать опции хостинга открытыми
Ослабить атрибут сегодня, чтобы будущий кросс-сайтовый SPA «просто заработал».

Плюсы:
- Позднему кросс-сайтовому переезду не понадобится менять куку.

Минусы:
- **Разменивает CSRF-защиту без текущего бенефициара** — SPA не существует, а ADR-0009 same-origin.
- `None` вдобавок *требует* кросс-сайтовой семантики доставки и более широкой экспозиции; `Lax` всё равно не
  понесёт куку на кросс-сайтовых *sub-resource* запросах (тот `fetch`, которым идёт refresh) — то есть даже не
  решит кросс-сайтовый случай чисто: ослабит безопасность **и** не починит гипотезу до конца.
- Нарушает «заработай ослабление» (драйвер 1) и fail-safe defaults.

## Решение

**Берём Опцию 1.** Держим refresh-куку на `HttpOnly; Secure; SameSite=Strict`. Фиксируем здесь, что этот
атрибут **привязывает фронт к одно-сайтовой (тот же регистрируемый домен) топологии**, которую даёт
[ADR-0009](0009-mvp-vs-target-architecture.md). **Не ослаблять преждевременно.**

Перед размещением SPA на любом **кросс-сайтовом** origin (другой регистрируемый домен, либо кросс-сайтовый
статик/CDN-хост) этот ADR **обязан быть пересмотрен** — пересмотр ослабит `SameSite` до `Lax` или
`None; Secure` **и** добавит компенсирующую CSRF-защиту (напр. double-submit / origin-проверяемый CSRF-токен на
маршруте refresh), потому что ослабление SameSite убирает структурный CSRF-страж, на котором кука держится
сегодня. **Разбиение по same-site поддоменам** этот ADR **не** трогает — ему нужен лишь уже засеянный allowlist
`CORS_ORIGINS`.

## Последствия

### Положительные
- Сессия сохраняет сильнейшую CSRF-позицию для принятой (same-origin) топологии, бесплатно.
- Топологическая связка явна: следующее решение о хостинге фронта обязано свериться с этим ADR, а не обнаружить
  ограничение через продакшен-отказ сессии.
- Чисто стыкуется с фиксом базового пути F1a: `Path` куки теперь выводится из единого источника публичной базы
  (`config/api-base.ts` → `/api/v1/auth`), поэтому set и clear совпадают с публичным путём браузера.

### Отрицательные / принятые ограничения
- Кросс-сайтовый фронт — гейт-путь (нужно переоткрыть этот ADR + добавить CSRF-защиту). Так и задумано — гейт
  существует, чтобы размен безопасности был осознанным.
- Различие «same-site поддомен (только CORS) vs кросс-сайт (ещё и SameSite)» обязано соблюдаться при выборе
  топологии фронта; оно задокументировано выше, чтобы не сработал слишком широкий рефлекс «ослабить куку».

### Нейтральные
- Этот ADR не требует изменений кода или схемы; он фиксирует позицию вокруг существующего атрибута.
