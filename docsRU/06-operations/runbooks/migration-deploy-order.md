# Runbook — порядок миграций и деплоя (безопасность N-1 при rolling-deploy)

> **Статус:** Active (AUDIT4 P1-5). **Область:** порядок применения миграции схемы и релиза кода так,
> чтобы **под предыдущей версии (N-1), продолжающий обслуживать трафик пока новая схема уже применена**,
> не ломался. Ответственные: devops + backend-engineer. EN-оригинал:
> [`docs/06-operations/runbooks/migration-deploy-order.md`](../../../docs/06-operations/runbooks/migration-deploy-order.md).

## WHAT (что)
Единое авторитетное правило: **когда** миграцию можно применять «на живую» (пока приложение обслуживает)
против **stop-the-world** (приложение остановлено, либо двухфазный expand→contract), плюс классификация
N-1-безопасности каждой миграции и ожидание CI, которое это охраняет. Миграции лежат в
`ZooLink/migrations/` и **никогда** не выполняются Prisma Migrate (ADR-0007) — сегодня прод применяет
`database_schema.sql` при provision, поэтому этот runbook вступает в силу в момент перехода прода на
**migrate-in-place-while-serving**.

## WHY (почему)
Идемпотентность (повтор×2 на актуальной схеме) уже доказана в CI и чиста. **Непроверенная ось — N-1**:
при rolling-deploy есть окно, где новая схема применена, но старые поды ещё выполняют старый код. Три
уже поставленные миграции ломают это окно (AUDIT4 devops/reviewer-qa/architect, ⇊сошлись):

- **0033** `listings.market VARCHAR(9) NOT NULL` (без DEFAULT) — старый под, вставляя листинг без `market`
  → `нарушение NOT NULL (23502) → 500` на **каждом** создании.
- **0028** `users.email` → AES-`enc:v1:` шифртекст + `email_bidx` (backfill шифрует существующие строки) —
  старый код делает `WHERE email = $plaintext` → не находит **ни одного** пользователя → логин/восстановление
  ломаются в окне.
- **0029** `UNIQUE(viewer_id, listing_id)` на `contact_reveals` — повторный reveal старого кода, ранее
  допустимый, → `23505 → 500` на этом одном эндпоинте (деградирует один путь, не ядро).

При сегодняшнем `docker compose` **stop-the-world recreate** (provision применяет схему, затем api/worker
стартуют с нуля) окна N-1 не существует, поэтому это латентно. Оно становится **инцидентом данных/аутентификации**
при первой же миграции «на живую». Дёшево предотвратить сейчас, дорого обнаружить потом.

## WHY-BETTER (почему так лучше для всего проекта)
- **Expand → migrate → contract** — индустриальный стандарт zero-downtime; закрепив его как правило дома,
  каждую будущую миграцию пишут против известного контракта, а не импровизируют при деплое.
- Делает явным случай **производного значения**: `listings.market` ВЫВОДИТСЯ из вида (species) животного
  (ADR-0002), поэтому **корректного нейтрального default нет** — произвольный `DEFAULT 'pet'` молча пометил
  бы livestock-листинги, созданные подами N-1, и **нарушил бы разделение рынков** (хуже, чем чистый 500).
  Поэтому исправление 0033 намеренно **порядковое, не DDL** (в отличие от 0031 `view_count DEFAULT 0` /
  0035 `content_updated_at DEFAULT now()`, где нейтральный default КОРРЕКТЕН и используется для N-1
  write-compat).
- Даёт слою ИИ-операторных операций (ADR-0006) детерминированный, машинопроверяемый пред-деплой-гейт.

## Правило — expand · migrate · deploy · contract

1. **Expand (сначала обратно-совместимая схема).** Колонки добавлять **nullable или с корректным
   нейтральным DEFAULT**; новые таблицы/индексы; расширять типы. Никогда не добавлять `NOT NULL`-без-default,
   не удалять/переименовывать колонку, не сужать тип, не добавлять UNIQUE, который старые записи нарушают,
   — пока старый код работает.
2. **Migrate (применить expand-миграцию на живую).** Безопасно, старый код не затронут.
3. **Deploy (выкатить новый код).** Новый код пишет новые колонки / использует новые поиски.
4. **Contract (только после исчезновения всех старых подов).** В *следующем* релизе: `SET NOT NULL`,
   снять временный DEFAULT, удалить старые колонки, добавить ужесточающий UNIQUE. Никогда в одном релизе
   с expand.

Если миграцию нельзя сделать expand-безопасной (корректный нейтральный default невозможен, напр.
**производное** значение) — она **stop-the-world**: остановить приложение (или свести старые поды к нулю)
*перед* её применением.

## Классификация N-1 по миграциям (авторитетная)

| Миграция | Вердикт N-1 | Обработка деплоя |
|---|---|---|
| **0033** `listings.market NOT NULL` (производное, нет корректного default) | **UNSAFE** | **Stop-the-world** — остановить приложение до миграции (`DEFAULT` нарушит разделение рынков ADR-0002, DDL это не чинит; корректное значение есть только в новом коде). |
| **0028** email→шифртекст + bidx | **UNSAFE** | **Stop-the-world**, либо окно **dual-read expand** (держать путь plaintext-поиска живым, пока все старые поды не сольются) перед contract. |
| **0029** `contact_reveals UNIQUE(viewer,listing)` | **friction (MINOR)** | Деградирует один эндпоинт; краткое окно допустимо, либо stop-the-world вместе с остальными. |
| 0031 `view_count NOT NULL DEFAULT 0` | **SAFE** | На живую — старые INSERT проходят через default. |
| 0035 `content_updated_at NOT NULL DEFAULT now()` | **SAFE** | На живую — `DEFAULT now()` корректный нейтральный default, сохранён навсегда для N-1 write-compat. |
| 0036 `consents.seq GENERATED ALWAYS AS IDENTITY` | **SAFE** | На живую — назначается БД, никогда не пишется приложением; старые INSERT его опускают и проходят. |
| 0034 `user_roles` junction (dormant) + backfill | **SAFE** | На живую — аддитивная таблица, код её не читает. |
| 0023 триггер ownership-transfer → GUC-gated | **SAFE** | На живую — старый код не ставит GUC → прежнее поведение сохранено. |
| 0016 / 0026 сверка CHECK principal_type | **SAFE** | На живую — только имя ограничения, значения без изменений. |

**Классификация по умолчанию для НОВОЙ миграции:** SAFE только если она чисто аддитивна с корректным
нейтральным default (или новая таблица/индекс, которых старый код не касается). Всё с `SET NOT NULL`,
backfill-then-constrain, сужением типа, drop/rename или ужесточающим UNIQUE — **UNSAFE → stop-the-world**,
если не написано как двухрелизный expand→contract.

## Ожидание CI
- **Есть сегодня (блокирующее):** джоб `migration-drift` повторяет каждую миграцию **дважды на актуальной
  схеме** и делает DDL-diff → доказывает *идемпотентность* + *сходимость схемы*. Работает на **пустых
  таблицах**, поэтому **не** доказывает корректность backfill и путь апгрейда N-1.
- **Требуется (рекомендовано, AUDIT4 P1-5/B1 — devops + reviewer-qa):** добавить джоб `migration-upgrade`
  (он же `migration-replay-with-data`): provision схемы **на N-1**, засеять представительные строки
  (листинги без `market`, пользователи с plaintext email, дубли `contact_reveals`), применить **только
  новейшую миграцию** и проверить (a) успех, (b) каждая backfill-колонка не-NULL **и корректна**,
  (c) повтор — no-op. Это истинный тест N-1; самый дешёвый-сейчас / дорогой-потом страж.

## Чек-лист оператора (перед применением миграции в проде)
1. Прочитать классификацию N-1 новой миграции (добавлять строку `-- N-1:` в шапку миграции, как 0035/0036).
2. **SAFE** → применить на живую, затем выкатить код.
3. **UNSAFE** → сначала объявить окно обслуживания / свести старые поды к нулю, применить, затем выкатить
   код (или выполнить двухрелизный expand→contract, если простой недопустим).
4. Никогда не применять UNSAFE-миграцию, пока старые поды обслуживают. Никогда не добавлять произвольный
   DEFAULT к **производной** колонке «чтобы сделать её безопасной» — это меняет чистый 500 на молчаливое
   повреждение данных.
