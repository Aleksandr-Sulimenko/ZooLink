# Спецификация: Сервис гео-поиска

## Результат
Обеспечить эффективные возможности гео-поиска для поиска животных и объявлений в указанном радиусе (1-100 км) от местоположения пользователя. Поддерживать точные расчеты расстояния и фильтрацию, чтобы обеспечить поиск на основе местоположения во всех доменах рынка (Домашние животные, Скот, Подбор).

> ⚠️ **Решение MVP (зафиксировано):** в MVP используются колонки `lat`/`lng` + **формула Haversine с предфильтром bounding box** (без расширений), по [ADR-0009](../04-decisions/0009-mvp-vs-target-architecture.md) и `storage.md`. **PostGIS** (и альтернатива `earthdistance`/`ll_to_earth`) — **Фаза 2+**, а не открытый вопрос MVP. Упоминания PostGIS ниже — это Target-вариант.

## Область и границы
**Включает:**
- Расчет расстояния с использованием формулы Хаверсин или расширения PostGIS
- Поиск по радиусу: найти все точки в пределах X километров от заданной широты/долготы
- Интеграция с сущностями Объявлений (Рынок домашних животных, Рынок скота)
- Интеграция с сущностями Животных (для домена Подбора)
- Поддержка как точного соответствия местоположения, так и поиска по радиусу
- Возможность комбинировать гео-поиск с другими фильтрами (вид, порода, цена и т.д.)
- Оптимизация производительности для больших наборов данных (100k+ записей)
- Конфигурация ограничений радиуса поиска (мин 1км, макс 100км согласно требованиям)

**Исключает:**
- Маршруты/направления - отложено
- Автозаполнение мест/геокодинговое обслуживание (обрабатывается внешним API Карт)
- Сложные поиски по полигонам (например, поиск внутри границ города) - отложено
- Отслеживание местоположения в реальном времени - отложено
- Офлайн карты/кэширование - отложено

## Ограничения
- **Юридическое:** Должен использоваться соответствующий геокодинговый сервис (API Яндекс.Карт для MVP согласно решению о стеке технологий).
- **Точность:** Расчеты расстояния должны быть достаточно точными для доверия пользователей (ошибка в пределах 100м допустима).
- **Производительность:** Запросы гео-поиска должны выполняться за <1s для 95% запросов при ожидаемой нагрузке.
- **Масштабируемость:** Должен эффективно обрабатывать 100k+ записей с геотегами.
- **Технологии:** Использовать PostgreSQL с расширением PostGIS или реализовать эффективную формулу Хаверсин в SQL.
- **Удобство использования:** Радиус поиска должен быть регулируемым через UI (ползунок/ввод) с четкими единицами расстояния (км).
- **Данные:** Данные о местоположении должны храниться как координаты широты/долготы (WGS84).

## Предыдущие решения
- Хранить местоположение как отдельные столбцы с плавающей точкой широты и долготы в таблицах Объявления и опционально Животных.
- **MVP (зафиксировано):** PostgreSQL `lat`/`lng` + Haversine + предфильтр bounding box, B-tree индексы по lat/lng. PostGIS/earthdistance — Фаза 2+ (ADR-0009).
- Для MVP реализовать гео-поиск с использованием формулы Хаверсин, оптимизированной с предварительной фильтрацией ограничивающего прямоугольника для снижения вычислительной нагрузки.
- Внешний геокодинг (адрес в координаты) будет обрабатываться через API Яндекс.Карт посредством абстракции frontend/backend.
- Максимальный радиус поиска применяется на уровне 100км для предотвращения злоупотребляющих запросов.
- Минимальный радиус поиска составляет 1км для обеспечения значимых результатов.
- Данные о местоположении обязательны для всех объявлений; пользователи должны предоставлять местоположение через взаимодействие с картой или ввод адреса.

## Трассируемость НФТ
Эта спецификация охватывает следующие нефункциональные требования:
- **Производительность (НФТ-ПРОИЗВ)**: Запросы гео-поиска должны выполняться за <1s для 95% запросов при ожидаемой нагрузке (см. docs/02-requirements/nfr/performance.md)
- **Безопасность (НФТ-БЕЗОП)**: Использует API Яндекс.Карт для геокодинга, как указано в решении о стеке технологий (см. docs/02-requirements/nfr/security.md)
- **Доступность (НФТ-ДОСТУП)**: Радиус поиска должен быть регулируемым через UI (ползунок/ввод) с четкими единицами расстояния (км) (см. docs/02-requirements/nfr/accessibility.md)

## Пользовательские истории

### Функциональность гео-поиска
**UC-GS-01:** Как пользователь, ищущий животных или объявления рядом со мной, я хочу искать в пределах заданного радиуса, чтобы эффективно находить локальные предложения.
- Критерии приёмки:
  - Радиус поиска регулируется от 1 км до 100 км через ползунок или поле ввода
  - Определение текущего местоположения с разрешения пользователя
  - Ручной ввод местоположения через адрес или взаимодействие с картой
  - Результаты поиска показывают расстояние от местоположения пользователя
  - Гео-поиск выполняется за <1s для 95% запросов
  - Возможность сочетать гео-поиск с другими фильтрами (вид, порода, цена и т.д.)
  - Чёткое указание, когда в радиусе не найдено результатов

**UC-GS-02:** Как пользователь, заботящийся о приватности, я хочу управлять передачей своего местоположения, чтобы комфортно пользоваться платформой, защищая личную информацию.
- Критерии приёмки:
  - Явный запрос разрешения на доступ к местоположению
  - Возможность отключить службы геолокации и использовать только ручной ввод
  - Данные о местоположении хранятся минимально (нужны только широта/долгота для поиска)
  - Точный адрес не передаётся другим пользователям
  - Опция использовать приблизительное местоположение (уровень города/региона) для просмотра
  - Понятное объяснение, как используются и хранятся данные о местоположении

**UC-GS-03:** Как продвинутый пользователь, я хочу сохранять и повторно использовать избранные местоположения и настройки поиска, чтобы быстро обращаться к часто искомым областям.
- Критерии приёмки:
  - Сохранение текущего местоположения как избранного с собственным названием
  - Быстрый доступ к сохранённым местоположениям из интерфейса поиска
  - Сохранение фильтров поиска в сочетании с местоположением для поиска в один клик
  - Синхронизация сохранённых местоположений между устройствами (будущее улучшение)
  - Импорт/экспорт сохранённых местоположений (будущее улучшение)
  - **Скоуп:** сохранение/повторное использование поисков и локаций — **MVP** (хранится в таблице `saved_searches`). Проактивные **алерты** о новых подходящих объявлениях — **LIVE** (Slice H4, SS-M1..SS-M7 ниже); повторное **переисполнение** сохранённого поиска по требованию — **Phase 2** (см. `01-discovery/future-features.md`).

## Алгоритм, контракт результата и edge-cases (раунд 4, нормативно)

**Haversine + bounding-box (MVP):** радиус Земли `R = 6_371_000 м`.
- **Bbox-предфильтр** (использует B-tree по lat/lng): `Δlat = radius_m / 111_320`;
  `Δlng = radius_m / (111_320 * cos(radians(lat)))`; фильтр `lat BETWEEN lat0-Δlat AND lat0+Δlat`, аналогично lng.
- **Точное расстояние:** `d = 2*R*asin(sqrt( sin²((lat-lat0)/2) + cos(lat0)cos(lat) sin²((lng-lng0)/2) ))`, `d ≤ radius_m`.
- **Граница:** сравнение `≤` с допуском `±100 м` (NFR), поэтому «ровно на радиусе» — ВКЛЮЧАЕТСЯ, несмотря на float-погрешность.

**Контракт результата:** `ORDER BY distance_m ASC, created_at DESC, id ASC`; `distance_m` возвращается (округлённо);
пагинация `page`/`limit` (default 20, max 100); `total` = COUNT в радиусе. Всегда с `status='ACTIVE'` и фильтром по `market` животного.

**Edge-cases (нормативно):**
- **Антимеридиан (±180° lng):** при пересечении bbox ±180 (актуально для РФ: Чукотка/Камчатка) — разбить на два диапазона lng (`lng ≥ min` OR `lng ≤ max`).
- **Приполюсные:** клампить `Δlng` (cos→0) до 180°.
- **Нет координат:** объявления без `lat/lng` исключаются из гео-результатов (без fallback на центр города в MVP).
- **Радиус:** `1_000 ≤ radius_m ≤ 100_000`; вне — отклоняется.
- `listings.search_radius_m` — **не** фильтр гео-поиска (зарезервирован под «ищу в радиусе X» для matching); авторитетен радиус запроса.

**Combined search и saved searches:** гео + русский FTS (`to_tsvector('russian', …)`) + триграммы + атрибуты
(species/breed/price/type) — один запрос (bbox + bitmap-AND GIN-индексов). Схема `saved_searches.filters` =
параметры гео-запроса: `{ q?, species_id?, breed_id?, listing_type?, price_min?, price_max? }` + хранимые `lat/lng/radius_m`;
переисполнение маппит их в параметры `/geo-search`.

## Сохранённые поиски — сохранение / список / удаление (раунд 5, нормативно) — Listings Slice 3

> **WHAT:** Закрепить контракт `/saved-searches` (GET list, POST create, DELETE) за валидированными
> инвариантами SS-1..SS-6: чтение в собственном скоупе, удаление 404-no-leak, ограниченный whitelist
> `filters` (вкл. `market`), границы `radius_m` + согласованность lat/lng, обёртка списка
> `{items, meta: PageMeta}` и Idempotency-Key как единственная дедупликация. Без изменения схемы
> (таблица `saved_searches` уже существует; у `radius_m` нет DB CHECK, поэтому его границы — на уровне
> приложения).
> **WHY:** preflight reviewer-qa по Slice-3 вернул GO-no-migration со списком пробелов (G1..G6); контракт
> был неоднозначным (`filters: type:object`, сырой массив списка, не заданное правило owner-scope/no-leak),
> что заставило бы бэкенд гадать по классу риска №1 в истории проекта (IDOR) и по разделению рынков
> ADR-0002.
> **WHY-BETTER-for-the-whole-project:** сборка становится механической и на 100% покрываемой тестами; IDOR
> закрыт на уровне контракта (own-scope + 404-no-leak); ADR-0002 сохраняется в алерты Фазы 2 (сохранённый
> поиск привязан к рынку); форма списка теперь совпадает с API_CONVENTIONS §5 (заявление §5 в заголовке файла
> становится истинным); произвольный клиентский JSON никогда не может быть сохранён.

Эти инварианты **тестируемы** и владеют жизненным циклом сохранённого поиска. Коды ошибок `code` — RFC7807
(`API_CONVENTIONS §4`); переиспользуемые коды отмечены, новые вводятся здесь.

Валидация **на уровне приложения** — у `radius_m` нет DB CHECK. | DTO + service guard. | `422` `RADIUS_OUT_OF_RANGE` (reused, Slice-2 listings) для границы; `422` `GEO_PARAMS_INCOMPLETE` (reused, Slice-2 listings) для согласованности (одно из lat/lng отсутствует, либо несоответствие радиус/точка) |
| **SS-5** | `GET /saved-searches` возвращает стандартную обёртку **`{items: [SavedSearch], meta: PageMeta}`** с query-параметрами `page`/`limit` (зеркалит `/geo-search`), сортировка по умолчанию `created_at:desc`. **Не** сырой массив. | Pagination lib (`backend/src/lib`). | `400` `INVALID_SORT` для `sort` не из whitelist |
| **SS-6** | Дедупликация — **ТОЛЬКО по Idempotency-Key (повтор 24ч)** (§11): **нет** DB-unique на `(user_id, filters)` и **нет** уникальности `name` для пользователя. Два сохранения с **разными** ключами (или без ключа) **разрешены by design**; тот же ключ + то же тело → сохранённый 201 повторяется; тот же ключ + другое тело → 422 (платформенное поведение §11). | Платформенный idempotency middleware. | `422` (§11 повтор ключа с другим телом) |

**Сводка кодов ошибок (сохранённые поиски):**

| code | HTTP | Когда | Reuse / new |
|------|------|-------|-------------|
| `SAVED_SEARCH_NOT_FOUND` | 404 | DELETE несуществующего **или не-своего** id (SS-2 no-leak) | new |
| `INVALID_FILTERS` | 422 | у `filters` неизвестный ключ, несоответствие типа, превышение cap размера 2 КБ, либо `price_max < price_min` (SS-3) | new |
| `RADIUS_OUT_OF_RANGE` | 422 | `radius_m` присутствует, но вне `[1000,100000]` (SS-4) | reused (Slice-2 listings) |
| `GEO_PARAMS_INCOMPLETE` | 422 | lat/lng не «оба присутствуют или оба отсутствуют», либо нарушена согласованность радиус/точка (SS-4) | reused (Slice-2 listings) |
| `INVALID_SORT` | 400 | `sort` не из whitelist (SS-5) | reused (Slice-2 listings) |
| (§11 reuse) | 422 | Idempotency-Key повторён с другим телом (SS-6) | platform §11 |

**Дрейф переисполнения (зафиксировано, не решено — Фаза 2):** сохранённые `filters` используют
`species_id:int`, тогда как `/geo-search` отдаёт `species:string`. Когда алерты/переисполнение Фазы 2
маппят сохранённый поиск в query-параметры `/geo-search`, этот маппинг int↔string (и пробел
`listing_type=leasing` — миграция листингов 0021 добавила `leasing`, ещё не значение `/geo-search`) должен
обрабатываться слоем маппинга. Зафиксировано здесь по правилу иерархии истинности «ни одно требование не
теряется молча».

## Проактивные алерты по сохранённым поискам — сопоставление и уведомление (round-N, нормативно) — Slice H4 (AUDIT4)

> **ЧТО:** Вытянуть «проактивные алерты по сохранённым поискам» (ранее — Фаза 2) вперёд и зафиксировать
> как SS-M1..SS-M7. Когда листинг становится **ACTIVE** (модерация APPROVE → outbox-событие
> `Listing.Activated`, уже эмитится в той же tx), worker-consumer (`SavedSearchMatchConsumer`, второй
> элемент `OUTBOX_CONSUMERS`, отличный от реестрового `NotificationConsumer`) сопоставляет его с
> `saved_searches` пользователей (`offering_type='ANIMAL_LISTING'`) и материализует **одно IN_APP-
> уведомление `saved_search_matched` на каждую совпавшую пару (saved_search, listing)** (читается через
> `GET /v1/me/notifications`). Шаблон засеян как EMAIL ×(ru,en) в миграции 0037 (*channel ≠ source*).
> Ни нового эндпоинта, ни новой колонки схемы.
> **ЗАЧЕМ:** AUDIT4 отметил, что у платформы **нет цикла возврата со стороны спроса** — пользователь
> сохраняет поиск и никогда не узнаёт о подходящем листинге (сильнейший сигнал удержания для
> двустороннего маркетплейса). Событие, таблица `saved_searches`, seam OfferingRef (0032) и инфраструктура
> consumer (0030, ADR-0021) уже существовали; не хватало лишь строки-шаблона + матчера — аддитивный slice,
> хрестоматийный случай «фаза по стоимости изменения».
> **ЧЕМ ЛУЧШЕ-для-всего-проекта:** потребление уже эмитируемого `Listing.Activated` (а не сопоставление
> внутри транзакции модерации) держит модерацию в неведении о сохранённых поисках — сбой сопоставления
> лишь ретраит доставку этого consumer'а, но **не может** откатить валидное одобрение; детерминированный
> по-парный `idempotency_key` уведомления даёт exactly-once при **нулевой** новой схеме (нет колонки-
> маркера, нет цикла опроса); а разделение рынков ADR-0002 структурно обеспечено в предикате сопоставления.

| ID | Инвариант (MUST) | Обеспечение | Прим. |
|----|------------------|-------------|-------|
| **SS-M1** | На `Listing.Activated` сохранённый поиск совпадает, если **все** его присутствующие фильтры удовлетворены листингом. Оцениваемое подмножество: `market`, `species_id`, `breed_id`, `listing_type` (равенство); `price_min`/`price_max` (границы — листинг **без цены** никогда не удовлетворяет поиску с ценовой границей); гео `radius_m`+`lat`/`lng` (точный Haversine — листинг **без координат** никогда не удовлетворяет гео-поиску). | `SavedSearchMatchConsumer.matchSql` (параметризованный `$queryRaw` только по `saved_searches`). | reverse-query |
| **SS-M2** | **`q` свободный текст НЕ вычисляется** серверно (нет дешёвого однозначного полнотекста по локализованному JSONB title/description). Поиск с `q` всё равно совпадает по **остальным** фильтрам. | документированное опущение; полнотекст — отслеживаемый follow-up. | предел подмножества |
| **SS-M3** | **Кросс-рыночная безопасность ADR-0002:** поиск совпадает, только если он **привязан к рынку** листинга — пинит `market` (== рынку листинга) **ИЛИ** пинит `species_id`/`breed_id` (каждый живёт ровно в одном рынке и должен равняться значениям листинга). **Безрыночный** поиск (нет якоря market/species/breed) **НЕ** сопоставляется. Алерт не может пересечь pet↔livestock. | предикат-якорь `matchSql` + пункты равенства. | `422` н/п (read-side) |
| **SS-M4** | **Exactly-once на пару:** не более одного уведомления `saved_search_matched` на пару `(saved_search, listing)`, когда-либо — независимо от at-least-once повторной доставки `Listing.Activated`. | `notification_logs.idempotency_key = 'saved_search_matched:<savedSearchId>:<listingId>'` + `ON CONFLICT DO NOTHING`. | дедуп |
| **SS-M5** | Продавец **никогда** не получает алерт о собственном листинге. | `matchSql`: `s.user_id <> seller_id`. | само-исключение |
| **SS-M6** | Алерт по сохранённому поиску — это **запрошенное пользователем сервисное** уведомление (opt-in самим фактом сохранения), доставляемое через **IN_APP** → **transactional-always, НЕ гейтится `notification_prefs.promo`** (который управляет будущими EMAIL/SMS *маркетинговыми* рассылками). Opt-out — **удаление сохранённого поиска** (SS-2). | consumer пишет IN_APP безусловно, зеркаля дисциплину transactional-always из ADR-0021. | решение о предпочтениях |
| **SS-M7** | Листинг, который **уже не ACTIVE** на момент relay (напр. продан/отменён до near-real-time-обработки события), **не** порождает алерт; удалённый листинг пропускается. | consumer перечитывает листинг и гейтит на `status='ACTIVE'`. | защита от устаревания |

**Follow-ups (зафиксировано, не построено):** (1) полнотекстовое сопоставление `q` (нужна выбранная FTS-
стратегия по локализованному JSONB); (2) **аналитическое** событие `SavedSearch.Matched` для воронки
match→view→contact (сейчас сигнал совпадения — строки `notification_logs`; отдельное событие добавится,
когда data-analyst специфицирует воронку); (3) суточный лимит алертов на пользователя (только если
тривиально переиспользуется из quota-lib) — сегодня анти-спам это по-парный дедуп (SS-M4) + якорение по
рынку (SS-M3); (4) локализация заголовка на получателя (тело алерта интерполирует заголовок листинга
**ru-first**; заголовок по языку — незначительное уточнение).

## Согласование канона near-me + резерв `geo_anchor` (round-6, нормативно) — Wave D / D7

> **ЧТО:** (1) Объявить **`GET /v1/listings`** (discovery-путь Slice-2 — `market` + `lat`/`lng`/`radius_km` +
> `sort=distance`, возвращает `distanceM`) **единственным каноническим near-me-контрактом**. (2) Пометить эндпоинт
> **`/geo-search`** (`geo-search-api.yaml`) **устаревшим — заменённым, плановое удаление**: он дублирует тот же поиск по
> радиусу, **не имеет контроллера** (в `backend/src/modules/` нет geo-модуля — подтверждено grep) и сохранён лишь чтобы
> требование не потерять молча. (3) Пометить **`/geo/geocode`** **запланированным (не реализован)** — геокодирование
> адрес→координаты это будущая возможность (раздел «Вне области»: геокодирование через внешний Maps API), отличная от
> поиска по радиусу; это ни дубликат, ни живой эндпоинт. (4) Направить Phase-2 повтор сохранённого поиска на
> **канонический `/listings`**, а не на `/geo-search`. (5) Зарезервировать **`geo_anchor`** как offering-agnostic форму
> начала поиска (см. ниже). Без изменения схемы, без изменения кода живого пути `/listings`, без правки живого контракта
> `/saved-searches`.
>
> **ПОЧЕМУ:** в корпусе было **два конфликтующих near-me-контракта** — `/geo-search` (`radius_m`, 1000–100000 м,
> `species:string`, мёртвый yaml) и discovery `/listings` (`radius_km`, 1–100, `species_id:int`, ЖИВОЙ в коде).
> Разработчик или Phase-2 слой маппинга не мог понять, какой авторитетен, а спека сохранённых поисков (§159, §201) всё
> ещё направляла повтор на мёртвый эндпоинт. Без согласования это заставляет угадывать на near-me-поверхности.
>
> **ПОЧЕМУ-ЛУЧШЕ-для-всего-проекта:** один авторитетный контракт discovery (нет расходящихся единицы радиуса / типа
> species / пробела `listing_type=leasing` для синхронизации); мёртвый `/geo-search` помечен, а не удалён, так что
> требование доживёт до будущего выделенного geo-домена, если он появится; **резерв `geo_anchor` сейчас** означает, что
> будущий *find-nearby для услуг/товаров* (экосистемное видение) расширит тот же ключ discovery на подтипы предложений
> **без переписывания API** — правило «фаза по стоимости изменения» применено к гео, по образцу seam OfferingRef (ADR-0014).

**Канон (нормативно):**

| Аспект | Канонический (ЖИВОЙ) | Устарел / Запланирован |
|---|---|---|
| Поиск объявлений по радиусу near-me | **`GET /v1/listings`** с `lat`,`lng`,`radius_km` (1–100), `market`, `sort=distance`, ответ `distanceM` | `GET /geo-search` (`radius_m`) — **устарел, заменён, плановое удаление; нет контроллера (мёртвый)** |
| Адрес → координаты | — (в MVP нет) | `GET /geo/geocode` — **запланирован (не реализован)**; будущий прокси внешнего Maps |
| Сохранить/список/удалить поиск | **`/saved-searches`** (ЖИВОЙ, SS-1..SS-6) — без изменений | — |

**Согласование единиц (Phase-2 маппинг, зафиксировано — заменяет маршрутизацию §159/§201):** сохранённый поиск хранит
`radius_m` (метры); канонический путь `/listings` принимает `radius_km`. Phase-2 повтор/алерты ДОЛЖНЫ маппить
сохранённый поиск в параметры **`/listings`**: `radius_km = round(radius_m / 1000)`, `species → species_id` (int-lookup)
и обработку значения `listing_type=leasing` (есть в `/listings`). Прежний текст, маппящий в `/geo-search`, сохранён выше
как исторический след, но **больше не цель** — цель это канонический путь `/listings`.

### `geo_anchor` — offering-agnostic резерв начала discovery (только форма; без реализации)

`geo_anchor` — это **зарезервированная абстракция «где ищет искатель»**, offering-agnostic, чтобы будущий find-nearby по
**услугам / товарам / экспертизе** (экосистемное видение) переиспользовал один ключ discovery, а не выводил заново
per-offering geo-API.

- **Сегодняшняя конкретная форма (единственный реализованный случай):** `geo_anchor` это **точка + радиус** — триплет
  `lat`/`lng`/`radius_km`, уже присутствующий в `GET /v1/listings`. В живом контракте ничего не меняется; текущие
  параметры И ЕСТЬ точечная форма `geo_anchor`.
- **Зарезервированные будущие формы (отложены, gated — здесь НЕ строятся):** **именованное место / полигон города-или-региона**,
  **зона обслуживания** провайдера (покрытие продавца/вета/грумера) и хранилище **PostGIS `geography`**. Это Фаза 2+ по
  ADR-0009 (PostGIS явно Target, не MVP) и остаётся отложенным/gated — этот раздел резервирует только **форму и имя**, без
  колонки, эндпоинта, поведения.
- **Инварианты, которые ДОЛЖНЫ выполняться, когда появится более богатая форма:**
  - **G7-1 (рынки остаются разделены):** `geo_anchor` offering-и-market-agnostic как *локация*, но discovery по нему ДОЛЖЕН
    по-прежнему AND-пересекать фильтр `market` (ADR-0002) — гео-якорь никогда не расширяет и не смешивает рынки.
  - **G7-2 (один контракт):** find-nearby для нового подтипа предложения расширяет **канонический discovery-контракт в
    стиле `/listings`** (или его offering-обобщённого преемника) — НЕ воскрешает параллельный эндпоинт в стиле `/geo-search`.
  - **G7-3 (пара с OfferingRef):** когда discovery охватывает предложения, результат `geo_anchor` несёт полиморфные
    `offeringType`/`offeringId` (ADR-0014 OfferingRef, миграция 0032), чтобы один near-list связно смешивал подтипы.
  - **G7-4 (форма-сейчас, поведение-отложено):** резерв `geo_anchor` не даёт **ничего** в рантайме сегодня — единственное
    живое поведение это существующие точка+радиус на `/listings`. Богатые якоря за будущими gates.

> Кросс-ссылки: таблица seam в `docs/04-decisions/ECOSYSTEM_ADR_PLAN.md` (Wave D / **D7**, миграция = нет);
> `AUDIT3/architect.md` (geo_anchor RESERVE-NOW); OfferingRef `ADR-0014 §Amendment 2026-07-04`. Отдельный нумерованный ADR
> для `geo_anchor` здесь **не** заводится (D7 — contract/code-only, без схемы); если будущая богатая форма окажется
> структурной — эскалировать к **architect** за ADR в тот момент.
