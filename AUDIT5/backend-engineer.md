## 2. Находки (severity · антарая · file:line · образец)

### Б1 · BLOCKER · ось 3 (границы) + ось 7 (цена) — глобальный rate-limit считает ВСЕХ клиентов одним IP

**Антарая:** `бхранти-даршана` (замер объявляет «на клиента», а меряет обратный прокси; авивека: адрес
соединения принят за адрес пользователя).

- `src/lib/rate-limit/rate-limit.module.ts:17` — глобальный `APP_GUARD` ThrottlerGuard, `limit: 100 / ttl 60_000`.
- `node_modules/@nestjs/throttler/dist/throttler.guard.js:141` (v6.5.0, прочитано в исходнике, не по памяти):
  `async getTracker(req) { return req.ip; }`.
- `grep -rn "trust proxy|trustProxy|X-Forwarded|getTracker" backend/src` → **пусто**. `src/main.ts:18-56` не
  ставит `app.set('trust proxy', …)`, `getTracker` нигде не переопределён.
- `docker-compose.yml:12` `image: caddy:2-alpine`, `deploy/Caddyfile:18` `reverse_proxy api:3000`; сервис `api`
  живёт в сетях `[edge, internal]` **без опубликованных портов** — то есть каждый запрос приходит в Express с
  IP контейнера Caddy.

Express без `trust proxy` даёт `req.ips = []` и `req.ip` = адрес сокета. Значит **вся платформа сидит в одном
ведре**:

| ведро | объявлено | фактически при Caddy |
|---|---|---|
| default (все маршруты) | 100 запросов / 60 с на клиента | 100 / 60 с **на всю платформу** = 1,67 req/s |
| `identity.controller.ts:29` REGISTER | 5 / 15 мин на IP | **5 регистраций на всю платформу за 15 минут** (480/сут) |
| `identity.controller.ts:33` RECOVER_REQUEST | 5 / 15 мин | 5 восстановлений на всю платформу |
| `content-report.controller.ts:30` REPORT | 10 / 15 мин | 10 жалоб на всю платформу |
| `agent-credential.service.ts:154` per-IP 60/ч | «на IP, против credential-stuffing» | 60 обменов токена **на всех агентов вместе** |

**Образец с названной нагрузкой:** 1000 активных пользователей × ~50 запросов/сут = 50 000 req/сут; если
пик — 8 часов, это **1,74 req/s против потолка 1,67 req/s**. То есть на объявленной нагрузке платформа
throttled'ится **в день запуска**, а пользователи видят чужие 429. Регистрация ломается раньше всех: шестой
человек за 15 минут получает 429 и уходит.

**Почему это тихий отказ:** оператор увидит «429» и решит, что кого-то штормит; метрика по IP покажет ОДИН IP
с аномальным трафиком — тот самый прокси. Ни одна ось до сегодняшней этого не смотрела.

**Починка:** `app.set('trust proxy', 1)` (или подсеть docker-сети edge — доверять ТОЛЬКО Caddy, иначе клиент
подделает `X-Forwarded-For` и обойдёт лимит) + приёмочный тест: два запроса с разными `X-Forwarded-For`
обязаны попасть в РАЗНЫЕ вёдра, а третий с подделанным заголовком в обход прокси — в общее.
Смежники: **security** (подделка XFF), **devops** (Caddyfile/сеть).

### Б2 · BLOCKER (для слайса H4) · ось 1 + ось 3 — «ru-fallback» локализации заголовка структурно не может сработать

**Антарая:** `бхранти-даршана` (юнит-тест мерит форму, которой боевой производитель не порождает).

- Производитель: `src/modules/notification/saved-search-match.consumer.ts:282-284` `localizedTitle()` →
  `{ ru: this.locale(...,'ru'), en: this.locale(...,'en') }`, а `locale()` (`:301-307`) на отсутствующей локали
  возвращает **`''`**, не `undefined`.
- Потребитель: `src/modules/notification/notification-writer.service.ts:117`
  `out[key] = byLang[language] ?? byLang.ru ?? '';` — `??` **не** откатывается на пустой строке.

Итог: ключ всегда присутствует, fallback никогда не срабатывает. **Прогон РЕАЛЬНЫХ методов** (ts-node,
`new SavedSearchMatchConsumer(...)` → `new NotificationWriter(...)`, без переписывания логики):

```
ru-only объявление | получатель=ru   produced={"ru":"Щенок лабрадора","en":""}   rendered listing_title="Щенок лабрадора"
ru-only объявление | получатель=en   produced={"ru":"Щенок лабрадора","en":""}   rendered listing_title=""        ← ПУСТО
en-only объявление | получатель=ru   produced={"ru":"","en":"Labrador puppy"}    rendered listing_title=""        ← ПУСТО
en-only объявление | получатель=fr   produced={"ru":"","en":"Labrador puppy"}    rendered listing_title=""        ← ПУСТО
битый title_localized | любой        produced={"ru":"","en":""}                  rendered listing_title=""
```

**Достижимо сегодня, не в теории:** `listing.service.ts:194` требует лишь **одну** непустую локаль
(`titleLocalized must have at least one non-empty locale`), а `users.preferred_language` — настраиваемое поле
(`profile.service.ts:55`, `@IsIn(['ru','en'])`). На dev-БД **141 из 3325 пользователей = 4 % уже стоят `en`**
(`select preferred_language, count(*) from users group by 1`). Значит первое же демандное письмо возвратной
петли — «Новое объявление по вашему поиску: » с пустым заголовком.

**Ось 13 (адресность) — тест не ловит свою мутацию:** `notification-writer.service.spec.ts:48` фикстура
`{ ru:'Щенок', en:'Puppy' }` (ОБЕ локали заполнены), `:56` fallback проверяется языком `'fr'`, ключа которого
в карте нет. Обе формы боевой `localizedTitle()` не порождает никогда. Тест зелёный, поведение сломано.

**Починка (одна строка + тест):** `locale()` возвращает `undefined` при отсутствии локали (тогда `??`
заработает), либо `resolveLocalized` переходит на проверку по истинности: `byLang[language] || byLang.ru || ''`.
Тест-мутант: en-only объявление + получатель `ru` → в теле обязан быть английский заголовок, не пустая строка.

### Б4 · MAJOR · ось 3 — сохранённый поиск с `null`-значением любого ключа молча умирает навсегда

**Антарая:** `бхранти-даршана` (для class-validator `null` == «отсутствует», для JSONB `filters ? 'q'` —
«присутствует»; два слоя понимают null по-разному, и никто не мерит стык).

Проба DTO (ts-node на реальном `SavedSearchFiltersDto` с теми же опциями, что в `saved-search.service.ts:147`):

```
q:null             ACCEPTED      ← @IsOptional() пропускает null
market:null        ACCEPTED
species_id:null    ACCEPTED
q:newline          ACCEPTED
q:NUL-byte         ACCEPTED
q:200ok            ACCEPTED
q:201              REJECTED(q)
unknown-key        REJECTED(bogus)
q:number           REJECTED(q)
```

Проба матчера (точная копия `matchSql`, `saved-search-match.consumer.ts:236-274`, на живом PG,
`BEGIN…ROLLBACK`):

```
t4-q-JSON-NULL    {"market":"pet","q":null}        → matched = NULL (не TRUE) → НИКОГДА не совпадёт
t5-market-NULL    {"market":null,"species_id":1}   → matched = NULL           → НИКОГДА не совпадёт
```

Механизм: `s.filters ? 'q'` = TRUE, но `s.filters->>'q'` = SQL NULL → `btrim(NULL)=''` → NULL, `strpos(...)>0`
→ NULL; вся цепочка AND схлопывается в NULL, строка не возвращается. `t5` особенно нагляден: `species_id:1`
совпадает с объявлением, но `market:null` убивает якорь.

**Что видит пользователь:** 201 Created, поиск в списке, ноль уведомлений, ноль записей в логах. Идеально тихий
отказ ровно в той функции, ради которой слайс H4 существовал (возвратная петля).

**Починка:** в `validateFilters` (`saved-search.service.ts:133-163`) выбрасывать ключи со значением `null`
(либо 422) ДО записи; в `matchSql` подстраховаться `IS NOT TRUE`/`COALESCE`, чтобы NULL не поглощал предикат.
Негативный тест: создать поиск с `{"market":"pet","q":null}` → активировать подходящее объявление → строка
уведомления ОБЯЗАНА появиться (сегодня — нет).

### Б5 · MAJOR · ось 4 — список уведомлений деградирует ЛИНЕЙНО от пожизненного числа алертов

**Антарая:** `прамада` (индекс под сортировку не дописан, хотя `orderBy` стоит рядом в том же файле).

`src/modules/notification/notification-read.service.ts:40-50`: `where {user_id, type:'IN_APP'}`,
`orderBy [{created_at:'desc'},{id:'desc'}]`, offset-пагинация, **плюс `count()` на КАЖДЫЙ запрос страницы**.
Индекс всего один: `idx_notiflog_user btree (user_id)` — ни `type`, ни `created_at` в нём нет.

Измерено на живом PG (50 000 IN_APP-строк одному пользователю, вставлены и откачены в одной транзакции):

| запрос | факт |
|---|---|
| страница 1 (`LIMIT 20 OFFSET 0`) | Index Scan по **всем 50 000** записям индекса, `Buffers: shared hit=1540`, top-N heapsort, **49,0 мс** |
| `count(*)` того же запроса (идёт в том же HTTP-вызове) | ещё **23,2 мс**, ещё 1540 буферов |
| глубокая страница (`OFFSET 40000`) | **external merge sort, Disk: 1672 kB**, temp read=209/written=210, 27,6 мс |

Итого один просмотр первой страницы почтового ящика = **~72 мс и ~3080 буферов**, и это растёт линейно
навсегда, потому что ретенции нет (Б3).

**Кто набивает ящик так быстро:** матчер считает поиск «привязанным к рынку» уже при одном ключе `market`
(`saved-search-match.consumer.ts:241`). То есть сохранённый поиск `{"market":"pet"}` **совпадает с КАЖДЫМ
активированным объявлением рынка**, а суточной шапки нет (спец 07 её сознательно отложил). При модели §4
(50 активаций/сут) такой пользователь получает 50 алертов/сут → 50 000 строк за **2,7 года**; при 10-кратном
объёме объявлений — за **100 дней**. Разовый выброс тоже возможен: шапка фан-аута `MAX_MATCHES_PER_LISTING = 500`
(`:11`) → одно популярное объявление = до 500 строк уведомлений + 500 событий outbox.

**Починка:** индекс `(user_id, type, created_at DESC, id DESC)` (уберёт и сортировку, и heap-фильтр), keyset-
пагинация вместо offset, `count` — приблизительный/кешируемый; и вернуть к решению отложенную суточную шапку /
дайджест (**архитектор** + **data-analyst**, как и записано в спеке).

### Б6 · SHOULD-FIX · ось 4 — `refresh_tokens` не чистится; протухшие сессии остаются в «активном» частичном индексе

**Антарая:** `стьяна` (частичный индекс объявлен «только живые сессии», но живым он быть перестал).

Измерено на dev-БД: **3486 строк, из них 3013 = `revoked_at IS NULL AND expires_at < now()`** против **37**
действительно живых. Соотношение мусора к делу — **81 : 1**, и весь мусор сидит в
`idx_refresh_tokens_user_active btree (user_id) WHERE revoked_at IS NULL`, то есть в индексе, который создавался
маленьким по замыслу.

Причины:
- ни одного `DELETE` по `refresh_tokens` в коде нет (`grep`: только `updateMany … revoked_at`), ретенция их не
  знает (Б3);
- `refresh-token.service.ts:138-149` `evictOldestIfOverCap` считает семьи по `revoked_at IS NULL` **без**
  `expires_at > now()` → протухшая брошенная семья занимает слот из `MAX_ACTIVE_FAMILIES = 5`
  (`refresh-token.service.ts:6`), пока следующий логин её не вытеснит.

**Скорость роста при названной нагрузке:** access-TTL 15 мин (`.env: JWT_ACCESS_TTL=15m`), ротация создаёт
НОВУЮ строку и никогда не удаляет старую (`:87-99`). При 2 часах активного пользования = 8 ротаций + 1 логин =
**9 строк/пользователя/сут** → 1000 DAU = **9 000 строк/сут = 3,29 млн строк/год**. При измеренных **500 байт
на строку** (1704 kB / 3486 строк, вместе с индексами) это **4,5 МБ/сут ≈ 1,64 ГБ/год** — **самый быстрый
накопитель в системе, и на ~99 % это мусор**.

**Починка:** проход в `RetentionService`: `DELETE FROM refresh_tokens WHERE expires_at < now() - interval
'30 days'` (идемпотентно, батчами) + `AND expires_at > now()` в запросе вытеснения. Заодно закрыть контрактную
дыру: `refresh_tokens` отсутствует в таблице ретенции data-governance.

### Б7 · SHOULD-FIX · ось 3 + ось 4 — `INCR`-затем-`EXPIRE` не атомарен: ключ может навсегда потерять TTL

**Антарая:** `прамада` (TTL ставится только при `count === 1` — ровно в тот единственный момент, когда его можно
потерять; данные были на виду).

Три идентичные копии одного кода:
- `src/modules/agent-auth/agent-credential.service.ts:321-334` (обмен токена агента, 30/ч на credId, 60/ч на IP),
- `src/modules/animal/transfer.service.ts:654-667` (лимит инициации трансфера),
- `src/modules/listing/listing.service.ts:665-681` (contact-reveal).

Проба на живом Redis (свой ключ, удалён сразу):

```
after INCR only -> TTL=-1        ← ключ ВЕЧНЫЙ
after EXPIRE   -> TTL=3600
cleaned: exists=0
```

Если процесс умрёт / соединение оборвётся между `INCR` и `EXPIRE`, счётчик становится вечным. Как только он
переползёт лимит, этот credId / viewer / IP получает **429 навсегда**, причём `const retryAfter = ttl > 0 ? ttl
: RATE_WINDOW_SEC` отдаёт клиенту утешительные 3600 секунд, которые никогда не истекут. Плюс вечный ключ в
Redis — тихое накопление (сегодня живая база чистая: `info keyspace` → `db0:keys=359,expires=359`, TTL есть у
всех 359 — счастливый путь держит, вопрос только в окне краха).

**Починка:** одна атомарная операция — Lua-скрипт или `SET key 0 EX <window> NX` + `INCR`; и вынести три копии
в единый лимитер в `src/lib/rate-limit` (сейчас это тройное дублирование одного алгоритма).

### Б8 · MINOR · ось 3 — `q` всё-таки склеивается через границу полей, если сам содержит перевод строки

**Антарая:** `бхранти-даршана` (гарантия объявлена в docstring и в нормативной спеке, но не держится).

`saved-search-match.consumer.ts:287-290` и спека 07 SS-M2 утверждают: поля склеены `\n`, поэтому «`q` никогда не
совпадёт через границу двух разных полей». Проба (живой PG, точная копия предиката):

```
t8-q-cross-field  {"q":"лабрадора\nPuppy"}  → matched = TRUE   (title_ru "…лабрадора" + title_en "Puppy")
t9-q-trailing-nl  {"q":"милый\n"}           → matched = TRUE   (desc_ru "Очень милый" + desc_en "Very cute")
```

DTO перевод строки пропускает (`@IsString @MaxLength(200)`, проба Б4: `q:newline ACCEPTED`). Ущерб мал —
это лишний, слишком широкий матч, а не утечка через рынок (якорь ADR-0002 проверяется отдельно и держит).
**Известный nit подтверждён, но уточнён:** обычный многословный `q` границу не пересекает (разделитель `\n`, не
пробел) — нужен именно перевод строки внутри `q`.
**Починка:** нормализовать пробелы в `q` при валидации (или отбить управляющие символы) и поправить формулировку
docstring + SS-M2 — сначала документ, потом код.

### Б9 · MINOR (гипотеза) · ось 3 — `q` с байтом U+0000 обещает 500 вместо 422

DTO принимает (проба Б4: `q:NUL-byte ACCEPTED`), а jsonb — нет:

```
psql> SELECT '{"q":"a\u0000b"}'::jsonb;
ERROR:  unsupported Unicode escape sequence
DETAIL:  \u0000 cannot be converted to text.
```

Prisma сериализует объект `filters` в JSON-текст, PG приводит его к jsonb → ошибка драйвера, неотображённая в
RFC7807 → 500 вместо честного 422 INVALID_FILTERS. **Сквозь Prisma не проверял** — помечаю гипотезой.
Тест: `POST /v1/saved-searches` с `q`, содержащим `\u0000` → ожидается 422.

### Б10 · MINOR · ось 3 — агентский credential можно выпустить уже протухшим

`agent-credential.service.ts:273-280` `parseExpiry` проверяет только `Number.isNaN`. `expiresAt` в прошлом →
201 Created, plaintext-секрет показан ОДИН раз (`:100`) и не обменивается никогда (`:169` `expires_at.getTime()
> now` → uniform 401). Ни предупреждения, ни лога. Админ получает мёртвый ключ и узнает об этом от агента.
**Антарая:** `прамада`. **Починка:** 422, если `expiresAt <= now()`. В e2e (`test/agent-auth.e2e-spec.ts:288`)
покрыт только уже-истёкший при обмене, не выпуск в прошлое.

### Б11 · INFO · `confirmed_sales` не имеет собственного CHECK «ровно одна сторона»

`\d confirmed_sales`: CHECK'и есть на `market`, `status`, `anchor_type`, `offering_type`,

### Б12 · INFO · у `q` сохранённого поиска нет прямого аналога

## 3. Что оси проверили и что ДЕРЖИТ (ось 12 — замок пропускает годное)

Опровергнутые гипотезы важны не меньше находок:

1. **Кириллица в `lower()` — работает, включая закреплённый прод-образ.** Дев-PG14 `lc_ctype = en_US.UTF-8`;
   `strpos(lower('ЩЕНОК Лабрадора'), lower('щенок')) = 1`. Риск «C-локаль ломает регистронезависимость» проверен
   **запуском самого образа**: `docker run --rm postgres:16-alpine` → `lower('ЩЕНОК') = 'щенок'`,
   `strpos(...) = 1`. Гипотеза **опровергнута для закреплённого стека** (`COLLATE "C"` действительно не
   опускает регистр — проверено отдельно, — но БД так не создаётся).
2. **Пустой и пробельный `q` — no-op, как объявлено** (пробы `t2`, `t3` → TRUE).
3. **Спецсимволы `%`, `_`, `\` литеральны** (`t6`, `t7` → FALSE): `strpos` — не `LIKE`, wildcard-класса нет;
   параметр связан, инъекции нет.
4. **Рост outbox НЕ трогает relay.** Гипотеза «100 % обработанных строк убьют выборку» опровергнута замером:
   при **100 000** обработанных строк план тот же — `Index Scan using idx_outbox_ready`, **1 буфер, 0,045 мс**
   (базовая линия на 2871 строке: 4 буфера, 0,105 мс). Частичный индекс `WHERE processed_at IS NULL AND
   dead_lettered_at IS NULL` изолирует relay от завала полностью. Потолок outbox — хранение и бэкап, не relay.
5. **TTL у Redis-ключей есть у всех, кто их ставит:** idempotency (`idempotency.interceptor.ts:74,123` — `EX` и
   на резервацию, и на результат), OTP (`otp.service.ts:55-57,77,80`), claim-code (`claim-code.service.ts:64,116`),
   view-dedup (`listing.service.ts:310`, `EX 1800 NX`), throttler (`ThrottlerStorageRedisService`). Живая база:
   359 ключей, **у всех 359 есть expires**. Единственная дыра — окно Б7.
6. **Края agent-auth покрыты e2e и держат:** битый/чужой формат и неверный секрет → один и тот же 401
   (`test/agent-auth.e2e-spec.ts:244`), ревокнутый → 401 (`:254`), истёкший → 401 (`:288`), пустой профиль →
   обмен проходит, но операция запрещена deny-by-default (`:229`), AGENT-ADMIN не может выпускать (`:151`),
   деактивация агента каскадно рвёт креды (`:299`, `:318`). Разбор `parseCredential` (`:262-271`) отбивает
   `zlk_agent_<uuid>` без секрета (`sep = -1`) и `zlk_agent__secret` (`sep = 0`). **Не покрыто: границы
   rate-limit (30/ч, 60/ч) — ни одного теста, и именно там живёт Б1.**
7. **Захват `confirmed_sales` покрыт по всем названным краям:** org→user (`test/confirmed-sales.e2e-spec.ts:228`),
   →org (`:255`), livestock (`:278`), параллельный accept — ровно одна строка (`:182`), повторный accept —
   без второй строки (`:173`), declined/cancelled/expired — без строки (`:197`,`:206`,`:215`), append-only и
   все CHECK'и негативно (`:310-344`). Этот лейн — самый крепкий в волне; «самый первый трансфер в пустой БД»
   ничем не отличается (никаких агрегатов/счётчиков он не трогает).

## 4. Ось 4 — модель накопления с названной нагрузкой

**Измеренная цена строки** (живой PG14, вместе с индексами; получено разностью `pg_total_relation_size` до/после
вставки, транзакция откачена):

| таблица | байт/строку | как получено |
|---|---|---|
| `outbox_events` | **454** | Δ 43,3 МБ / 100 000 строк (полезная нагрузка формы `SavedSearch.Matched`) |
| `notification_logs` | **338** | Δ 16,1 МБ / 50 000 строк (IN_APP-алерт) |
| `audit_log` | **376** | 13 МБ / 36 230 строк живой таблицы |
| `refresh_tokens` | **500** | 1704 kB / 3486 строк живой таблицы |

**Допущения нагрузки (назовите иные — пересчитайте по тем же множителям):**
A1 — 1000 активных пользователей/сут. A2 — 5 % публикуют объявление → **50 активаций/сут**. A3 — каждая
активация даёт 2 события (`Moderation.Decided` + `Listing.Activated`). A4 — 2 % инициируют трансфер → 20/сут ×
3 события (`Initiated` + разрешение + `ConfirmedSale.Confirmed`). A5 — фан-аут сохранённых поисков **M** на
активацию; считаю два сценария: **M = 10** (ранний рынок) и **M = 100** (зрелый: ~10 % DAU держат один
привязанный к рынку поиск); жёсткая шапка — 500. A6 — сессии: access-TTL 15 мин, ~2 ч активности → 9 строк
`refresh_tokens`/пользователя/сут. A7 — ~3 аудируемых действия на пользователя/сут.

| накопитель | строк/сут | МБ/сут | ГБ/год |
|---|---|---|---|
| `refresh_tokens` | 9 000 | 4,50 | **1,64** ← быстрее всех, ~99 % мусор (Б6) |
| `audit_log` | 3 000 | 1,13 | 0,41 (контракт разрешает 3 года → 1,2 ГБ) |
| `outbox_events`, M = 10 / M = 100 | 660 / 5 160 | 0,30 / 2,34 | 0,11 / **0,86** |
| `notification_logs`, M = 10 / M = 100 | 560 / 5 060 | 0,19 / 1,71 | 0,07 / **0,62** |
| **итого** | | **6,1 / 9,7** | **2,2 / 3,5** |

**Что сломается ПЕРВЫМ (по порядку, а не по громкости):**

1. **Глобальный throttler — в день выхода на 1000 DAU** (Б1). Потолок 1,67 req/s против 1,74 req/s расчётного
   пика; регистрация умирает на шестом человеке за 15 минут. Это не накопление вовсе — это неверный адрес
   замера, и потому оно бьёт раньше любого роста.
2. **Список уведомлений** (Б5): линейная деградация, измеренные 72 мс + 3080 буферов на 50 000 строк. При
   рыночно-привязанном поиске — 2,7 года при названной нагрузке, **~100 дней** при 10-кратном объёме
   объявлений. Первым это почувствует самый лояльный пользователь — тот, кто дольше всех с нами.
3. **`refresh_tokens`** (Б6): 3,29 млн строк/год, «активный» частичный индекс уже сегодня 81:1 мусорный.
4. **Диск и бэкапы** — последними: 2,2–3,5 ГБ/год. То есть «не прунить» само по себе платформу не свалит;
   свалит её **отсутствие индексов под запросы к разросшимся таблицам** и невыполненное обещание ретенции.
