**Сводка по швам:** из десяти позиций **обходов нет ни у одной** — ни один шов не обойден кодом,
который писал бы мимо него. Деградация другая и однотипная: **шов кладут, а инвариант вокруг него
оставляют на старой колонке** (`favorites.listing_id` UNIQUE), **или пишут в шов журналом там, где
форма обещает состояние** (`user_roles`), **или оставляют словарь уже, чем обещанный ADR-ом**
(`market` без `both`). Это не небрежность исполнителя — это отсутствие приёмочного вопроса
«переехал ли ИНВАРИАНТ на новый шов, а не только колонка».

### 2.2 Инверсия статусов — **вернулась** (новая, не та, что закрыл AUDIT4)

`AUDIT4/architect.md:29` записал в FIXED-VERIFIED: «инверсия prerequisite-before-dependent решена,
цепочка монотонна». На `c44874c` цепочка **снова не монотонна**, в другом месте:

```
docs/04-decisions/0020-versioned-consent-record-model.md:  **Status**: Proposed — ready; awaiting owner nod …
docs/04-decisions/0021-first-outbox-consumer-notification-path.md:  **Status**: Proposed
```

При этом:
- **ADR-0020 реализован полностью** — миграция `0029` завела `consents`, `0036` добавила `seq`,
  `0040 §C` расширила `chk_consents_consent_type` на `REVIEW_PUBLICATION`, а `ConsentService`
  живёт в коде и гейтит распространение контактов;
- **ADR-0021 реализован полностью** — миграция `0030`, `NotificationConsumer` — первый
  зарегистрированный `OUTBOX_CONSUMERS`, `0037` добавил второго;
- **ADR-0039 (Accepted)** в шапке пишет «**Builds on** ADR-0020 … ADR-0021» — то есть **принятое
  решение стоит на двух только предложенных**.

Это не косметика: иерархия истины ставит ADR **выше** схемы, а здесь схема ушла впереди двух ADR,
которые формально ещё не решения. Любой, кто завтра будет разрешать конфликт «код vs ADR-0020»,
получит ответ «ADR не действует» — при живой таблице и живом гейте.

**Антарая: `анавастхитатва` (достигнутое не удержано)** — класс дефекта был вычищен для 0014/0018 в
июльской волне и отрос на 0020/0021 в следующей же. Лечится не «поправить статус ещё раз», а замком:
приёмка слайса, который реализует ADR, должна требовать, чтобы этот ADR был Accepted **до** миграции.

### 2.3 Мелкий дрейф статуса/нумерации

- **Пропуск номеров ADR 0023–0034.** Индекс `docs/04-decisions/README.md` прыгает с 0022 сразу на
  0035; файлов 0023–0034 нет, резервирующей записи — тоже. Похоже на попытку выровнять номер ADR по

## 4. РАЗВИЛКА A — `markSold` PENDING→CONFIRMED против append-only `confirmed_sales`

### 4.1 Что на самом деле сломано (шире, чем в постановке задачи)

Постановка называет одну транзакцию. На живых артефактах их **шесть**. Машина состояний
`docs/specs/18-reputation.md:252-262`:

```
[*] --> PENDING_CONFIRMATION : markSold + номинация покупателя
[*] --> CONFIRMED            : transfer COMPLETED          ← единственная, совместимая с append-only
PENDING_CONFIRMATION --> CONFIRMED : покупатель подтвердил
PENDING_CONFIRMATION --> DISPUTED  : сторона оспорила
PENDING_CONFIRMATION --> EXPIRED   : вышел срок
PENDING_CONFIRMATION --> CANCELLED : продавец отозвал
DISPUTED --> CONFIRMED / CANCELLED : решение модерации
```

Триггер `trg_confirmed_sales_immutable` (`database_schema.sql:694-696`) блокирует **любой** UPDATE.
То есть на выбранной форме реализуемо **ровно одно ребро из семи** — то, которое и построено.

Противоречие живёт **внутри самого ADR-0038**, не только в коде: строка 72 решает «LISTING_MARK_SOLD
создаёт строку PENDING_CONFIRMATION», строка 74 — «его **собственная машина состояний**», а sketch
на строке 174 — «append-only через `trg_block_modify_append_only` (переиспользовать — **не изобретать
второй путь неизменяемости**)». Два этих требования несовместимы, и запрет на второй путь
неизменяемости — это ограничение, которое ADR наложил сам на себя и которое теперь связывает руки
двум из трёх веток.

Дополнительно, что важно для цены: `status` имеет `DEFAULT 'PENDING_CONFIRMATION'` (`:662`), то есть
**таблица спроектирована под машину состояний**, а единственный живой писатель этот дефолт
перекрывает. Форма и поведение смотрят в разные стороны уже сейчас.

### 4.2 Ветки с ценой

#### Ветка A-i — **строка-преемник** (как `consents`): переход = новая строка, старую не трогаем

| Ось | Цена |
|---|---|
| **Реализация** | Миграция: добавить `seq BIGINT GENERATED ALWAYS AS IDENTITY` (ADR-0039 §3 сам объявил монотонный `seq` **стандартным требованием ко всякой append-only-таблице «побеждает последний»** — у `confirmed_sales` его нет, у `consents` и `reviews` есть: `:1227`, `:728`) + индекс головы. **Снять или перестроить `uq_confirmed_sales_transfer UNIQUE(ownership_transfer_id)`** (`:687`) — вторая строка той же сделки его нарушит; заменять придётся частичным unique по голове, что возвращает ровно ту болезнь, которую разбирает Развилка B. Плюс всем читателям — резолвер головы вместо чтения строки. |
| **Владение** | Дорого и надолго. «Сделка» перестаёт быть строкой и становится **цепочкой**, а цепочку нужно разрешать в каждом месте: репутация, funnel, ФЗ-152-стирание, экспорт. `reviews.confirmed_sale_id → confirmed_sales(id) ON DELETE CASCADE` (`:711`) указывает на **конкретную строку**: отзыв, написанный на строку-состояние `CONFIRMED`, при последующем диспуте окажется прицеплен к устаревшему звену, а `uq_reviews_current_per_direction` ключуется по `confirmed_sale_id` — цепочка расщепит «один отзыв на направление» на «по одному на звено». Это делает A-i **самой дорогой веткой не в реализации, а в эксплуатации**. |
| **Конфликт с инвариантами** | Прямой с `uq_confirmed_sales_transfer` (INV-4-зеркало). Косвенный, но тяжёлый — с якорем proof-of-transaction ADR-0039 §3. |
| **Обратимость** | **Средняя.** Уйти с цепочки на что угодно другое = схлопывать историю, а схлопывание append-only — это и есть то, чего append-only не разрешает. |
| **Совместимость с ADR** | Полная с ADR-0038 §5 (второго пути неизменяемости не появляется). |

#### Ветка A-ii — **частичное ослабление триггера** (разрешить UPDATE только колонок статуса)

| Ось | Цена |
|---|---|
| **Реализация** | Дешевле всего по строкам кода: одна триггерная функция, разрешающая UPDATE, если менялись только `status/confirmed_at/buyer_confirmed_at` и переход легален. **НО** `trg_block_modify_append_only` — **общая** функция четырёх таблиц (`moderation_decisions :484`, `consents`, `confirmed_sales :696`, `reviews :744`). Править её нельзя, значит нужна **вторая** функция — а это ровно то, что ADR-0038 sketch:174 запретил дословно. Ветка требует **поправки принятого ADR**, а не только миграции. |
| **Владение** | Умеренное, но качественно иное: неизменяемость перестаёт быть свойством **таблицы** и становится свойством **колонки**. Каждый будущий столбец придётся классифицировать вручную; ошибка классификации тихая. Приёмка усложняется: сегодня «append-only» доказывается одним негативным тестом (`reputation-storage.e2e-spec.ts:87-92`), после — матрицей «колонка × переход». |
| **Конфликт с инвариантами** | С самим ADR-0038 §5. С аудиторской ценностью реестра: строка перестаёт быть свидетельством того, что было в момент действия. |
| **Обратимость** | **Низкая.** После первого мутированного статуса вернуться к строгому append-only нельзя — предыдущие значения не сохранены **нигде**. Эту ветку выбирают один раз и навсегда. |
| **Что смягчает** | Если добавить «журнал переходов» рядом, обратимость возвращается — но это уже ветка A-iii. |

#### Ветка A-iii — **`markSold` пишет отдельную не-append таблицу подтверждений**

| Ось | Цена |
|---|---|
| **Реализация** | Новая таблица (`sale_confirmations` или аналог), изменяемая, с собственной машиной состояний; `confirmed_sales` остаётся append-only и приобретает **честное имя**: строка появляется **тогда и только тогда, когда сделка подтверждена**. Требует: убрать `DEFAULT 'PENDING_CONFIRMATION'` и сузить `chk_confirmed_sales_status` (или задокументировать, что весь словарь, кроме `CONFIRMED`, зарезервирован под второе место). +1 таблица (41→42). Прецедент в проекте **уже есть и работает**: `reputation_aggregates` — явно «NOT append-only, изменяемый кэш пересчёта» (`:769`), и его изменяемость доказана положительным тестом (`reputation-storage.e2e-spec.ts:207`). |
| **Владение** | Самое низкое из трёх. `confirmed_sales.id` остаётся **стабильным** — FK из `reviews`, funnel, репутация и ФЗ-152-путь не меняются вообще. Диспут после подтверждения (которого сегодняшняя машина не умеет, а ADR-0040 §16 явно хочет) ложится в изменяемую таблицу без единой правки якоря. |
| **Конфликт с инвариантами** | Ни одного нарушенного. Появляется новая обязанность: две таблицы должны сходиться — но она **проверяема одним запросом** (у каждой `CONFIRMED`-строки подтверждения есть ровно одна строка сделки), в отличие от «правильно ли классифицирована колонка» в A-ii. |
| **Обратимость** | **Высокая.** Разделение факт/состояние — обычная нормализация; свернуть обратно можно, если реальность окажется проще. |
| **Цена, которую надо назвать честно** | Запись о сделке живёт в двух местах, и читателю надо знать, в каком. Плюс миграция «сузить статус» задевает принятый ADR-0038 (аддитивно — сужение зарезервированного словаря, не отмена решения). |

## 5. РАЗВИЛКА B — `reviews.superseded_by_id` против append-only-триггера

### 5.1 Что на самом деле сломано (сильнее, чем «форма спит»)

Три факта из схемы, которые нужно держать рядом:

```
database_schema.sql:721  superseded_by_id UUID REFERENCES reviews(id) ON DELETE SET NULL  -- forward-указатель
database_schema.sql:737  CREATE UNIQUE INDEX uq_reviews_current_per_direction
                           ON reviews(confirmed_sale_id, direction) WHERE superseded_by_id IS NULL;
database_schema.sql:742  CREATE TRIGGER trg_reviews_immutable BEFORE UPDATE OR DELETE ON reviews …
```

Указатель **вперёд**: чтобы пометить предшественника, нужен UPDATE **старой** строки — а он
заблокирован. Значит `superseded_by_id` навсегда NULL у всех строк. Значит частичный unique
`WHERE superseded_by_id IS NULL` покрывает **все** строки и работает как **полный**
`UNIQUE(confirmed_sale_id, direction)`.

Отсюда — уточнение к формулировке «партиал-unique head сейчас INERT»: он **инертен только потому,
что писателей нет вовсе**. По форме он **не инертен, а активно запрещающий**: он делает
редактирование-в-грейс (ADR-0039 §3 / owner fork 3: «правка внутри 72 часов = новая строка-преемник»)
**структурно невозможным**. И это не гипотеза — это **проверено зелёным тестом в репозитории**:

```
backend/test/reputation-storage.e2e-spec.ts:95
  it('one-CURRENT-per-(sale,direction): a second head (superseded_by_id NULL) is rejected …')
```

Тест утверждает как желаемое ровно то, что делает целевое поведение недостижимым. Это классический
случай, когда **замок зелёный, потому что меряет не то, что объявляет**.
**Антарая: `бхранти-даршана`.**

**Долг шире `superseded_by_id`.** На той же append-only таблице лежат ещё две колонки, изменяемые
по замыслу:
- `moderation_status VARCHAR(20) NOT NULL DEFAULT 'PENDING'` (`:719`) — переходы
  PENDING→APPROVED/REJECTED/CHANGES_REQUESTED (ADR-0040 §2);
- `is_visible BOOLEAN NOT NULL DEFAULT FALSE` (`:720`) — double-blind: ADR-0039 §3 прямо пишет
  «обе стороны раскрываются вместе — это действие планировщика/события», то есть UPDATE.

Обе заблокированы тем же триггером. Значит **любая** ветка Развилки B, решающая только
`superseded_by_id`, оставит `reviews` нереализуемой ещё по двум осям. Это надо решать одним заходом.

### 5.2 Что говорят собственные прецеденты платформы

У проекта уже есть **два** рабочих ответа на «как супersede в append-only», и `reviews` изобрёл третий:

| Прецедент | Механизм | Голова определяется | Детерминизм |
|---|---|---|---|
| `consents` (мигр. 0029/0036) | без указателя вовсе | `ORDER BY seq DESC` (`:1227`, `idx_consents_seq_current :1231`) | полный (тотальный порядок; ровно это чинила 0036) |
| `moderation_decisions` (ADR-0011 §3) | **обратный** указатель `supersedes_decision_id` (`:460`), ставится на **новой** строке при INSERT + биконстрейнт `chk_moddec_override` (`:465-467`) | строка, на которую никто не ссылается | полный (анти-join, а не разрыв ничьей) |
| `reviews` (мигр. 0040) | **прямой** указатель + частичный unique по голове | никак — указатель невозможно поставить | — |

Обратный указатель совместим с append-only **по построению**: он всегда пишется в момент INSERT
новой строки. Прямой — нет. Это не вопрос вкуса, это разница «пишу о себе» vs «пишу о чужой строке».

### 5.3 Ветки с ценой

#### Ветка B-i — **резолв по `seq DESC`; выбросить `superseded_by_id` и частичный unique** (модель `consents`)

| Ось | Цена |
|---|---|
| **Миграция сейчас** | Одна, на **пустой** таблице: `DROP INDEX uq_reviews_current_per_direction`, `DROP COLUMN superseded_by_id`, `DROP INDEX idx_reviews_subject_market` → пересоздать без предиката `superseded_by_id IS NULL`. `idx_reviews_current_seq` (`:740`) уже существует и становится главным индексом. Ноль данных → ноль риска. |
| **Миграция потом** | Та же самая, но на живых отзывах, и с обязательным ответом «какая из накопленных строк — голова», которого в данных нет. |
| **Урок 0036 (монотонный `seq`)** | **Соблюдён идеально** — это буквально модель `consents` после 0036: тотальный порядок, разрыв ничьей невозможен, «побеждает записанный последним» разрешается причинно. |
| **Симметрия с `moderation_decisions`** | **Нет.** Платформа получает две разные модели супersede вместо одной. Читателю нужно помнить, у какой таблицы какая. |
| **Что теряется** | Явная ссылка «эта правка заменила вон ту». Восстановима запросом (соседний `seq` в той же паре), но в строке её нет. Для правки-в-грейс это, вероятно, неважно; для юридического «что именно изменил автор» — важнее. |
| **Решает ли `moderation_status`/`is_visible`** | **Нет.** Обе остаются заблокированными. |

#### Ветка B-ii — **обратный `supersedes_review_id` + UNIQUE** (модель `moderation_decisions`)

| Ось | Цена |
|---|---|
| **Миграция сейчас** | Одна, на пустой таблице: переименовать/заменить колонку на `supersedes_review_id UUID REFERENCES reviews(id)`, снять частичный unique по голове (голова = «на кого не ссылаются», индексом это не выражается — нужен либо анти-join, либо `seq DESC`), добавить индекс `ON reviews(supersedes_review_id) WHERE … IS NOT NULL` — точная копия `idx_moddec_supersedes` (`:472`). |
| **Миграция потом** | Дороже: помимо переименования — восстановление цепочек по данным, которых не будет. |
| **Урок 0036** | **Соблюдён**, если оставить `seq` (он уже есть) для порядка. Обратный указатель даёт **происхождение**, `seq` — **порядок**; это не дубль, это две разные вещи, и `moderation_decisions` живёт ровно так, только без `seq`. |
| **Симметрия с `moderation_decisions`** | **Полная.** Одна модель супersede на всю платформу; ревьюеру и агенту-оператору не нужно учить второй диалект. Для ADR-0040 (агент-модератор отзывов через тот же `moderation_decisions`) это ощутимо: две соседние таблицы будут читаться одинаково. |
| **Что теряется** | «Одна голова на (сделка, направление)» перестаёт быть DB-инвариантом и становится инвариантом приложения. Это осознанный размен: у `moderation_decisions` его тоже нет. |
| **Решает ли `moderation_status`/`is_visible`** | **Нет.** Те же две колонки остаются заблокированными. |

#### Ветка B-iii — **оставить форму как есть, решить в behaviour-слайсе**

| Ось | Цена |
|---|---|
| **Миграция сейчас** | Ноль. |
| **Миграция потом** | Одна из B-i/B-ii, **плюс** снятие уже поставленного зелёного теста, который кодифицировал неверный инвариант (`reputation-storage.e2e-spec.ts:95`), **плюс** правка ADR-0039 §3, который называет `superseded_by_id` механизмом. |
| **Урок 0036** | Соблюдён формально (`seq` есть), но не применён: рядом с ним стоит несовместимый второй механизм. |
| **Симметрия** | Третий диалект супersede остаётся в каноне. |
| **Скрытая цена** | Главная и не бухгалтерская: **зелёный тест закрепляет ложный инвариант**. Пока он в наборе, любой следующий читатель (человек или агент) примет «вторая голова отклоняется» за требование продукта, а не за побочный эффект неработающего указателя. Это ровно тот способ, которым в этом проекте уже трижды рождался класс «форма есть, поведения нет» — и, в отличие от первых трёх раз, **сейчас он записан в приёмку**. |
| **Когда это правильный выбор** | Если держатель считает, что вся Развилка B должна решаться **вместе** с `moderation_status`/`is_visible` (см. ниже) — тогда откладывание осмысленно, но откладывать надо **явно**, погасив тест и пометив ADR-0039 §3, а не молча. |

#### Ветка B-iv *(добавлена лейном — она единственная закрывает все три колонки)* — **неизменяемое содержание + изменяемое состояние рядом**

`reviews` хранит то, что автор написал (рейтинг, текст, автор, сделка, `seq`) — append-only, честно
и навсегда. Всё, что **меняется по замыслу** (`moderation_status`, `is_visible`, ссылка на преемника),
переезжает в соседнюю изменяемую строку состояния — тем же приёмом, каким `reputation_aggregates`
уже объявлен «NOT append-only, изменяемый кэш» (`:769`), а модерационный вердикт уже живёт отдельным
реестром `moderation_decisions`.

| Ось | Цена |
|---|---|
| **Миграция сейчас** | Самая крупная из четырёх: +1 таблица (41→42), вынос трёх колонок из `reviews`. На **пустых** таблицах — по-прежнему одна миграция без данных. |
| **Миграция потом** | Существенно дороже: три колонки с историей, которой в append-only не сохранилось. |
| **Урок 0036** | Соблюдён: `seq` остаётся порядком фактов; состояние живёт там, где ему разрешено меняться. |
| **Симметрия** | Полная и **вглубь**: `reviews` = факт, `review_state` = состояние, `moderation_decisions` = решение, `reputation_aggregates` = кэш. Четыре роли, четыре формы, ни одной подмены. |
| **Совпадает с Развилкой A** | Да — это **та же самая ветка A-iii**, применённая к отзывам. Если держатель выберет A-iii, выбор B-iv делает канон однородным; если выберет A-ii, B-iv станет внутренне непоследовательным. **Развилки A и B связаны — их стоит решать одним движением.** |
| **Цена, которую надо назвать** | «Отзыв» перестаёт быть одной строкой. Для чтения это join; для приёмки — две таблицы вместо одной. |
