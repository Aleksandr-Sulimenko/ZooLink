## 0. Чего эти оси НЕ увидят (пустая клетка видна как пустая — объявлено ДО чисел)

1. **Поведение под реальным продакшн-трафиком.** Всё меряно на одиночных запросах curl. Нет
   конкурентности, нет насыщения пула, нет thundering-herd при возврате зависимости. Вывод
   «самолечится за N секунд» верен для одного клиента, не для 10k RPS.
2. **Реальный отказ внешнего провайдера (SMS.RU / Unisender).** Адаптер жёстко зашит на
   `https://sms.ru` (`smsru.adapter.ts:15`). Проверить «провайдер лёг → 503» вживую = сделать
   реальный исходящий вызов стороннему вендору — это **outward-действие вне моего мандата**
   (дир. №7), и я его НЕ делал. Ветка `ProviderError → 503` подтверждена статически + юнит-спекой
   + живым доказательством, что фильтр вообще работает (см. §2в) — но НЕ сквозным прогоном.
3. **Долгий прогон.** Максимальное непрерывное наблюдение — ~8 минут на отказ. Утечки дескрипторов,
   рост памяти при часах недоступности зависимости, переполнение лога — не мерены.
4. **Многоинстансность.** Один экземпляр API и один worker. Гонки advisory-lock между репликами
   (находка AUDIT4 про pooled-соединение) НЕ воспроизводились.
5. **MinIO живьём.** MinIO не поднимался вообще; проверка storage-пути шла в режиме «хранилище
   мертво» (это и было нужно), но «MinIO жив, креды битые → 403 от S3» не наблюдался.
6. **Реальный дедлеттер.** Событие до `dead_lettered_at` не доводилось (нужно 8 настоящих
   отказов консьюмера); наблюдаемость дедлеттера оценена по коду + доказанному отсутствию метрик.
7. **CI-половина.** Ничего не гонялось в GitHub Actions.

### (а) Redis недоступен

Убит `redis-server :6390` (host :6379 нетронут — `redis-cli -p 6379 ping` → `PONG` во время всего опыта).

| путь | наблюдено | вердикт |
|---|---|---|
| `/health/live` | **HTTP 500** | 🔴 **fail-DEADLY** |
| `/health/ready` | **HTTP 500** (ожидалось 503) | 🔴 неверный код |
| `POST /v1/auth/register/phone` (OTP в Redis) | HTTP 500 | fail-closed |
| `GET /v1/me` | HTTP 500 | fail-closed |
| `GET /v1/listings?limit=1` (публичное чтение) | HTTP 500 | fail-closed |
| `GET /v1/listings/{id}` (view-dedup) | HTTP 500 | fail-closed |
| `POST /v1/me` c `Idempotency-Key` | HTTP 500 | fail-closed (задумано) |
| `POST /v1/listings` (**задуманный fail-OPEN** квоты) | HTTP 500 | 🔴 деградация НЕДОСТИЖИМА |
| `GET /metrics` (несёт `@SkipThrottle`) | **HTTP 200** | ✅ выжил |

**Образец — дыра, ради которой ось существует:**
```
$ curl -s -w '\nHTTP %{http_code}\n' http://127.0.0.1:3377/health/live
{"type":"about:blank","title":"INTERNAL SERVER ERROR","status":500,"code":"INTERNAL",
 "instance":"/health/live","requestId":"538aa178-16ad-4bc0-88ac-de17625e4208",
 "detail":"An unexpected error occurred."}
HTTP 500
```

**Адресность (ось 13) — доказано СВОЕЙ мутацией.** Тот же `/health/live` при **PG** мёртвом
(Redis жив) отвечает **200**, а `/health/ready` — корректным **503**:
```
=== PG DOWN, Redis UP ===
/health/live:  {"status":"ok"} HTTP 200
/health/ready: {"...","status":503,"code":"UPSTREAM_UNAVAILABLE"} HTTP 503
```
Значит дефект — **именно Redis-контур**, а не общая поломка health. Второй независимый
свидетель: `/metrics` — единственный маршрут в кодовой базе с `@SkipThrottle()` — под тем же
отказом отдаёт 200. Причина локализована однозначно.

**Механизм.** `RateLimitModule` вешает `ThrottlerGuard` глобально через `APP_GUARD`
(`rate-limit.module.ts:22`) на хранилище `ThrottlerStorageRedisService`
(`rate-limit.module.ts:19`). Гвард отрабатывает **до** хендлера; при мёртвом Redis он бросает →
500. `HealthController` (`health.controller.ts:8-14`) не несёт `@SkipThrottle()` —
`grep` по всему `src` даёт ровно одно применение декоратора: `metrics.controller.ts:14`.
Сам хендлер `live()` при этом честно бездеп: `return { status: 'ok' }` (`health.controller.ts:20`).

**Почему это блокер, а не хвост.** `backend/Dockerfile:36` — контейнерный HEALTHCHECK бьёт
именно в `/health/live`:
```
CMD node -e "fetch('http://localhost:3000/health/live').then(r=>process.exit(r.ok?0:1))..."
```
Моргнул Redis → `/health/live` 500 → `r.ok=false` → контейнер **unhealthy**. Проба живости,
чья единственная задача — не зависеть ни от чего, зависит от Redis. На любом оркестраторе с
рестартом по liveness (Swarm, будущий k8s, autoheal) это **усилитель аварии**: моргание Redis
→ рестарт всех API → лавина переподключений → авария длиннее исходной.

**Также сломано:** тщательно задокументированный fail-OPEN квоты создания объявлений
(`listing.service.ts:707-715`, комментарий «A Redis outage must not block ALL listing creation
platform-wide») **недостижим** — гвард 500-ит раньше сервиса. Замер: в логе за весь опыт
`grep -c "quota check skipped"` = **0**. Спроектированная деградация — мёртвый код.

**Хорошая новость (доказана):** **самолечение без рестарта**. Redis поднят обратно — без
перезапуска приложения `/health/live` → 200, `/health/ready` → 200 `{"redis":{"status":"up"}}`,
`register/phone` → 202. Авария полностью транзиентна, ручного вмешательства не требует.

### (б) Хранилище (S3/MinIO) недоступно + креды заведомо битые

MinIO не запущен вовсе (`ss -ltn | grep 9000` — пусто; `curl :9000` → код 000), креды в env —
`S3_ACCESS_KEY=dev` / `devsecret`, то есть невалидны для любого реального S3.

```
$ curl -X POST .../v1/listings/{id}/photos/upload-url -H "Authorization: Bearer …"
{"uploadUrl":"http://localhost:9000/zoolink-media/listings/…?X-Amz-Algorithm=AWS4-HMAC-SHA256
 &X-Amz-Credential=dev%2F20260804%2Fru-central1%2Fs3%2Faws4_request&X-Amz-Date=20260804T104641Z
 &X-Amz-Expires=900&X-Amz-SignedHeaders=host&X-Amz-Signature=84f7cda8f0…","method":"PUT",…}

**Вердикт: тихий отказ, наружу невидим.** Presign — чистая локальная HMAC-подпись без единого
сетевого вызова (`s3.adapter.ts:26-29` → `sigv4.ts:51`, `Promise.resolve`). Поэтому:

- `/health/ready` хранилище **не проверяет вовсе** — там только postgres+redis

- отказ всплывает **у клиента** на PUT (замер: `PUT result: 000` — connection refused),
  то есть у продавца, который «не может загрузить фото»;
- ни лога, ни метрики, ни счётчика на стороне платформы.

Это одновременно дефект оси 6 (нет деградации) и оси 8 (владелец узнаёт от пользователей).

**Но обнаружено худшее, и оно доказано:** выбор провайдера управляется **наличием credential,

`UNISENDER_API_KEY`, `EMAIL_FROM` — `z.string().optional().default('')`

Прод-деплой с пустым `SMSRU_API_ID` **успешно загрузится** и молча возьмёт заглушку. Наблюдённые
последствия (живой лог изолированного экземпляра, дефолтный `.env` — ровно эта конфигурация):

- регистрация отвечает **202 VERIFICATION_REQUIRED** — снаружи неотличимо от успеха;

*Проверено и ОПРОВЕРГНУТО (гипотеза не подтвердилась):* я предполагал, что отказ провайдера

(`identity.service.ts:44`) **не содержит** `PENDING_VERIFICATION`, поэтому повтор регистрации
проходит и переотправляет код. Блокировки нет.

## 3. ОСЬ 8 — НАБЛЮДАЕМОСТЬ · вердикт: **🔴 NO-GO**

### (а) Порождённый список фоновых контуров — что покажет тихую смерть?

`grep -rn "@Cron\|@Interval\|setInterval" src --include='*.ts' | grep -v spec` — ровно 4 контура,
плюс 2 консьюмера, работающих внутри тика реле (`Outbox relay started (poll 2000ms, 2 consumer(s))`).

| контур | где | здоровый такт | что покажет тихую смерть |
|---|---|---|---|
| outbox relay | `outbox.relay.ts:57`, 2000 мс | молчит (успех не логируется) | **ERROR каждые 2 с** — единственный громкий контур |
| moderation-escalation | `moderation-escalation.job.ts:26`, `*/15` | INFO «tick done» | 🔴 **НИЧЕГО** |
| retention-expire | `retention-expire.job.ts:27`, `0 * * * *` | INFO «tick done» | 🔴 **НИЧЕГО** |
| transfer-expiry | `transfer-expiry.job.ts:28`, `0 * * * *` | INFO «tick done» | 🔴 **НИЧЕГО** |
| NotificationConsumer | внутри тика реле | молчит | наследует ERROR реле |
| SavedSearchMatchConsumer | внутри тика реле | молчит | наследует ERROR реле |

**Доказано экспериментом, а не рассуждением.** Ускорил ТОЛЬКО безвредный escalation-крон
(`MODERATION_ESCALATION_TICK_CRON='*/10 * * * * *'`; в БД 0 записей `PENDING_MODERATION` —
тик holостой), убедился, что он тикает, затем убил PG в 14:19:25:
```
[14:19:00.022] INFO: moderation/escalation tick done — escalated 0 item(s)
[14:19:10.015] INFO: moderation/escalation tick done — escalated 0 item(s)
[14:19:20.016] INFO: moderation/escalation tick done — escalated 0 item(s)
>>> PG KILLED at 14:19:25
```
После убийства за 30 с: строк со словом `escalat` — **0**. Ни ERROR, ни WARN, ни
unhandled-rejection (`grep -icE "unhandled|rejection|AdvisoryLock"` = **0**). Распределение
контекстов лога за опыт — внутренний контроль в одном и том же процессе:
```
153 "context":"OutboxRelay"          ← кричит
 31 "context":"ModerationEscalationJob"  ← все 31 ДО смерти PG, после — ни одной
```
Причина: в `tick()` всех трёх джоб **нет try/catch**; отклонённый промис проглатывается
планировщиком. Разница между работающей петлёй и мёртвой = **отсутствие строки INFO**. Никто и
ничто не следит за отсутствием: нет метрики «последний успешный тик», нет heartbeat.

**Цена по смыслу:** `retention-expire` выполняет **удаление аккаунтов по ФЗ-152**. Его тихая
смерть = молча остановленное юридически обязательное стирание. `moderation-escalation` держит
SLA-эскалацию. **Смежная лана: legal.**

*Смягчает:* сам процесс переживает отказ и самолечится (после возврата PG тики возобновились:
31 → 34 за 25 с, без рестарта).

### (б) Дедлеттер аутбокса — кто узнает?

`onFailure` при `attempts >= MAX_ATTEMPTS` (8) пишет `dead_lettered_at` и логирует
(`outbox.relay.ts:141-148`):
```
Outbox event {id} ({event_type}) dead-lettered after {n} failed attempts: {message}
```
**Это ВСЁ.** Одна строка ERROR в stdout worker-контейнера + колонка в таблице. Метрики нет
(доказано в §3в), алертинга нет (§3д), Sentry в worker **не инициализируется вовсе**
(`grep -n "Sentry\|initSentry" src/worker.ts` → пусто, хотя docblock `sentry.ts:5-6` обещает
«Called from main.ts/worker.ts»), healthcheck worker'а отключён (`docker-compose.yml:82-83`).
Узнать о потерянном навсегда событии можно только вручную:
`SELECT … WHERE dead_lettered_at IS NOT NULL`. **Вердикт: молча.**

*FIXED-VERIFIED против AUDIT4:* прошлая находка «attempts++ на каждый lease → дедлеттер здоровых
событий» **починена** — `claim()` теперь двигает только `next_attempt_at`, счётчик растёт
исключительно в `onFailure` (`outbox.relay.ts:64-66` + `:137-140`, помечено P2-1). Замер живой
БД: `dead_lettered = 0` из 2890 событий.

Единственная кастомная метрика в кодовой базе — `zoolink_audit_actions_total`
(`audit.metrics.ts:23`); `grep -rn "new Counter\|new Gauge\|new Histogram"` по `src` даёт ровно

🔴 **И она мертва — доказано на бегу.** Выполнено аудируемое действие, факт записи подтверждён
в БД, метрика после этого всё равно отсутствует:
```
audit rows BEFORE: 36210
POST /v1/me → HTTP 200
audit rows AFTER:  36211        ← действие реально записано

**не импортирует `MetricsModule`**, а `MetricsModule` не глобальный. `MetricsService` в этом
инжекторе неразрешим → `@Optional()`-заглушка (`audit.metrics.ts:24` `if (!metrics) return;`),
задуманная для worker'а, срабатывает **и в API**. Счётчик не конструируется никогда.
**Это опровергает AUDIT4/devops.md:105-114**, где со слов чтения кода утверждалось, что
`/metrics` экспортирует «Node defaults **+ one audit counter**». Экспортирует только defaults.
Антарая ровно та, что в словаре: замер объявляет себя присутствующим и лжёт зелёным.

### (г) Молчаливые `catch` по `backend/src` — порождённый список с вердиктами

`grep -rn "\.catch(" src --include='*.ts' | grep -v spec` → 4 совпадения;
`} catch` (не-spec) → 36 блоков, каждый прочитан. Проглатывающих — 8; остальные 28 транслируют
ошибку в доменный HTTP-код (P2002→409, P2003→400 и т.п.) и к оси не относятся.

| место | что глотает | вердикт |
|---|---|---|
| `listing.service.ts:313-315` | `captureView` → `logger.warn` | ✅ **оправдан** — best-effort счётчик просмотров не должен ронять чтение; **и он логируется** |
| `listing.service.ts:707-715` | квота создания → `logger.warn`, fail-OPEN | ✅ оправдан по замыслу (abuse-control ≠ гейт корректности), **но недостижим** — см. §2а |
| `listing.service.ts:718` | `.ttl(key).catch(() => -1)` | ✅ оправдан — деградация значения `Retry-After` |
| `optional-jwt.guard.ts:24-26` | битый/протухший токен → аноним | ✅ оправдан — смысл «optional» |
| `media-url.ts:44-46` | `new URL()` → `false` | ✅ оправдан — невалидный URL не в allowlist (fail-closed) |
| `http.util.ts:26` | `res.text().catch(() => '')` | ✅ оправдан — тело нужно лишь для текста ошибки |
| `agent-credential.service.ts:256-258` | `touchLastUsed` → **пусто, без лога** | 🟡 **тихий отказ** — `last_used_at` и есть сигнал «протухший credential»; его отказ невидим. Сам сигнал наблюдаемости отказывает молча |

заслуживают строки в логе.

### (д) Алертинг — существует ли контур вообще?

**Честное «нет». Контура нет ни в каком виде.** Проверено по репозиторию:

- В `docker-compose.yml` **7** сервисов: `proxy`, `provision`, `api`, `worker`, `postgres`,
  `redis`, `minio`. Нет ни Prometheus, ни Alertmanager, ни Grafana, ни единого экспортёра —
  **никто не скрейпит `/metrics`**. `deploy/Caddyfile` проксирует только `/api/*` и `/health/*`,
  `/metrics` наружу не выведен.
- **Правил алертов нет нигде** — ни PromQL, ни alertmanager.yml, ни Grafana-правил (файлов
  `*prometheus*/*alertmanager*/*grafana*/*.rules` в репозитории не существует).
- **Sentry — гарантированный no-op:** `sentry.ts:9` `if (!env.SENTRY_DSN) return false;`, а
  `SENTRY_DSN=` пуст и в `.env`, и в `.env.example:102`. Даже с настроенным DSN **worker не
  отчитывался бы вовсе** — `initSentry` в `worker.ts` не вызывается.
- **CI никого не зовёт:** в `.github/workflows/` нет ни `if: failure()`, ни slack/email-шага.
- `docs/06-operations/monitoring.md` описывает **24 именованных алерта** (`APIHighLatency`,
  `ModerationQueueDepth`, `ModerationSLAPetViolation`, …) и каналы (PagerDuty/Slack/Jira).
  Ни один не сконфигурирован, и **ни один неисполним**: документ не называет ни одного
  конкретного идентификатора метрики, а из требуемых серий не существует **ни одной** (§3в).
  Часть алертов вдобавок предполагает Kubernetes, который ADR-0009 и `docker-compose.yml:2`
  прямо отвергают. Это **декорация**, а не контур.
- `docs/06-operations/runbooks/`: реально существует **один** файл по делу —
  `migration-deploy-order.md`; `database-failover.md`, `storage-failover.md`,
  `service-restoration.md` числятся «Planned» и **не существуют**. Ранбуков «Redis лёг»,
  «реле встало», «дедлеттер» нет — ровно тех, что нужны находкам выше.
- **Healthcheck никого не уведомляет и ничего не чинит:** `restart: unless-stopped`
  перезапускает по **выходу процесса**, а не по `unhealthy`. Контейнер `api`, вечно
  проваливающий health, будет вечно висеть `unhealthy`, не перезапускаясь и никого не извещая.
  У `worker` healthcheck **отключён** (`docker-compose.yml:82-83`) — зависший worker снаружи
  неотличим от здорового.

**Итог оси 8:** владелец не узнает **ничего** из перечисленного, пока не откроет логи руками
или пока не пожалуются пользователи. Для ADR-0006 (операторские роли выполняют ИИ-агенты) это
и есть главный блокер: у агента-оператора **нет программного чтения состояния системы**.

## 4. Находки (severity · антарая · file:line · образец)

**P0-R1 · BLOCKER · `бхранти-даршана` (замер лжёт: проба живости объявлена бездепной и зависит
от Redis) · `health.controller.ts:19-21` + `rate-limit.module.ts:22` + `Dockerfile:36`**
`/health/live` отдаёт **500** при недоступном Redis. Хендлер бездепный, но глобальный
`ThrottlerGuard` на Redis-хранилище отрабатывает раньше; `@SkipThrottle()` во всей кодовой базе
стоит ровно один раз — на `/metrics`. Контейнерный HEALTHCHECK бьёт именно в `/health/live` →
моргание Redis помечает API unhealthy и на оркестраторе с рестартом по liveness даёт
крash-loop. Образец и контр-мутация (PG-down → 200/503) — §2а.
*Починка:* `@SkipThrottle()` на `HealthController` (минимум — на `live`) + `skipIf`/try-catch в
хранилище троттлера, чтобы отказ Redis деградировал, а не 500-ил. **Требует решения security:
fail-open или fail-closed для rate-limit** (fail-open снимает защиту от abuse на время аварии).

**P1-R2 · CRITICAL · `анавастхитатва` (прод-замок заведён для 4 переменных и не удержан на
классе) · `env.validation.ts:132,135,137` + `providers.module.ts:24-31`**
Нет прод-проверки credential SMS/email. Деплой с пустым `SMSRU_API_ID` грузится, молча берёт
заглушку: регистрация отвечает **202**, SMS не уходит **никому**, OTP пишется в лог открытым
текстом (`[STUB] SMS to ***0001: … код подтверждения 181211`). Сигнал — одна строка WARN на
старте. *Починка:* fail-fast в `validateEnv` по образцу `METRICS_TOKEN` (`:225-233`);
заглушку запретить при `NODE_ENV=production`. **→ security** (OTP в логах).

**P1-R3 · CRITICAL · `стьяна` (объявление есть, действия нет) · `moderation-escalation.job.ts:27-38`,
`retention-expire.job.ts:28-42`, `transfer-expiry.job.ts:28-40`**
Все три `@Cron` без try/catch; отказ такта **полностью бесшумен** (доказано: 31 INFO до смерти
PG, 0 строк после, при 153 ERROR от реле в том же процессе). Разница «работает/мертво» =
отсутствие строки INFO, за которым никто не следит. `retention-expire` выполняет ФЗ-152-стирание
→ молча останавливается юридически обязательная операция. *Починка:* try/catch + ERROR в каждом
такте; gauge «последний успешный тик» на контур. **→ legal** (ФЗ-152).

**P1-R4 · MAJOR · `бхранти-даршана` · `audit.module.ts:7-10` + `audit.metrics.ts:24`**
Единственная доменная метрика `zoolink_audit_actions_total` **никогда не регистрируется**:
`AuditModule` не импортирует `MetricsModule`, `@Optional()`-деградация (задуманная для worker'а)
срабатывает и в API. Доказано на бегу: `audit_log` 36210→36211, метрика по-прежнему отсутствует.
**Опровергает AUDIT4/devops.md:105-114.** *Починка:* `imports: [MetricsModule]` в `AuditModule`
+ приёмочный тест «метрика присутствует в скрейпе».

**P1-R5 · MAJOR · `аласья` (перечень алертов вместо контура) · `/metrics` + `docker-compose.yml`**
31 семейство метрик, все `nodejs_*`/`process_*`; ноль доменных. Скрейпера нет, правил нет,
Sentry no-op и в worker не подключён, CI молчит, `monitoring.md` описывает 24 неисполнимых
алерта. Дедлеттер, зависшее реле, backlog эскалации, 5xx — **не наблюдаемы вовсе**. Для ADR-0006
это и есть блокер агент-управляемой эксплуатации.

**P2-R6 · MAJOR · `бхранти-даршана` · `s3.adapter.ts:26-29` + `health.controller.ts:29-30`**
Presign отдаёт **201** при мёртвом хранилище и битых кредах (сетевого вызова нет); хранилище не

периодический пробник) + метрика.

**P2-R7 · MAJOR · `авирати` (деградация спроектирована, но не доведена до боевого режима) ·
